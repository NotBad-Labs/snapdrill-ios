# Execution Decisions

> 记录执行层决策，不替代 ADR。格式：编号 / 日期 / 决策 / 理由 / 影响范围。

## D-20260411-001

- 日期：2026-04-11
- 决策：建立 `docs/memory/` 作为入 git 的可追溯上下文层。
- 理由：Codex 默认不具备隐式跨会话长期记忆；审计工作需要可回放、可审查、可交接。
- 影响范围：文档协作流程、跨 agent 接手效率。

## D-20260411-002

- 日期：2026-04-11
- 决策：接手优先级排序为 `#578`（审计）→ `#574`（删除状态机）→ Apple 账号解除后功能事项。
- 理由：`#578` 是明确指定的接手任务；`#574` 存在已知一致性风险且不依赖外部账号。
- 影响范围：短期开发节奏、Issue 排期。

## D-20260411-003

- 日期：2026-04-11
- 决策：在执行记录中坚持“源头文档优先”，不以快照层反向定义事实。
- 理由：当前文档体系正在收敛到 `PRD + ADR + TDD` 作为上游定义，避免再次出现双入口和语义漂移。
- 影响范围：审计结论判定标准、后续文档变更方式。

## D-20260411-004

- 日期：2026-04-11
- 决策：在进入代码工作前，先完成全量文档上下游关系梳理并固化为 `docs/DOC_DEPENDENCY_MAP.md`。
- 理由：避免“边改代码边补文档”导致的返工；先锁定 Source of Truth 与传播路径，再执行实现与审计。
- 影响范围：`#578` 审计方法、后续功能开发顺序、文档同步效率。

## D-20260411-005

- 日期：2026-04-11
- 决策：文档属性判定采用“内容语义优先”，不按文件名判定。
- 理由：用户指出“文件名与内容可能错位”的真实风险；若仅按文件名，会把错误层级固化并放大返工成本。
- 影响范围：产品文档审读方法、文档重构准则、冲突修复顺序。

## D-20260411-006

- 日期：2026-04-11
- 决策：产品文档治理采用分批执行（语义归类 → 冲突修复 → 结构重构），并输出审读报告留痕。
- 理由：一次性大改风险高、可回滚性差；分批次更适合持续校准，避免新冲突被覆盖。
- 影响范围：产品文档重构节奏、审计可追溯性、后续协作成本。

## D-20260411-007

- 影响范围：接手顺序、后续产出节奏、风险闭环效率。

## D-20260412-002

## D-20260412-003

- 决策：将 `.claude/worktrees/**` 明确排除在文档治理与审计统计范围外。

- 影响范围：`workflow/KNOWLEDGE_MAP/DOC_DEPENDENCY_MAP/DOC_GOVERNANCE_CLOSURE` 的治理口径与后续审计边界。

## D-20260412-004

- 日期：2026-04-12
- 决策：`DeletionScheduler.scheduleDeletion(ids:)` 在空集合输入时直接 no-op，不再提交上一批或改变 UI 状态。
- 理由：空输入原实现会产生副作用（可能误提交上一批、错误弹出 undo toast），与“空操作不改状态”原则冲突。
- 影响范围：`#574` 删除状态机一致性、`LibraryViewModel` 空输入容错、回归风险降低。

## D-20260412-005

- 理由：保持治理节奏不中断，同时确保每个风险项可追溯、可分配、可验证关闭。
- 影响范围：Phase 3 批次执行策略、`docs/memory/code-audit-batch-*.md` 与 GitHub issue 的联动方式。
