## 分歧 2：剔除悬空支腿，认定塌缩建议成立

**接受你的纠正，无保留。** 我 R3 整条围绕"4 处 @Query"的论证——@Query vs Repository 的边界、用 DTS 驳"换 store 不能用 @Query"——**支腿悬空，应整条剔除**。本仓 0 个 @Query 这个事实，让我那段"官方范式是换 container→环境 context 自动刷新→@Query 自动刷新"变成了在反驳一个本仓不存在的对立面。我是在跟自己脑补出来的架构辩论。这是典型的"用通用领域知识填补缺失事实"——我知道 SwiftData 圈子里 @Query vs Repository 是经典争论，就默认你的仓库也站在那个争论里，而你根本没用 @Query。

需要说清楚的是：**剔除这条支腿，并不改变 R3 对"数据 actor"的认定**。DataExecutor 因 SwiftData 主线程陷阱而 off-main 创建，这条依然成立、依然是硬约束驱动、依然判你对——它不依赖 @Query 是否存在。塌掉的只是"Repository 因为 @Query 不适配换 store 才需要"这条理由，而那条理由我 R3 本来就判它"站不住"。所以净效果是：**我 R3 的结论方向不变，但我必须承认我用了一个错误的事实前提去支撑一个本来就该用别的理由支撑的结论。** 这恰恰落进了我 R3 末尾自己立的那条警告——"对的判断被错的账目包裹"。我自己也犯了。

**塌缩建议（ReviewRepository 保留 + Subject/Source/Grade/Tag → TaxonomyRepository）：认定合理，且你给的实证把它从"建议"升级成了"有据"。** 理由分两层：

第一层，**ReviewRepository 不可塌缩，是硬约束，不是偏好**。你给的实证——many-to-many tag 的内存过滤 + SM-2 选题 + 分页 + 批量改名——其中 many-to-many 内存过滤这一条是 `#Predicate` / `@Query` 在当前 SwiftData 下**做不到**的（to-many 关系上的复合谓词支持残缺，这正是我第一轮就标的 SwiftData 弱点）。所以 ReviewRepository 里装的是"框架能力缺口的补偿逻辑"，这是 Repository 模式**唯一**真正无可争议的存在理由：封装一个底层做不到、必须在内存里补的操作。它有真实逻辑、且该逻辑无处可去，保留是对的。

第二层，**Subject/Source/Grade 三份字符级相同的模板复制 + Tag 近纯转发，是 cargo cult 的教科书标本**。我 R3 说"7 个像一实体一个机械套用"是方向直觉，你的 grep 把它坐实为"3 份方法体除类型名外字符级相同"。这已经不是"像"，是字面意义的复制粘贴。三个文件不是三个抽象，是同一个抽象被手抄了三遍——而且因为它们共享同一个 mainContext，连各自的 rollback 都是冗余的（共享 context 上一次 rollback 覆盖全部）。把它们合并成 TaxonomyRepository，不是"减少文件数"的审美，是**消除一个被实例化了三次的零逻辑抽象**——Sandi Metz 那条"宁可重复也不要错误抽象"在这里要反着用：这里连重复都不是真重复，是同一抽象的多份拷贝，合并后是**一份抽象服务三种分类法**，参数化掉实体类型即可。

**唯一要你回头确认的一点（防止我又脑补）：** Subject/Source/Grade 三者除了实体类型，**业务语义上是否真的同构**？字符级相同的 CRUD 方法体证明了"存取逻辑"同构，但没证明"业务规则"同构。具体说——这三种分类法里，有没有任何一个未来会长出独有的约束（比如 Grade 有顺序、需要校验"三年级不能排在二年级前"；Source 可能有层级或外部来源标识；Subject 可能是固定枚举而另两个是用户自定义）？如果三者业务规则会分化，那 TaxonomyRepository 应该用**一个泛型/协议 + 三个轻量特化**，而不是塞进一个无差别大类。如果确认三者就是"名字不同的同一种扁平标签"，那合并成一个无差别 TaxonomyRepository 完全正确。这个判断你在代码里看得见业务规则，我看不见——请你定。

**分歧 2 终态：**
- 认定：数据 actor 对（硬约束，不变）；@Query 支腿剔除（我的事实幻觉）；ReviewRepository 保留（硬约束：补偿 to-many 谓词缺口）；Subject/Source/Grade/Tag 塌缩为 TaxonomyRepository 合理（消除三次实例化的零逻辑抽象）。
- 去污染最小动作：四 Repo 合一，按 context 而非按实体组织；把"消除死锁"的功劳归还 DataExecutor，不再挂在 Repository 名下。
- 仍需你补查：三种分类法的**业务规则**是否同构（决定 TaxonomyRepository 是无差别大类还是泛型+特化）。

## 分歧 3：接受归因修正，撤回对 SmartPaper 的指控

**接受归因修正，完全。** 我 R3 把 to-many+optional 谓词的性能风险**错挂在 SmartPaper 名下**，这是又一处事实幻觉：我在无代码下假设"智能组卷"这个**名字**意味着复杂的多标签组合查询，于是把我第一轮标记的 SwiftData 弱点顺手栽给了它。你的 grep 证明 SmartPaper 是 385 行、单条 scalar `#Predicate`（只过滤 subjectRawValue + difficulty 两个标量）+ 复用既有列的 SortDescriptor + fetchLimit，**根本不碰 tags 这个 to-many 关系**。风险的真实位置在 Library 浏览的 fetchFilteredModels（有 tag 过滤时全量 fetch + 内存 filter）。归因修正成立，我撤回对 SmartPaper 的指控。

而且这条修正比"挂错地方"更进一步：**SmartPaper 的实现本身已经是我 R3 推荐的那一极简档**——"按标量筛选 + 抽 N 题"，甚至用 SM-2 紧迫度排序代替了随机（这比随机更好，因为它让组卷复用了复习信号，是一个真实的产品价值而非花哨）。没有配额、聚合、去重、智能排布层（grep 这些词 = 0）。所以我 R3 担心的"向低频高复杂功能过度倾斜"，在 SmartPaper 上**不存在**。这里没有过早优化。

**但分歧 3 还剩一个没被这次实证触及的部分，我要保留。** 你的实证证明了"实现不复杂"，但没有触及我 R3 真正判为污染的那一点——**价值链文档与实现的内部矛盾**（文档把复习标为"附加值"，工程却把 SM-2 + 组卷做成核心闭环）。"SmartPaper 只有 385 行很精简"和"复习闭环到底是不是这个产品的核心价值"是两个独立问题。前者你证伪了（不复杂），后者没被证伪（仍是一份文档说一套、产品定位是另一套的矛盾）。所以：

**分歧 3 终态：**
- 认定：实现复杂度污染**不成立**（撤回，SmartPaper 已是极简档，归因错在我）；to-many 风险归因修正为 Library.fetchFilteredModels。
- 仍然保留的认定：价值链描述与产品实际重心的矛盾**是文档侧的待澄清项**，与代码复杂度无关——这条这次实证没碰，不能算被清除。
- 去污染最小动作：（技术侧）无，SmartPaper 不用动；若要优化，优化对象是 Library 的全量 fetch+内存 filter，不是组卷。（产品侧）把价值链文档里"复习=附加值"与"核心闭环"的矛盾显式裁掉一个——但这是产品判断，不是架构污染，权重下调。
- 仍需你补查：Library.fetchFilteredModels 在真实数据量（家庭级数千条）下，全量 fetch+内存 filter 是否构成可观测卡顿——若不卡，这条风险纯属理论，可不动（我第一轮就说过这个量级未必触发）。

## 分歧 1：接受细化，"真边界只有一条半"被证伪

**接受细化，并承认我 R3 低估了。** 我 R3 说"真边界只有一条半（核心/数据零上行依赖），5 里有审美水分"。你用可证伪尺子逐包查，4 个边界都举得出"删了会被打开的具体编译错误"：Core（deps=[]，并入则核心逻辑能 import SwiftData、测试失去独立性）、Data（封 ZIPFoundation，并入则 View 能绕过 actor 直接碰存储）、UI（封 Mantis，6 个消费者共享）、Features（target 依赖图拦截跨 Feature import）。

我低估的具体机制是这个：**我只想到了"分层方向"（上层不依赖下层）这一种可被编译验证的边界，漏了"第三方依赖封装"这一种。** "把每个第三方库（ZIPFoundation、Mantis、Firebase）关进单独包"产生的收益不是审美——它是**可编译验证的依赖收敛**：包外的任何代码想直接 import ZIPFoundation/Mantis 都会编译失败，于是第三方 API 的爆炸面被物理限制在单包内，换库时改动面被编译器锁定为"只可能在这一个包里"。这是 `internal` 给不了的（`internal` 管符号可见性，管不了"哪个包有权 link 哪个第三方 target"）。所以这 4 个边界各自对应一条可证伪的"删了就报错"的约束，**不是审美，是我漏算的一类编译验证收益**。我接受 (a)。

**对 (b) Infrastructure 死占位的处置：建议"从链接里摘掉，降为纸面保留 / git 分支保留"，而不是"标注未来激活占位防误改"。** 理由是可证伪的，不是偏好：

你已经实证它是"已链接但死"——CN 构建里 import 0 次、FirebaseBootstrap 引用 0 次，且它"保 Core 零依赖"的辩护**站不住**（Core 零依赖由 Core 自己 deps=[] 保证，与 Infra 是否存在无关）。一个 link 了但全仓零 import 的包，提供零编译验证收益（它没拦截任何东西，因为没有东西依赖它），却持续产生成本：每次全量编译要处理它、每个新 agent 读架构时要理解"这个空包是干嘛的"、它的存在本身是一条"未来会有海外版"的**推测性承诺**，而推测性承诺正是 pre-PMF 阶段最该砍的东西（我第一轮判据：押注未确定的未来，期望值为负）。

"标注未来激活占位防误改"这个方案我反对，因为它把成本固化：注释和"纸面保留"一样能防误改，但不强迫全量编译和架构理解持续为一个 speculative 层付费。**正确处置是把它降到"零运行成本"的形态**——从 Package.swift 的 link 依赖里摘掉，代码留在 git（分支或一个 `future/` 目录或干脆 git 历史里），配一行 ADR 记"海外版激活 Firebase 时从此处恢复"。这样未来激活的成本（从 git 恢复一个包）远低于现在持续背着它的成本，且符合"YAGNI：需要时再建，建的成本很低就不必预建"。

唯一让我犹豫的反方：如果"未来海外版"不是 speculative 而是**已排期的确定路线**（有时间表、有承诺），那预留占位就从"投机"变成"已知需求的脚手架"，保留链接的理由会增强。这取决于海外版的确定性等级——这是我看不见的商业事实，你定。但**即便保留，也应保留为"有 ADR、有激活条件、当前零 import 是已知状态"的显式占位，而不是默默 link 着的死代码**。

**分歧 1 终态：**
- 认定：4 个边界非审美（每个对应可证伪的"删了就报错"约束，含我漏算的"第三方依赖封装"这一类编译验证收益）；第 5 个包 Infrastructure 是 speculative 死占位（实锤：零 import、零引用、辩护不成立）。
- 去污染最小动作：Infrastructure 从 link 依赖摘掉，代码降为 git/纸面保留 + 一行 ADR 记激活条件；除非海外版是已排期的确定路线，那就转为"显式标注的占位"而非"默默 link 的死包"。
- 仍需你补查：海外版的确定性等级（speculative vs 已排期），决定 Infrastructure 是"摘掉"还是"显式占位"。

**第二类——仍未被证实、我至今仍悬在推测上的结论（你尚未实证，我主动标注，免得它们冒充已验证结论混过去）：**
