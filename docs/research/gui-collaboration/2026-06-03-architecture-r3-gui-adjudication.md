## 前提重估："多 agent 并行"是否推翻"单人 → 协调收益≈0 → 少架构"？

**部分推翻，但要把收益拆细——因为项目把三种不同的收益混在了一起。**

我第一轮的"单人"推理有一个隐含错误：我把"协调成本"等同于"人际沟通成本"，于是单人 → 沟通≈0 → 协调收益≈0。但协调成本的真正构成是**"并行修改者之间的冲突率 × 冲突解决成本"**，而不是"开会沟通的次数"。多个 AI agent 在独立 worktree 并行改代码，冲突率是实打实上升的——哪怕修改者全是 AI、整合者只有你一个人。这一项我漏了。

但要立刻做三点区分，否则会滑向项目的自我合理化：

**第一，worktree 已经提供了"工作隔离"，SPM 模块并不提供同一种隔离。** git worktree 在**文件系统/版本控制层**隔离 agent；SPM 模块在**编译/依赖层**隔离代码。这是两根正交的轴。项目理由 ① 把"SPM 边界 = AI agent 工作隔离"当成一回事，是偷换概念——agent 的工作本来就被 worktree 隔离了，不靠 SPM。SPM 真正能减少的是**合并冲突**（如果不同 agent 被分派到不同包），而这要求 agent 的任务**按包切分**才成立。

**第二，"减少合并冲突"这个收益，对一个按"层"切分的 5 包结构基本不兑现。** 你的 5 包是 核心服务/数据/UI/功能/基础设施——这是**纵向分层**。但多个 agent 通常是**横向按功能**并行（agent A 做拍照、agent B 做复习、agent C 做导出）。横向并行的 agent 会**同时涌进"功能包"这一个包**，在那里照样撞车。所以"层切分"服务的是依赖纪律，**不是** agent 工作隔离。要真正隔离 agent 工作，得按 feature 切包（CaptureFeature / ReviewFeature / ExportFeature），而你不是这么切的。**结论：项目理由 ① 的前半句（agent 隔离）对这个具体切法基本不成立。**

**第三，真正站得住的是理由 ① 的后半句——编译期单向依赖强制——而且多 agent 把它从"锦上添花"抬升到了"真收益"。** 这是我第一轮明确低估的地方，下面在分歧 1 里展开。

> 净结论：多 agent 把天平往"更多架构"推了一格，但推力来自**编译期依赖强制**这一条，不是来自"模块=隔离"这条。把两者分开，是判定后面所有分歧的关键。

## 分歧 1（模块化）：5 个 SPM 包

**裁决：各半，主轴判为「推导遗漏」——但偏向"对的事情，部分理由是错的"。不构成想法污染，但理由 ① 需要重写。**

**依据：**

第一轮我反对模块化，给的是两条**成本**理由（SwiftData 文件布局崩溃、编译时间）和一条**收益落空**理由（收益团队级、单人无法兑现）。现在：

- 两条成本理由被实证**证伪**了。项目把 `@Model` 全部集中在数据包、未跨模块切分,因而没踩到崩溃——这正是我第一轮提的崩溃风险的正确规避方式（我说的是"激进地把 SwiftData 模型切到独立模块/文件可能触发崩溃"，集中放置恰好绕开）。编译时间也未成为瓶颈。**当我列举的成本都不发生时，反对的天平就塌了一半。**

- "收益团队级、单人无法兑现"这条，被多 agent 事实**部分证伪**。编译期单向依赖强制是一个**真收益**，且是"文件夹+纪律"无法等价提供的。理由很硬：纪律是**软约束**，依赖人（你）在 review 时抓到越界引用；多个 AI agent 并行生成代码时，**潜在越界编辑的产生速率上升，而你的 review 带宽固定**。编译器拒绝向上依赖是**硬约束**，对 N 个 agent 零边际 review 成本。这是 `internal`/`private` 访问控制给不了的——访问控制管的是"谁能看见符号",管不了"依赖方向"。所以"核心层零外部依赖、编译期拒绝反向引用"在多 agent 下是货真价实的防腐化机制。

但要扣住怀疑：**这条收益论证的是"要有依赖方向边界",不是"要有 5 个包"。** 编译期方向强制只需要"沿你想保护的方向存在边界"。真正高价值的边界其实只有一条半：核心/数据层对 UI/功能**零依赖**。这大概需要 2–3 个包（Core、Data、其余），不必然是 5。5 包里"功能"如果是单包，多 agent 横向并行照样撞车（见前提第二点）；"基础设施"若是杂物抽屉，则是常见的凑数层。所以**原则（编译期方向强制）成立，但包的数量与切法里仍可能掺了"分层越多越干净"的审美惯例**。

**临界点（你问的：文件夹+纪律何时真正不足、必须升级编译边界）：**

不是行数，也不是团队人数,而是**"边界违例的产生速率 > 单一整合者的审查带宽"**。具体三个可观测信号，满足任一即应升级为编译边界：

1. **并行写入者 ≥ 2**（人或 agent）且会改到相邻层——多 agent 已满足。这是你这个项目越过临界点的真实原因，也是我第一轮没算到的。
2. **被保护的依赖方向，一次违例的回滚成本很高**——例如核心层一旦误引入 UI/具体存储，会迅速向多处扩散。这种"高扩散性边界"值得编译期焊死。
3. **审查者无法在每次合并时肉眼核验所有跨层引用**——多 agent 并行下这条几乎必然成立。

反过来，**单人顺序开发、单一变更流、低扩散边界**时，文件夹+纪律仍然够，编译边界只是心理安慰。你的项目恰好跨过了线，所以这里我判你赢——但赢的理由是"多 agent + 依赖方向防腐",不是项目原话里那句"SPM=agent 隔离"。

**若需去污染的最小动作（针对仍可能掺水的部分）:**

- 用一个客观问题校验包数：**逐包问"这个包的存在，是为了强制哪一条依赖方向?"** 答不出明确方向的包（典型嫌疑：基础设施、UI 与功能的边界），就是审美凑数,应合并。保留那些守护"核心/数据 零上行依赖"的边界。
- 若你确实想要 agent **工作**隔离（而不只是依赖纪律),那要按 **feature 切包**，而非按层。你现在的层切分服务依赖纪律、不服务 agent 隔离——别把后者写进理由里给自己背书。

**置信度：中等偏高（约 70%）。** 高的部分：编译期方向强制是真收益、多 agent 抬高了它的价值，这条推理很硬。不确定的部分：5 这个数字里到底有多少是必要边界、多少是审美。**最需要的额外实证**：把每个包的"它强制了哪条依赖方向、删掉它会破坏什么"写出来——凡是只能用"更清晰/更整洁"来辩护、举不出被编译器拦下的具体反向引用的包，就是污染残留。

## 分歧 2（Repository vs @Query）：7 Repository + DataExecutor

**裁决：各半。数据 actor 判为「推导遗漏」（我赢错了，你对）；Repository 这一层判为「理由部分站不住,偏污染」——但污染来源是把两个独立决策捆在了一起。**

**依据，拆成两个独立决策：**

**决策 A：off-main-actor 的数据 actor（DataExecutor）。这条你完全对，我第一轮没强调够。** 我搜了一圈，SwiftData 的 `@ModelActor` 有一个**至今（iOS 26）未修的**著名陷阱：它**在创建时所处的执行上下文**决定 context 跑在主线程还是后台——在 SwiftUI 里几乎总是在 MainActor 上创建，于是"后台 actor"实际仍在主线程跑，该卡还是卡，严重时与 XPC/主线程交互处出现死锁。Michael Tsai（2025-08）与 Matt Massicotte 都确认：可靠的解法就是**确保 ModelActor 在主线程之外创建**，常见手法是用一个外层 actor 的 lazy 属性把它"装箱"。这正是你 DataExecutor"off-main-actor 创建消除真实死锁"在做的事。**所以这是被硬约束（SwiftData 的真实缺陷）驱动的正确决策，不是 cargo cult。我判你赢。**

**但注意:这条只论证了"要一个 off-main 的数据 actor",它一个字都没论证"要 Repository"。** 死锁的解药是 actor,不是 Repository。把"死锁"当成 Repository 的理由,是 non sequitur——你可以有 DataExecutor 而完全不要那 7 个 Repository。别让一个真实的 actor 战功,替一层未被它证明的 Repository 背书。

**决策 B：Repository 取代 @Query，理由是"多 Profile 切换要重建整个 ModelContainer，@Query 视图绑定不适配运行时换 store"。这条比你以为的弱。**

我查了 Apple DTS 的明确答复：运行时**替换整个 ModelContainer 是官方认可的做法**，而且 DTS 工程师明说——当你用 `modelContainer(_:)` 更新后,**注入环境的 modelContext 会自动改变,从而触发视图层自动刷新**;并且他给的"典型该这么做的场景"恰恰就是**"每个用户有自己的 store、登录时切换 store"**——和你的多 Profile 物理隔离一模一样。换句话说:**"运行时换整个 container"非但不与 `@Query` 冲突,官方给的范式正是"换 container → 环境 context 自动换 → `@Query` 视图自动刷新"。** 所以"@Query 不适配运行时换 store"这个理由,在官方语义下不成立。

那 Repository 还剩什么站得住的理由?有一条,但项目没说出来:**`@Query` 只能活在 SwiftUI 视图里**。你 memory 里这类应用要在**非视图语境**访问数据——后台 OCR 回填、导出、复习调度、未来 widget/App Intent。这些地方 `@Query` 用不了,本来就得走 context/actor。这是 Repository(或直接用 DataExecutor 暴露方法)的**真**理由,比"运行时换 store"硬得多。

**所以分歧 2 的真相:**

- 数据 actor:对(硬约束:SwiftData 主线程陷阱)。
- "Repository 因为运行时换 store 才需要":**站不住**(官方范式下 @Query 适配运行时换 container)。
- "数据访问要能在非视图语境用":**站得住**,但这不需要 7 个 Repository,DataExecutor 暴露方法即可。
- **7 个 Repository 这个数量**是最可疑的污染点。7 很像"一个实体一个 Repository"的机械套用(经典 cargo cult:Java/后端那套 one-repository-per-table 搬到一个本地单库 app)。本地 SwiftData 场景下,聚合根没那么多,大量 Repository 往往是把"对同一个 context 的几次调用"包成一个类、再乘以实体数。

**最小去污染动作:**

1. 把"消除死锁"从 Repository 的理由列表里删掉,只留给 DataExecutor。
2. 把 Repository 的存在理由**重写为唯一站得住的那条**:"在非视图语境(后台 OCR、导出、widget)访问数据"。然后用这条理由反过来审 7 个 Repository——**纯粹服务于 SwiftUI 列表/详情的读取,保留 @Query,删掉对应 Repository**(你已经有 4 处 @Query,说明这条路本来就走得通)。
3. 对剩下的写入/后台访问,评估能否collapse 成 1–2 个面向用例的入口(挂在 DataExecutor 上),而不是 7 个面向实体的 Repository。

**置信度:中等(约 60%)。** 不确定来源:我不知道你那 7 个 Repository 是面向实体还是面向用例、4 处 @Query 是有原则的保留还是历史遗留。**最需要的额外实证(去代码里答):**(a) 7 个 Repository 是不是大致"一实体一个"?若是,强烈指向 cargo cult。(b) 那 4 处 @Query 与 7 个 Repository 的边界依据是什么——是"视图内只读 vs 跨语境读写"这种有原则的划分,还是随手而为的不一致?(c) Repository 里是否有任何一个,除了"转发一次 context 调用"之外没有真实逻辑(过滤、组合、缓存、用例编排)?纯转发的就是多余的一层。

## 分歧 3(复习/组卷的架构权重)

**裁决:各半,但污染主要在**「价值链描述」**这份文档本身,而非实现——附一个更重的 pre-PMF 警告。**

**依据:**

先拆"复习/组卷"这个被捆在一起的说法,因为两者复杂度差一个量级:

- **SM-2 间隔复习**:这是 Anki 那套经典算法,纯函数、几百行、无外部依赖、无复杂查询。**它便宜**。"投入了不小工程量"如果指的是 SM-2,那其实没多贵,谈不上过度倾斜。
- **智能组卷**:这才是复杂度/风险的真正聚集地——它通常要按多维标签做筛选、组合、去重、配额,正好命中我第一轮警告的 SwiftData "to-many + optional 谓词"弱点。如果组卷逻辑很重,这里才是"向低频高复杂功能倾斜"的真嫌疑。

再判"复习是核心还是增值"这个**项目自身的内部矛盾**(我第一轮就点过它自相矛盾):

从第一性的产品价值看,**"拍照+OCR+存档"是已被商品化的能力**——Apple 备忘录、各种扫描 app 都做。一个家长**专门**用你这个 app 而不是通用扫描器的理由,大概率正是**"错题本+遗忘曲线复习"这个学习闭环**。若如此,**复习是核心价值,"价值链里把复习标为附加值"才是那份被污染的文档**——很可能是早期把产品当成"扫描 app"而非"学习 app"来想,残留下来的旧框架。这种"文档说一套、工程做另一套"恰恰是自我强化合理化的典型痕迹:没人回头改文档,于是两套并存。

**但这里有个比"谁是核心"更要命的 pre-PMF 问题,我必须讲重:零用户阶段,你并不知道复习闭环会不会被用。** 把可观工程量(尤其智能组卷)押在一个**未被验证**的价值假设上,本身就是风险——无论它将来是不是核心。最健康的姿态是承认价值链是**假设不是事实**,然后让"先验证哪条路被真实使用"来决定资源,而不是同时把采集可靠性和复习/组卷都做重(两头下注,pre-PMF 的聚焦风险)。

**最小去污染动作:**

1. **解决文档与实现的矛盾,二选一并写死**:要么承认这是"学习 app、复习是核心"(那就把价值链描述改对,工程投入正当);要么承认复习是增值(那就给智能组卷做复杂度审计、考虑砍到 SM-2 够用的最小版本)。**现在两套并存,就是污染本身。**
2. 对**智能组卷**单独做一次"它真的需要这么复杂吗"的审计:MVP 阶段,"按标签筛选+随机抽 N 题"可能就够,复杂配额/智能排布是典型的 pre-PMF 过早优化。
3. 若判定复习是核心,回头检查它有没有反向约束你的持久化建模(SM-2/未来 FSRS 的复习历史是 add-only 友好的吗?这关联第一轮的 CloudKit 锁定判据)。

**置信度:较低(约 50%)。** 因为裁决依赖一个我观测不到的变量——**你的真实产品价值假设**,以及智能组卷的实际复杂度。**最需要的额外实证:**(a) 智能组卷有多少行、依赖多复杂的查询?(b) 有没有任何早期信号(哪怕你自己当种子用户)表明复习闭环会被用,还是它纯粹是"应该有"的推测?(c) 砍掉智能组卷、只留 SM-2 + 手动选题,产品价值主张会不会塌——若不会塌,组卷就是当前该冻结的增值。

## 分歧 4(采集主路径可靠性):验证问题 + 合格线

你已有的(草稿恢复、OCR 失败重试提示、暂存图片重试)是**必要不充分**。它们都是"处理失败"的机制,但都绕开了那个核心问题:**原图在 OCR 之前是否已经持久化到不会因进程死亡而丢失的地方**。下面 5 个问题就是去戳这一点。

**去代码里实证回答的 5 个问题:**

1. **崩溃原子性**:用户拍完照、OCR 尚未完成时,如果 app 此刻被杀(崩溃 / 上滑关闭 / 系统 OOM 回收),重启后那条记录还在吗?——还是说原图此刻只在内存或临时目录,会丢?

2. **暂存的"暂存"到底有多持久**:你说的"暂存图片重试",那个暂存区是**落盘且重启后仍在**(真持久),还是进程内/启动即清的临时缓存(伪持久)?这是合格与否的分水岭——如果暂存活不过进程死亡,等于没存。

3. **写入顺序**:主路径的代码顺序是「先持久化原图 → 入队 OCR → 回填文本」(图优先,安全),还是「先 OCR → 拿到文本再把图文一起存」(OCR 优先,崩在 OCR 中途就丢采集)?

4. **状态是否被持久化且穷尽**:采集/OCR 的状态(captured / ocr_pending / ocr_failed / done 之类)是**写进了数据库、重启后能恢复**,还是只活在内存里?每个状态是否都有明确的恢复/重试路径,还是"草稿恢复"是另搭的一套 ad-hoc 机制、和 OCR 状态机各管各的?

5. **批量中断行为**:连续拍多张时中途被打断,**已拍的每一张是各自独立落地**(部分进度幸存),还是整个会话是一个单元、一断全丢?

**最低合格线(falsifiable):**

> **原图必须在尝试 OCR 之前就持久化到磁盘/数据库,使得任何一次采集都不会因 OCR 失败或 app 终止而丢失;每条采集都有一个被持久化、可重启恢复、可重试的状态。OCR 是一个可重跑的"富化"步骤,而不是"持久化的前置闸门"。**

判定规则很简单:**如果问题 3 的答案是"OCR 优先",或问题 2 的答案是"暂存活不过进程死亡",则不合格**——无论你有多少层重试提示,因为重试的前提是数据还在,而这两种情况下数据本身可能已经没了。草稿恢复 + 重试是合格线之上的体验加分,够不到合格线本身。反过来,只要原图在 OCR 前已落盘、状态已持久化,即使没有花哨的草稿恢复,也已经过线。

**置信度:高(约 85%)——对"合格线该划在哪"这件事。** 这条几乎是纯硬约束推导:最高频主路径 + 数据不可丢 = 采集必须先于富化落地。唯一不确定的是你的实现落在线的哪一侧,而那正是上面 5 个问题要替你测出来的。

## 综合:四个裁决的元观察

把四个裁决并排看,有个值得你警惕的模式:

- **分歧 1 和 2,我第一轮判错的根因是同一个——我用"纯单人"建模了一个其实是"多 agent + 物理多 store"的系统。** 多 agent 抬高了编译期依赖强制的价值(分歧 1),物理多 store + SwiftData 主线程陷阱抬高了数据 actor 的价值(分歧 2)。这两处你赢得正当,是我的前提缺了客观因素。

- **但在你赢的每一处旁边,都贴着一处"对的决策被错的理由包裹"**:分歧 1 里"SPM=agent 隔离"是错理由(真理由是依赖强制);分歧 2 里"死锁→Repository"和"换 store→不能用 @Query"都是错理由(真理由是 actor 解死锁、非视图语境访问需要它)。**这正是自我强化合理化最危险的形态——不是做错了事,而是为对的事记了错的账。** 错的账会在下一次决策时把你引向错的方向(比如用"agent 隔离"去论证再拆更多包,或用"@Query 不行"去论证砍掉本可保留的 @Query)。

- **分歧 3 和 4 指向同一件事:pre-PMF 的聚焦。** 复习/组卷的重投入与采集可靠性的未完全坐实并存,说明工程精力可能没有像第一轮判据要求的那样、极度向"采集不丢"这条最高频主路径倾斜。

**我整体最需要的一项额外实证**,如果只能选一个:**逐个决策去查"记的账对不对"——即每条架构理由,能不能举出一个具体的、可被编译器/运行时验证的事实来支撑,而不是只能用"更清晰/官方方向/防腐化"这类无法证伪的措辞。** 凡是只剩下不可证伪措辞的理由,就是想法污染的残留,无论它包裹的那个决策本身是对是错。这也是你下一轮揭示更多局部时,我会一直拿来戳的那把尺子。
