# SnapDrill 文档体系语义层审计报告【维度 1：跨文档语义链条】

> **版本**：2026-05-20 | **审计员**：Antigravity (Gemini 3.5 Flash (High)) 独立审计
> **审计范围**：
> - L1 Vision: `docs/product/product-vision.md`
> - L2 Design: `docs/product/product-design.md`
> - L3 Requirements: `docs/product/product-requirements.md`
> - L4 Tech: `docs/tech/architecture.md` + `docs/tech/non-functional-requirements.md`
>
> **审计纪律**：基于 F-008 纪律与 ADR-005 规范，执行完整 L1→L2→L3→L4 正向链条强校验，挖掘文档体系在演进中产生的语义偏离、逻辑残缺和概念漂移。

---

## 邻层正向校验概述

本轮审计采用**三方对抗模式**，由 Antigravity 针对每对邻层（V→D, D→R, R→T）进行正向强校验：
1. **L1 Vision → L2 Design (V→D)**：核对产品愿景的价值主张、使命、原则是否完全在交互与设计决策中落地，有无隐性冲突。
2. **L2 Design → L3 Requirements (D→R)**：核对设计决策在需求规格书中有无漏损、冲突、或缺乏配套逻辑。
3. **L3 Requirements → L4 Tech (R→T)**：核对需求功能规格与性能标准是否能在技术架构、模块划分和非功能需求（NFR）指标中找到合理的实现依据。

## 详细 Finding 描述

### L1 Vision → L2 Design (V → D)

#### 🔍 F-D1-001 [LOW] — 物理环境鲁棒性保障与 Pro 增值功能的边界模糊
- **上游主张**：Vision Principle 1 特别强调“对复杂物理环境的鲁棒性（夜晚昏暗光线、揉皱的试卷、红蓝黑笔交错、阴影和折痕）是核心技术考量——家长的真实拍摄场景远比实验室恶劣”。
- **下游现状**：Design 在“OCR定位”中针对鲁棒性的设计仅提出“高精度识别模式 + 稳定性指示器引导用户对准 + 自动框选”，这仅解决了物理拍摄阶段的抖动与范围问题。而真正应对“红蓝黑笔交错、折痕与阴影”的图像去噪和增强处理决策，完全被归在 Pro 版的“图片处理增强”中（“去手写/去批改痕迹/试卷还原”）。这导致免费用户在恶劣光线和皱折等普通真实采集场景下，缺乏设计与交互层的基本去干扰处理（如端上对比度调整或二值化阈值自适应交互决策），与 Vision 的“录入体验是生命线”原则产生体验脱节。

#### 🔍 F-D1-002 [MEDIUM] — “复习是可选功能”与底部常驻 5 Tab 顶级信息架构的直接张力
- **上游主张**：Vision 明确定义产品定位“不是 Anki 式记忆工具”，强调“复习只是附带福利，SM-2 是可选功能，不应侵蚀核心采集/管理/导出路径的简洁性”。
- **下游现状**：Design 在导航结构中将“复习”常驻为底部 Tab 栏的五个顶级 Tab 之一（首页/题库/采集/复习/设置）。这在最核心的 App 顶级信息架构上将“复习”提升到了与“采集”、“题库”平起平坐的顶级权重。虽然 Design 的“复习设计 - 克制原则”在文案中声称“复习入口在信息架构中不得压过采集和题库”，但在物理架构上它已严重侵蚀了主路径的极简视觉层级，与 Vision 极力避免喧宾夺主的定位产生语义偏离。

#### 🔍 F-D1-003 [LOW] — 海外华人双语 OCR 特定需求（繁体字/混排）的设计缺失
- **上游主张**：Vision 提及目标用户包括“海外华人学生”，核心痛点是“周末中文学校或家长自用中文教材场景，差异主要在双语 OCR 和界面语言偏好”。
- **下游现状**：Design 中对海外华人的应对仅做了“App内直接语言直选（中/英）”的设计决策，而在最关键的核心技术差异“双语 OCR”上，仅声明了“印刷体中英文 OCR 识别”，完全忽略了海外华人最常见的“繁体中文”教材和“中英文混排”场景的专门技术或交互支持决策。

#### 🔍 F-D1-004 [LOW] — 愿景级可度量成功信号的设计校准机制在 Design 中未闭环
- **上游主张**：Vision 设定了 8 项可度量的成功信号（如冷启动首次录入时间中位数、持续录入行为 D7 比例、Multi-Profile 可用性等），作为衡量产品“是否做对了”的设计校准器。
- **下游现状**：Design 完全没有对如何通过交互设计或底层统计埋点框架去无感采集、测量这些成功信号（特别是非事件源的“系统分享”和“系统打印”等路径）做出任何设计决策。设计与度量指标之间存在脱节。

### L2 Design → L3 Requirements (D → R)

#### 🔍 F-D1-005 [HIGH] — 来源/年级字段在题库列表管理链条中被“废线化”的规格缺失
- **上游主张**：Design 一方面声称“不做来源/年级过滤——使用频率低，加入过滤会增加 UI 复杂度”；但另一方面在字段可配置系统中，又将“难度、来源、年级、答案”列为可由用户按需开启的“系统字段”。
- **下游现状**：Requirements 承接了该过滤限制，且在题库排序规格中同样**未**包含“来源”和“年级”（仅支持时间/学科/难度/复习状态）。这导致了致命的功能残缺：用户即使在设置中开启并高成本录入了“来源”或“年级”字段，它们在整个题库管理页面中将**既无法过滤，也无法排序**。这两个字段沦为了只能在单题详情里看一眼的“死元数据”，毫无聚类和宏观筛选价值，导致开启此字段的用户场景彻底失效。

#### 🔍 F-D1-006 [HIGH] — Requirements 凭空引入“CSV 数据导入”，但 Design 零设计决策
- **上游主张**：Design 的数据核心基线是“图片是真相（Image is Truth）”，所有的导入/备份/安全恢复决策均围绕包含图片资产与数据库的 `.zip` 完整压缩包进行。
- **下游现状**：Requirements 在 v2.0 全景功能“导出与备份”中明确承诺了“CSV 数据导入（RFC 4180 合规）”这一 Must/Should 级功能。但在上游的 Design 文档中，**完全缺失**此功能的任何设计决策。特别是在“CSV 仅有文本字段，导入后没有图片”的情况下，如何处理与“Image is Truth”核心原则的冲突？CSV 导入导致数据冲突、覆盖或是追加的边界是什么？全部缺失上游设计指引。

#### 🔍 F-D1-007 [MEDIUM] — 多 Profile 关键生命周期（创建/删除/保护）的需求规格遗漏
- **上游主张**：Design 详细定义了多 Profile 的生命周期控制设计，包括“切换保护机制（进行中操作如备份/导出时拒绝切换）”、“最后一个 Profile 阻止删除”的保护逻辑。
- **下游现状**：Requirements 仅在 Must 中提到了“多 Profile”，在全景里一笔带过了“多 Profile 本地切换（参考 Obsidian）”。而对于 Profile 究竟如何“创建”、如何“删除”，以及最重要的“最后一个 Profile 禁止删除”的系统边界保护逻辑，在 Requirements 规格中**完全漏损**，缺乏需求闭环。

#### 🔍 F-D1-008 [LOW] — 软删除 Undo 窗口的强制退后台/强退一致性收敛规格缺失
- **上游主张**：Design 明确要求“后台/被杀收敛：App 在 undo window 内进入后台或被杀死时，下次启动必须收敛到确定状态，不出现幽灵记录”。
- **下游现状**：Requirements 对 Deletion Scheduler 撤销机制的定义仅限于“5 秒 Toast 撤销”，缺乏在突然强退、电话打断、切后台等操作系统干涉场景下数据状态如何进行“强制收敛”的功能规格说明，属于规格漏损。

#### 🔍 F-D1-009 [LOW] — 恢复前“安全网自动备份”的触发与交互设计缺失
- **上游主张**：Design 在备份与恢复设计中，仅规划了用户主动执行的“手动备份” `.zip` 压缩和恢复前的文件兼容校验。
- **下游现状**：Requirements 的非功能需求可靠性指标明确规定了“恢复前自动备份当前数据（安全网）”的安全规格。但 Design 中未对此“安全网自动备份”的自动生成时机、存储管理、静默/显式交互做任何设计支撑，属于设计缺失。

---

### L3 Requirements → L4 Tech (R → T)

#### 🔍 F-D1-010 [HIGH] — 独立正反面卡片自定义字号与 Dynamic Type 无障碍标准的技术概念混淆
- **上游主张**：Requirements 明确定义规格：“复习卡片外观字号：正面和背面独立设置，范围相同，提供实时预览”。
- **下游现状**：L4 Tech 在 `non-functional-requirements.md` 中，却将该字号可调规格描述为 `无障碍 - Dynamic Type | 复习卡片字号 12-24pt 可调`。这存在严重的技术概念混淆与实现漂移：Dynamic Type 是 iOS 系统的全局无障碍文本缩放机制，是由系统级设置驱动的。在技术上，在同一个页面内部，**绝无可能**实现“正面文本和背面文本独立套用不同的 Dynamic Type 缩放比例”。技术文档将“App 自定义滑杆调节字号”混淆为“Dynamic Type”，会直接导致开发架构设计出错，严重时甚至可能损害真正的原生无障碍缩放功能。

#### 🔍 F-D1-011 [HIGH] — CSV 数据导入的底层技术组件、协议及 NFR 验证完全空白
- **上游主张**：Requirements 将“CSV 数据导入（RFC 4180 合规）”列为 Core/Data 层的 Must/Should 级别功能。
- **下游现状**：L4 Tech `architecture.md` 中对 `SnapDrillData` 和 `SnapDrillCore` 模块职责描述中，**完全没有**定义任何关于 CSV 解析、导入事务、CSV 格式映射的技术模块。同时，外部依赖仅列了 `ZIPFoundation`，完全没有 CSV 解析库或手写解析的框架。而在 `non-functional-requirements.md` 的性能指标、内存场景上限、存储和可靠性表中，对“CSV 导入吞吐量、内存缓冲区上限、恶意 CSV 注入攻击防护”等完全是**零规划、零防范**。这属于明显的技术架构缺陷。

#### 🔍 F-D1-012 [LOW] — 1/2/4 题快速打印的 PrintService 独立架构模块缺失
- **上游主张**：Requirements 提出“单题快速打印：详情页固定 1 题/页；批量导出打印支持每页题数可选（1/2/4 题）”。
- **下游现状**：L4 Tech 架构图和模块职责仅在 Core 中声明了 `PDFExportService`，缺少对 iOS 原生 AirPrint 系统交互控制器（UIPrintInteractionController）以及在打印场景中做“1/2/4 题网格布局排版”的 `PrintService` / `PrintPageRenderer` 的技术组件划定。

## 语义审计结论（维度 1）

通过本轮对 **L1 愿景 → L2 设计 → L3 需求 → L4 技术** 的跨文档语义链条审计，Antigravity 发现 SnapDrill 文档体系在机械结构上虽已达成 Phase 9 收官的全绿状态，但在**深层语义对齐**上仍存在显著断档。

最为严重的漂移集中在：
1. **“来源/年级”字段的设计与需求脱节 (F-D1-005)**：导致高交互成本录入的字段在列表管理端毫无用武之地。
2. **CSV 导入的设计真空与技术缺位 (F-D1-006 & F-D1-011)**：需求层凭空塞入的 CSV 导入破坏了 Image is Truth 核心原则，且技术架构层零实现支撑。
3. **卡片独立字号与 Dynamic Type 混淆 (F-D1-010)**：混淆了无障碍标准与 App 级自定义功能，会引发重大的技术架构实现偏误。
