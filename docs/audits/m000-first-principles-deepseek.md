# M-000 第一性原理审计 — 独立扫 (家名: 异源独立扫)

## 总评 (≤ 200 字)
审计 14 项，PRIMARY 2 项、INHERITED 5 项、ANALOGY 4 项、UNDETERMINED 3 项。核心结论：**多数派生约束并非从底层事实推导，而是基于对传统软件工程流程（如加权评审、分层架构）的类比或对“LLM多模型可信度”的惯性假设；真正第一性的只有“议题清单驱动”和“用户-decision-log作为最终裁决”两条。** 最大风险：4 家异源选型缺乏非对称性论证，Overrule 机制过早复杂化，worktree 隔离是物理故障而非逻辑必需。

## 待审项明细

### [I001] 协作宪法定位 (M-000 第一章)
- **范围**: Layer 1
- **路径/出处**: M-000 v1.2, 第一章标题「协作宪法」
- **目的**: 给团队提供最高层级的决策原则，防止日常操作覆盖核心约束
- **机制**: 通过“宪法”隐喻，声明本文件不可轻易修改（需 Overrule 机制），其他规则都派生自它
- **替代**: 直接命名为“核心规则集”或“元规则文档”，不需要“宪法”这个类比也能达到目的
- **来源**: ANALOGY — 明显模仿国家宪法作为最高法的概念。在法律/政治领域，宪法有主权、立宪程序、司法解释等复杂机制；在此仅需要“高优先级规则”一意，却带来了修订门槛、解释权归属等未定义的类比负担
- **破坏测试**: 改名为“M-000 核心规则”后，系统运行不会退化：规则内容不变，删除“宪法”一词不影响任何推导或审计
- **Verdict**: ANALOGY
- **改造建议**: 重写为“M-000 核心规则集”，删除“宪法”隐喻。理由：避免引入不必要的立法/司法类比，降低新手理解成本。

### [I002] 默认多方异源 (M-000 v1.2 第三章)
- **范围**: Layer 1
- **路径/出处**: M-000 3.1 「默认多方异源」
- **目的**: 解决单一信息源（一个人或一个模型）产生有偏/不完整见解的问题
- **机制**: 要求每个议题至少由两个“不同源”的视角独立处理，源包括不同模型、不同人、不同 prompt 配方
- **替代**: 更朴素的方式：直接要求“任何决策必须附带至少一个对立观点记录”，无需预设“源”的物理异质性。本质只需观点多样性，而非源多样性
- **来源**: ANALOGY — 借用了流行病学/实验科学中“独立复现”的概念，但在此场景下“同源”的两人可能观点冲突，“异源”的 GPT 和 Claude 可能结论一致。源不能 guarantee 多样性，真正第一性的是“逻辑独立性”
- **破坏测试**: 如果将“异源”改为“异逻辑”（即要求论证路径不同而非模型不同），系统不会退化，反而更精确。现有规则会误过滤掉同模型但 prompt 不同的有效对比
- **Verdict**: ANALOGY (但可改造)
- **改造建议**: 重写为“默认异见化”：要求每个议题至少提供两个在论证前提或推理链条上不同的分析，而非要求物理源不同。理由：更接近第一性（确保逻辑独立性），避免工具绑定。

### [I003] 字数 B+ 方案 (2500 nwc + 400 代码块 + 4000 英译)
- **范围**: Layer 1
- **路径/出处**: M-000 第四章 / 字数约束
- **目的**: 控制输出长度，避免 token 浪费，保证可读性
- **机制**: 硬性数字上限（2500 自然字 + 400 代码块等效 + 4000 英译）
- **替代**: 更直接的方式：根据上下文窗口比例动态截断（如总 token 80%），或使用描述性约束（如“每条分析不超过半屏”）。硬性数字是来自人类写作习惯的惯性
- **来源**: INHERITED — 显然继承自人类文档规范和早期 LLM 调优经验。没有论证为什么 2500 不是 3000，为什么 400 不是 500。这些数字没有底层分解（如“经过 GPT-4o 32k 上下文最优性价比公式推导”）
- **破坏测试**: 将 2500 改为 3000 或删除数字，用户不会立即感受到退化；但若完全放开，可能产生过长的浪费。所以该规则有实用价值，但数字精确度是惯性
- **Verdict**: INHERITED
- **改造建议**: 保留但参数化：“字数上限设置为最大上下文窗口的 45% (当前约 2500 字)”，并附上推导公式。理由：让数字变得可计算、可调整，不再凭经验猜测。

### [I004] Overrule 机制 (M-000 第六章)
- **范围**: Layer 1
- **路径/出处**: M-000 6. Overrule 机制
- **目的**: 当元规则与现实决策冲突时，提供推翻规则的途径
- **机制**: 定义 Overrule 申请格式、生效条件（需要 user-decision-log 记录、同源警告等）
- **替代**: 更朴素的方式：直接在任何规则后注明“此规则可由项目 PO 在记录理由后临时覆盖”，无需多级审批流程
- **来源**: ANALOGY — 模仿 RFC 的“更新/废除”机制或法律中的“特别法优于一般法”。但项目场景中只有一个权力主体（PO），不需要复杂的多数投票、撤销原判等概念
- **破坏测试**: 简化 Overrule 为“PO 单方面声明”，系统不会退化，反而更快。现有过程文档：user-decision-log #007 记录了 Overrule 的结构化分解，但实际执行就是 PO 说了算
- **Verdict**: ANALOGY
- **改造建议**: 重写为“规则覆盖条款”：PO 可随时以 recording 形式覆盖任何规则，覆盖后原规则标记为 superseded。取消审核流程和同源警告要求。理由：去中心化控制不适用于单决策者。

### [I005] 风险接受 + 同源警告 (M-000 第七章)
- **范围**: Layer 1
- **路径/出处**: M-000 7. 风险接受与同源警告
- **目的**: 提示使用异源时可能忽视的内部一致性风险
- **机制**: 每次使用同源（如同一模型多次调用）时，自动输出警告，要求接受风险
- **替代**: 将“同源”定义为“生成时没有新的独立输入”，而不是模型开关。例如同一模型但用不同的随机种子或不同 prompt 不应警告
- **来源**: INHERITED — 继承了早期“异源=不同模型”的惯性，未区分“真正的同源”是信息重用而非模型重用
- **破坏测试**: 删除同源警告，系统不会退化，因为异源机制已经保证了多样性（或失败）。该警告增加了噪音
- **Verdict**: INHERITED
- **改造建议**: 废除同源警告，改为“信息同源检测器”（检测是否基于同一份前置输出来改写），若发现则自动提示，而非基于模型。理由：减少误报，聚焦真正风险。

### [I006] 4 家选型 (Claude/Codex/DeepSeek/Gemini)
- **范围**: Layer 2
- **路径/出处**: 派生约束 – 4 家参与
- **目的**: 确保审计有足够观点多样性
- **机制**: 固定使用四个特定模型作为异源源
- **替代**: 动态选择任意不同类模型（如 GPT-4o + Gemini + 本地开源），或只要求不少于3个不同推理引擎，不固定品牌
- **来源**: INHERITED — 明显继承自最初项目架构时的“四家人选”决策，没有论证为什么是这四个、为什么不能是其他。可能存在成本/隐私偏好，但未嵌入规则
- **破坏测试**: 移除一个（如 DeepSeek），换成 Qwen，系统功能不变；固定选型反而限制了未来新模型的加入
- **Verdict**: INHERITED
- **改造建议**: 改为“基于推理架构异质性的最少3家”，并列出当前推荐（但可替换）。理由：保留目的（多样性）但移除品牌锁定。

### [I007] worktree 物理隔离工作流
- **范围**: Layer 2
- **路径/出处**: 派生约束 – worktree 隔离
- **目的**: 防止多个 agent 同时写入造成冲突
- **机制**: 每个审计家使用独立的 git worktree 目录
- **替代**: 使用命名空间文件或分支锁定机制，不必创建整个目录副本
- **来源**: INHERITED — 来自传统 git 工作流（多人协作需要独立分支），但这里每个家是独立完成的，无需并发写同一仓库。实际上一次审计周期内4家各自输出，然后折叠，不存在冲突。worktree 增加了设置成本
- **破坏测试**: 删除 worktree 隔离，改用同一仓库下的不同子目录或命名文件，系统无退化，反而简化
- **Verdict**: INHERITED
- **改造建议**: 废除物理隔离，改用“输出目录分离”约定（如 /round-N/家名/）。理由：消除不必要的 git 复杂性。

### [I008] 5 Phases 起草流程 (sketch / independent / folding / sign-off)
- **范围**: Layer 2–3 (ADR-004)
- **路径/出处**: ADR-004 结构清洁方法论
- **目的**: 保证每一轮审计从草稿到签署的过程有序，避免混乱
- **机制**: 四阶段：sketch（框架）-> independent（各自输出）-> folding（合并）-> sign-off（PO 确认）
- **替代**: 简化为两阶段：独立输出 -> 合并+确认。sketch 和 sign-off 可以合并到一次检查中
- **来源**: INHERITED — 模仿敏捷开发中的 sprint 周期和评审节奏。项目 PO 一人决策，不需要集体 sign-off，sign-off 只是记录 PO 认可
- **破坏测试**: 删除 sketch 阶段（直接进入独立），输出质量不会退化（因为每个家已经知道议题）；删除 sign-off 阶段只保留 PO 确认（如 decision-log），系统无退化
- **Verdict**: INHERITED
- **改造建议**: 缩减为3阶段：准备（议题清单）-> 独立产出 -> 合并与裁决。将 sign-off 融入合并步骤中的 PO 最终审查。理由：减少仪式性步骤。

### [I009] 净化提示词 (prompt cleansing)
- **范围**: Layer 2
- **路径/出处**: 派生约束 – 净化提示词
- **目的**: 消除提示中隐含的偏见，确保各家收到相同的输入表述
- **机制**: 对原始提示进行格式化、去除额外上下文、标准化术语
- **替代**: 直接使用原始提示，各家自主忽略多余部分；或仅提供关键事项列表
- **来源**: UNDETERMINED — 未看到具体内容，不知道净化规则是否基于第一性分析（如“避免词序影响”等），但很可能是从“减少 LLM 偏见”的常见实践模仿而来，但没有论证为什么是净化而不是随机化
- **破坏测试**: 如果净化规则过于复杂（如重写所有同义词），删除后各家可能因 prompt 不同而产生差异，但差异本身正是异源想要的效果？需更多数据
- **Verdict**: UNDETERMINED (需检查具体净化算法)
- **改造建议**: 暂不修改。但要求写出净化原则的底层推导（如“删除所有评价性形容词，保留事实数据”），否则视为惯性。

### [I010] Sanity check 自反性 (跨 Round 复盘)
- **范围**: Layer 2–5 (#008)
- **路径/出处**: #008 中首次撤回
- **目的**: 确保元规则体系本身不被盲目执行，允许通过反思发现自身缺陷
- **机制**: 每一轮审计结束后，强制进行自反性检查（如“本轮的规则是否适用？是否有惯性？”）
- **替代**: 更直接：每次决策前自动检查该决策是否与已记录的矛盾点冲突（类似自动一致性检查）。当前是事后复盘，效率低
- **来源**: PRIMARY? 不，是ANALOGY — 模仿哲学中的“自反性”概念。但在此处，它只是“检查规则是否仍然合理”，可以命名为“规则健康检查”。不过目的和机制是合理的，且从底层事实“规则可能出错”推导出来。但命名有类比
- **破坏测试**: 删除后，系统会失去对规则演化错误的检测，退化明显（如 #008 中的 Overrule 异常可能发现不了）
- **Verdict**: ANALOGY (仅为命名类比，本质可接受)
- **改造建议**: 保留机制，改名为“规则有效性检查”，移除哲学术语。理由：减少理解成本。

### [I011] docaudit 11 check (含 verdict-sync / external-gap-expiry 等)
- **范围**: Layer 3
- **路径/出处**: docaudit 规范
- **目的**: 自动化检查文档一致性，避免过期或矛盾
- **机制**: 11 条检查项，如检测 verdict 是否与文档状态同步、外部引用是否超期、superseded-by 反向链接是否存在等
- **替代**: 简化为5-6个核心检查：状态一致性、链接有效性、日期过期。其他如“backlog-item-staleness”可能更适用于项目管理而非文档体系
- **来源**: INHERITED — 继承了传统文档治理中的“清单法”，从多篇参考中拼凑了11项，没有论证为什么是11不是7
- **破坏测试**: 移除其中3项（如 external-gap-expiry 在非外部文档中很少有用），未发现退化
- **Verdict**: INHERITED
- **改造建议**: 针对实际文档缺陷数据，重新裁剪 check 项，保留最常触发问题的3-5项，其余移到“可选检查”。理由：减少维护负担。

### [I012] frontmatter schema: layer 枚举 (principle/pattern/snapshot/archive/decision/contract)
- **范围**: Layer 3
- **路径/出处**: 文档 frontmatter 规范
- **目的**: 文档分类，方便导航和搜索
- **机制**: 枚举6种类型，每个文档都必须标注
- **替代**: 只用三种核心类型：原则（principle）、记录（record）、废弃（archive）。contract、snapshot 等边界模糊
- **来源**: ANALOGY — 明显模仿 ADR 分类和领域驱动设计中的“架构模式”，但 snapshots 和 archives 几乎没有区别，decisions 就是 record
- **破坏测试**: 合并“snapshot”和“archive”为“archive”，减少分类时，系统不会损失信息。删除整个 schema 改用搜索标签，系统可能退化（失去结构化），但当前分类太细反而增加认知负荷
- **Verdict**: ANALOGY
- **改造建议**: 压缩为3类：原则（principle）、决策记录（decision）、存档（archive）。去除非必要的枚举。理由：简化分类，减少歧义。

### [I013] 古德哈特防御 (Form over Substance)
- **范围**: Layer 4
- **路径/出处**: 核心概念
- **目的**: 防止规则被字面执行而忽视意图
- **机制**: 当检测到规则被“形式遵守但实质破坏”时，引入警告或降级
- **替代**: 更第一性的做法：在每条规则中内置“目的说明”，并允许违反规则只要达成目的（即目的优先）。而不是单独设立防御机制
- **来源**: PRIMARY — 古德哈特定律是观察到的现象，但这里的防御机制是从“人类会钻规则空子”这一底层事实推导出来的：要防止恶意合规，必须让规则意图显式化。不过命名借用经济学定律是类比，但机制本身是第一性的
- **破坏测试**: 删除该防御，系统会逐渐僵化（如 #007 中可能发生形式合规而实质偏差）。有实质退化风险
- **Verdict**: PRIMARY (机制)，但命名 ANALOGY
- **改造建议**: 保留机制，将防御内化到每条规则的目的字段中，同时保留一个全局“目的优先”原则。命名可改为“目的优先原则”。理由：去除非必要的经济学类比。

### [I014] F-008 「相同完整任务、不分工」
- **范围**: Layer 4
- **路径/出处**: F 规则索引 F-008
- **目的**: 保证每个 agent 独立应对整个任务，避免信息损失
- **机制**: 每个家必须处理整个议题，不能拆分成子任务给不同 agent
- **替代**: 如果任务过长，可分段处理但需保证完整信息传递（如先输出摘要再深度剖析）。当前规则完全禁止分工，可能浪费 token
- **来源**: PRIMARY — 从“异源需要独立见解”这一底层事实推导：分工会导致观点耦合，失去独立性。但未考虑分段可能（分段但保持上下文独立）。不过核心思想是合理的
- **破坏测试**: 去掉该规则，允许分工，则可能产生某人只做前半段，异质观点被稀释。退化明显
- **Verdict**: PRIMARY (但可优化)
- **改造建议**: 保留但允许“分段独立”模式：每一段由同一家独立完成全部上下文，但多个段可并行。规则改写为“禁止任务切分导致观点合作”。理由：提高效率，保持核心。
