# 设计原则与全局规范

> 本文档承载**跨功能**的总览与方法论：不属于任何单个 feature 的全局设计规则、信息架构、空状态与错误处理基线，以及缺陷严重度框架（S0-S3）。各功能专属的设计细节见对应 feature spec（`../features/active/` 与 `../features/backlog/`）。
>
> **上游依赖**：`vision.md`（使命、定位、用户、6 条原则、冲突裁决规则）。
> 本文件定义「为什么这样设计」——设计决策、交互铁律、策略理由。
> 具体功能行为见各 feature spec；发布范围与结果级验收见当前 Release PRD，`../reference/scope-and-roadmap.md` 只维护候选与重入边界。
>
> **设计决策变更需产品负责人批准**；编辑性修正由开发者维护。

## 全局设计规则

### 价值链与优先级（Kano 模型对标）

```
┌─────────────────────────────┐
│   回顾 / SmartPaper（可选复用） │  ← Kano: Excitement / Optional
├─────────────────────────────┤
│   导出 / 打印（核心终点）        │  ← Kano: Performance / Must outcome
├─────────────────────────────┤
│   整理 / 找回（核心体验）        │  ← Kano: Performance / Must outcome
├─────────────────────────────┤
│   忠实采集（生命线）             │  ← Kano: Basic / Must outcome
└─────────────────────────────┘
```

**输出边界**：导出 / 打印是核心价值链终点，手动可携带备份是 P4 的耐久承诺。具体格式和增强项由 Release PRD 决定，不能从当前实现反推永久 Must。

**设计铁律**：任何功能如果损害了采集、整理 / 找回、导出 / 打印的简洁性，就不该做。回顾与 SmartPaper 可以提供附加复用价值，但不得占据或复杂化主路径；当前不存在有效 Pro 分层。

### 情绪基调

SnapDrill 是纯粹的效率工具。全局文案、Onboarding、成功反馈与空状态均遵循以下规则。B6-A 下当前不应出现付费 / Pro 提示；未来若有新的 effective 商业 contract，相关文案仍受同一基调约束：
- **客观冷静**：不向用户贩卖焦虑（不做"今日仅剩 X 题额度"、不做连续天数打卡、不弹成就渲染）
- **成熟语气**：界面面向成年用户，中性、不幼稚、不卡通、无低龄化信号
- **尊重节奏**：把选择权交给用户，不主动推送、不施加压力

### 原则冲突裁决

冲突裁决规则见 `vision.md`§产品原则、§耐久取舍与§三层 SSOT 与变更生命周期；本文档不重复列出，只在具体设计场景中引用。

### 原则追溯标注

本文档每个设计章节标题后标注 `[PX]`，表示该设计服务于哪条 Vision 原则。下游文档引用时使用章节标题（含 `[PX]` 标注）。

### 学习与成功信号

Product Vision & Principles 不定义虚构 KPI。当前产品假设及推翻信号由 `assumptions.md` 管理；[Release 1 PRD](../product/release-1-prd.md) C4-D / C5-E 只允许预登记形成性 cohort 触发重新裁决，不能按人数门槛自动公开。C6-A 定义 PO 可裁决的风险政策，具体命令、设备和 test ID 属 QA / Release evidence plan。当前生产不做后端行为采集；不得为了补指标恢复 Firebase 或逐事件用户追踪。

## 信息架构 [P1 录入体验, P2 简洁]

### 导航结构

当前五个同级 Tab（首页 / 资料库 / 采集 / 回顾 / 设置）是实现事实，不是 Product Vision & Principles 或 Release 1 承诺。[Release 1 PRD](../product/release-1-prd.md) C3 规定普通启动默认进入 Dashboard，但不批准五 Tab 结构或 Review 的导航等级，也不单独授权实现。最终导航必须让采集、资料库和输出路径容易到达，且不得让附加能力主导首屏。

### Dashboard 设计角色

Release 1 Dashboard 是单一资料库的**任务入口和可执行状态概览**，不是学习 / analytics 门户：
- Capture 与 Library 一次操作可达；空资料库一次操作开始 Capture
- 可以显示未完成草稿、最近资料和能直接进入对应内容的本地事实
- Capture / Library 在视觉和 accessibility 顺序中先于任何 Review 入口
- 不展示 Profile / Workspace、昵称 / 头像身份入口、Pro / IAP / locked / coming-soon 或 analytics 模块
- Review 不使用 hero、进度环、连续记录或完成庆祝主导首屏

现有 Review hero、问候 / 头像、四项统计和高级统计锁态是相对 Release 1 PRD 的已知偏差。C2-Personalization 隐藏身份装饰；C4-D / C5-E 只允许 Review / SmartPaper 在非公开实验 build 从 Library 的单一静态次级入口出现。上述目标不单独授权实现，必须进入有界 implementation bet。

**Dashboard 文案防焦虑约束**（承接 vision §不贩卖焦虑）：
- 若保留数字，只显示能直接进入对应内容的**中性本地事实**
- **不**附带「比昨天少了 / 完成度 X% / 距目标还差 N 题」类比较或进度推送
- **不**用红色 / 警告色 / 感叹号渲染数字
- 「今日新增」语义仅是事实计数，不是「打卡」「冲量」隐喻

### 资料库信息架构 [P1 录入体验, P2 简洁]

**为什么默认按录入时间倒序**：最新录入的题目最可能需要编辑补充（加答案、补字段），倒序让它们最先出现。

**为什么当前实现的过滤维度走统一字段系统**：
- 分类与标签：Release 1 Must 的基础整理能力
- 来源 / 级别 / 自定义字段：Candidate optional，只有冻结 manifest 纳入时才允许用户启用；不预设为教育专用维度
- 不做独立难度星级；若未来纳入动态字段，难度 / 级别语义仍应由字段或标签表达，避免固定教育结构污染通用存档工具定位

**搜索基于 OCR 文本**：用户记得题目中的关键词，搜索匹配 OCR 识别出的文字内容。

Release 1 为 iPhone-only。iPad 与 Apple Pencil 不属于当前产品或设计承诺；现有自适应代码只算实现事实。未来重入必须先有外部价值证据和新的平台裁决，再补齐大屏工作流、布局、输入、无障碍、截图与发布验收，不能仅因代码可以运行就宣布支持。

## 空状态与错误处理设计 [P2 简洁, P4 数据安全, P5 成人生产力工具]

### 空状态原则

- 空状态先解释"这里为什么是空的"，再给一个最近动作入口，不做教育式说教
- 空资料库、无搜索结果、无待回顾资料属于三类不同空状态：首次未开始、过滤后为空、当前阶段已完成，文案必须区分
- 空状态 CTA 只给一个主动作，避免把用户带回复杂选择题
- 空状态不得借机强推订阅；Release 1 空状态优先指向采集、恢复或帮助，不出现付费墙

### 错误分级

| 级别 | 场景 | 处理原则 |
|---|---|---|
| **L1 可忽略提示** | OCR 识别不准、搜索无结果、无到期复习题 | 内联说明 + 可继续当前流程，不打断任务 |
| **L2 可恢复错误** | 权限缺失、导出失败、恢复校验失败、未来同步暂时异常 | 明确原因 + 给重试或替代路径，不静默吞错 |
| **L3 数据风险错误** | 保存失败、恢复半成功、资料库不可用、图片文件缺失 | 必须醒目提示结果摘要和后果，优先保护现有数据 |

### 可访问性基线

- 所有空状态图示和错误图标都必须有可读文本，不依赖颜色单独传递信息
- 错误反馈既要有视觉呈现，也要有 VoiceOver 可读文案和必要的 announcement
- 错误文案优先说人话，先描述结果和下一步，再补技术原因
- 可点击修复动作的命名必须直接对应用户意图，如"重试""去设置""恢复备份"，避免抽象按钮文案

## 缺陷严重度框架（S0-S3）

设计与验收共用一套缺陷严重度分级，用于排定测试优先级、收录边界用例、裁决"先修哪个 bug"：

| 严重度 | 含义 |
|---|---|
| **S0** | 数据不可逆丢失 |
| **S1** | 流程阻断 |
| **S2** | 有摩擦 |
| **S3** | 不紧急 |

优先级排序：**S0 > S1 > S2 > S3**。术语定义同 `../reference/glossary.md`§术语表。

**边界用例收录约定**：边界用例（Boundary Cases）仅收录 S0/S1 全部 + 高频 S2。具体边界用例按功能归入各 feature spec 的 Verify 节，例如采集相关见 `../features/active/feat-capture.md`、备份恢复相关见 `../features/active/feat-backup.md`。`../features/active/feat-profile.md` 已重基线为单一本地资料库规则；其中标注的 `develop` Multi-Profile 只属实现实证。

> 双框架分工：本严重度框架（S0-S3）与§价值链与优先级中的用户价值金字塔（Kano 对标）并用——价值金字塔回答"做什么 / 优先做什么"，严重度框架回答"哪个缺陷先修 / 哪个边界必测"。
