# M-004 降级操作手册

> M-004 定义「服务受限、用户长期不可达、工具失败、静默退化时的降级路径与停止等待判据」的可操作流程。承接 M-000 §10（风险、降级与复审）+ M-000 §11.1 派生职能 + MC-7（自动触发实为手动）+ MC-9（iOS 工程特有不可逆灰色地带）+ #025/#026 DeepSeek 通道故障实证。
> **前置依赖**：M-000 v2.0（§10）、M-001（§4.3 vendor 不可用降级 / §11.4 hook 失败兜底）、M-002（§4.1 不可逆事项 / §5.6 裁决方不可用）、M-005（§C 静默退化信号）、M-006（§5.6 共享失败降级 / §8.4 等待判据接口）。

## §1 定位

M-004 是「降级与停止等待」层的元规则。M-000 §10 给出原则（用户长期不可达 → 仅可逆动作；服务变化 → 自动触发复审），M-002 §5.6 给出原则级处置（物理 / 逻辑不可用 → 回退用户），M-001 §4.3 / §11.4 给出特定场景降级，M-005 §C 给出退化信号，M-006 §5.6 / §8.4 给出数据流转层降级。M-004 给出**完整的降级决策树 + 等待判据 + 不可逆动作清单**：

1. 触发降级的感知方与判据（§4）
2. 5 类服务受限的具体降级路径（§5）
3. 用户长期不可达时的等待判据（§6）
4. 工具失败的降级（§7）
5. iOS 工程特有不可逆动作清单（§8）
6. 静默退化触发的回退用户路径（§9）
7. 降级日志与复审节奏（§10）

M-004 不取代任何下游的具体重试逻辑、监控告警、CI 失败处理——M-004 定义这些工具应在什么条件下降级、降级到什么程度、何时停止等待、何时回退用户。

适用范围：所有受 M-000 §10 + §3 异源约束的协作 / 工具 / 数据场景（多方 sign-off、subagent 调度、CLI 调用、iOS 构建 / 发布、git 操作、API 请求、用户裁决等待）。

## §4 触发条件与感知方（承接 MC-7）

### §4.1 「触发由感知方发起，不依赖自动监控」原则

承接 MC-7（M-000 §7.3 「自动触发」实际为手动）：

- **当前项目无自动监控基础设施**（无 Prometheus / Datadog / 告警邮件链）
- 触发降级 / 复审 / 回退用户的责任**由感知方主动发起**：任一智能体（Claude / Codex / AGY / DeepSeek）或用户
- 感知方触发后**必须**按 §10 写入 user-decision-log（缺口记录或 M-002 §10.1 八字段条目）

**违反信号**：感知方意识到「该降级了」但未发起 → 按 M-005 §I「真违纪」处理（M-001 §9.4 私下授权检测扩展）。

### §4.2 感知方的判据

智能体感知到以下信号 → 必须触发降级流程：

1. **API / CLI 返回错误**（HTTP 4xx/5xx / CLI exit code != 0 / 超时 > §6.2 阈值）
2. **静默退化硬信号**（M-005 §C.1-§C.5 任一）
3. **隔离失效信号**（M-005 §B.2 5 条任一）
4. **配额 / 频率限制告警**（vendor 显式告警 / 响应延迟显著变化）
5. **凭据失效**（401 / 403 / token expired）
6. **模型 / 工具 sunset 公告**（vendor 官方声明，需 WebSearch 验证）

### §4.3 用户作为感知方

用户也可主动触发降级（如「先停下来，我看不到 Gemini 的响应了」）→ 智能体必须立即停止当前任务 + 按 §10 留痕，**不需要等待技术信号确认**。

### §4.4 感知方触发的最小留痕格式

```yaml
触发时间: YYYY-MM-DD HH:MM
感知方: <智能体名 / "user">
信号类型: <API / 退化 / 隔离 / 配额 / 凭据 / sunset / 用户直觉>
具体证据: <错误码 / 信号描述 / 用户原话>
触发降级动作: <按 §5-§9 哪一条处置>
```

留痕位置：本会话上下文 + user-decision-log（若触发不可逆 / 长期等待）+ commit message（若需 commit 中间状态）。

## §5 服务受限的降级路径（5 类）

### §5.1 API 限流（HTTP 429 / vendor rate-limit 告警）

1. **立即停止**当前 vendor 的并发调用
2. **退避策略**：指数退避（1s / 2s / 4s / 8s ... ≤ 64s 上限）；超过 64s 仍 429 → 标记 vendor「短期不可用」
3. **短期不可用**：在异源矩阵（M-001 §4.3）标 vendor 状态「⛔ 限流中（直到 HH:MM）」；其他 vendor 可正常用
4. **触发降级**：若该 vendor 是关键异源方 → 等待 + 通知用户；若是冗余 → 单家降级（≥2 家共识仍成立）
5. **复审**：vendor 限流恢复后留痕，60 天内同 vendor 限流 ≥3 次 → 触发 user-decision-log 缺口（评估是否减少调用频率或换 vendor）

### §5.2 网络中断（DNS / TCP / TLS / SSE 断流）

1. **重试上限**：3 次（每次间隔 5s / 10s / 30s）
2. 仍失败 → 检查本机网络（`ping 8.8.8.8` / `curl ifconfig.me`）
3. 本机网络正常 + vendor 端点不可达 → 标 vendor 「⛔ 网络不可达」
4. 本机网络异常 → 通知用户 + 阻塞所有外部 CLI / API 调用
5. **历史实证**：#024 DeepSeek wrapper 死锁 55 分钟 SSE 断流 → 教训：长连接（SSE / WebSocket）必须有 timeout（如 `agy --print-timeout 30m`）

### §5.3 凭据失效（401 / 403 / token expired）

1. **立即停止**所有使用该凭据的调用（避免反复消费失败配额）
2. **检查凭据是否泄露**（grep 最近 git history / paste 服务日志）→ 若有泄露嫌疑立即轮换
3. **轮换路径**（按 vendor）：
   - Anthropic / OpenAI / Google / DeepSeek：登录控制台 revoke + 重新生成 + 更新 `~/.zshrc` / 项目 `.env`（确保 `.env` 在 .gitignore）
   - Apple ID / fastlane match：按 §8 不可逆动作上交用户
4. **通知用户**：凭据失效是 P2 守护事项（涉及账号资产），必须用户裁决
5. **不允许智能体单方轮换凭据**（即使可逆）—— 凭据轮换属 M-005 §I.1 结构性决定

### §5.4 模型 / 工具 sunset（vendor 官方停服公告）

1. **WebSearch 验证**：先用 WebSearch 确认 sunset 是真实公告（防训练记忆误判 / 钓鱼信息）
2. **影响评估**：grep `docs/tech/reference/agent-cli-models.md` + 项目代码确认所有消费点
3. **过渡期**：vendor 通常给 30-90 天 sunset 缓冲，期间：
   - 继续可用但标 `agent-cli-models.md` `freshness: expired`
   - 加快寻找替代品（如 Gemini CLI sunset → AGY CLI 替代实证：sunset 主锚 [#015](user-decision-log.md#015) + `agent-cli-models.md`「2026-06-18 重大变更」段；AGY CLI 通道实证 [#025](user-decision-log.md#025)）
4. **过渡期结束**：按 M-002 §9 「跨 vendor 替换」流程走完整裁决，update agent-cli-models.md SSOT + 同 PR 改 `Scripts/gemini_utils.py` 等代码消费点
5. **实证锚定**：[#013](user-decision-log.md#013) Gemini model ID 误用是 sunset 处理失败的反面教材（model ID 与 wrapper 不匹配）；[#025](user-decision-log.md#025) AGY CLI 替代 Gemini CLI 是正面案例（vendor 同源 + 端点变化的平滑过渡）

### §5.5 配额耗尽（月度 / 周度 token 用尽）

1. **检测**：vendor 响应中含 `quota_exceeded` 或 HTTP 402
2. **本批暂停**：当前 vendor 暂停到下个计费周期
3. **替代方案**：
   - 该 vendor 是冗余 → 单家降级（≥2 家共识仍成立）
   - 该 vendor 是关键 → 等待 + 通知用户「该 vendor 配额耗尽，X 天后重置」
4. **配额耗尽的预警**（防被动）：高频用 vendor 应在 80% / 90% / 100% 三阈值告警（具体由 M-001 hook 实现）
5. **不通过升配额「自动续费」绕过**：升配额是用户裁决事项（涉及付费）→ 上交

## §6 用户长期不可达的等待判据

### §6.1 阈值定义

承接 M-000 §10「用户长期不可达时，智能体只可执行可逆、局部、低外部副作用动作」：

- **短期不可达**（< 4 小时）：等待，不主动降级；继续推进单方执行窗口（M-001 §8）内的任务
- **中期不可达**（4-24 小时）：暂停所有需要用户裁决的事项；本批已开始的可逆任务可继续完成；不启动新的多方异源任务
- **长期不可达**（> 24 小时）：**仅执行可逆、局部、低外部副作用动作**；不可逆事项**阻塞等待**（不允许智能体替代用户做裁决）
- **超长不可达**（> 7 天）：进入「session 冻结」状态，新会话开始时先 sync-status（M-001 §10）查看未完成事项

### §6.2 「可逆动作」的本节定义（M-001 §8 接口）

直接引用 M-001 §8 单方执行窗口清单，不重复定义。本节强调长期不可达时的**特别约束**：

- 即使在 M-001 §8 单方窗口内，也不允许批量动作（如批量改 frontmatter 50 个文件）
- 不允许跨厂商共享（M-006 §5.3 显式授权依赖用户）
- 不允许任何 hook 配置变更（hook 是治理基础设施）

### §6.3 等待时长的 grace period

- **用户裁决等待时长 grace period**：用户裁决标记后 24 小时内不允许智能体替代裁决（即使技术上可行）
- **不可逆事项 grace period**：24 小时阻塞等待；72 小时仍无响应 → 升级（创建提醒文件 `docs/audits/pending-user-decision-<日期>.md` + 在 STATUS.md 注记）

### §6.4 用户回归后的同步

用户回归后，智能体必须执行：

1. **sync-status** 拉取 user-decision-log + git log + STATUS.md 差异
2. **列出阻塞事项**（按 §6.3 grace period 标记）
3. **不主动恢复任务**：等待用户确认「从哪里继续」

## §7 工具失败降级路径

### §7.1 单 vendor CLI 失败（如 DeepSeek wrapper 死锁）

实证锚：#024 DeepSeek wrapper SSE 断流 55 分钟 / #025/#026 DeepSeek wrapper 调 `claude -p` 参数传递失败。

降级路径：

1. **首次失败**：记录失败模式（exit code / stderr / 超时）+ 标 vendor「⛔ 通道故障」
2. **替代方案**：
   - 该 vendor 是冗余 → 跳过，使用其他异源（按 #017/#021/#025/#026 实证 2 家 + 用户裁决有效）
   - 该 vendor 是关键 → 触发 §7.3 通道修复尝试
3. **修复尝试**：
   - 看 vendor CLI 升级日志（如 `~/.local/share/claude/versions/<v>` 变更日志）
   - 直接 API 调用绕过 wrapper（如 DeepSeek 直接 curl `api.deepseek.com/v1/chat/completions`）
   - 提交 wrapper bug 修复 PR
4. **持续故障**：同 vendor 通道在 30 天内 ≥3 次完全失败 → 触发 user-decision-log 评估是否从异源矩阵移除

### §7.2 L0/L1 跨厂商共享失败的降级（M-006 §5.6 接口）

直接引用 M-006 §5.6：

1. 不重试直到失败原因确认
2. 触发本节 §5（API / 网络 / 凭据 / sunset / 配额）相应降级
3. 失败记 §10 缺口（用户裁决该任务是否等待修复 vs 单方降级）

### §7.3 物理隔离失效的降级（M-005 §B.2 + M-001 §5.5 接口）

隔离失效信号触发：
1. **标记该方产出为「辅助视角」**（M-005 §B 处理）
2. 若该方是关键异源反对方 → 自动升级用户裁决（M-002 §4.2）
3. 若隔离失效是反复发生（同一 worktree / 同一 .claude.md 配置 ≥3 次）→ 重写 worktree 隔离脚本 + 触发 M-001 §5 复审

### §7.4 hook 失败的兜底（M-001 §11.4 + 本节扩展）

承接 M-001 §11.4 hook 脚本本身报错时的处置：

- **hook 报错**（exit 非 0/2 + stderr 非空）：不阻塞主命令（exit 0），记录到 `.claude/hooks/desensitize-errors.log`
- **hook 错误日志累积**：30 天内同 hook 错误 ≥10 次 → 触发 hook 维护 (debug + 修复)
- **hook 错误率 > 20%**：临时禁用该 hook（重命名为 `.disabled`）+ 通知用户 + 修复优先级最高
- **本节扩展（M-001 §11.4 仅 1 行）**：hook 失败时不阻塞主命令的策略本身需 30 天 / 90 天复审，确认未导致实际泄露（grep history + 复审 desensitize-errors.log）

### §7.5 skill 触发链失败的降级（M-003 §4 接口）

- skill 加载失败（frontmatter 解析错 / 路径不存在）→ 跳过该 skill + 通知用户
- skill 触发但执行报错 → 按 skill 自身定义的 fallback（若有）/ 否则降级为「不触发该 skill」
- 同 skill 连续 ≥3 次失败 → 自动标 `skill_audit_verdict: degraded` + 触发 M-003 §5 升降级评估

### §7.6 跨厂商数据共享授权撤回（M-006 §5.3 接口）

跨厂商共享授权应支持「主动撤回」（不只是被动失败）：

- 用户可在 user-decision-log 追加 `revocation: #NNN` 条目撤回 #NNN 的授权
- 撤回生效时刻：追加条目的时间戳
- 撤回后已经共享的数据无法收回（这是 P5 物理隔离失效后果），但后续不再共享 + 删除本机相关数据（按用户决定）

## §8 iOS 工程特有不可逆动作清单（承接 MC-9）

### §8.1 硬清单（必须用户显式授权，不允许智能体单方执行）

| 动作 | 不可逆原因 | 处置 |
|---|---|---|
| `git push` | 跨越本地工作区边界，对外承诺历史 | M-002 §4.1 + MC-9 第 1 项：push 必须显式用户授权（按 [#018](user-decision-log.md#018) 主笔不下场原则的延伸 + M-006 §10 私有 memory 治理：不引用未注册的私有 memory 作为权威源）|
| `fastlane match` 证书同步 | 跨设备同步 + 涉及 Apple Developer Portal | 用户裁决 + match 操作前确认 git remote 正确 |
| TestFlight 发布 | 对外用户可见 + 涉及版本号永久占用 | 用户裁决 + 发布前 DoD 校验完整 |
| Apple ID 改动（签名 / 团队 / 角色） | 涉及账号资产，可能影响所有 app | 用户裁决 + 改动前备份当前 provisioning profiles |
| 数据库迁移（destructive migration） | 数据可能丢失（即使有备份也涉及恢复操作） | 用户裁决 + 迁移前必须有备份 + dry-run 验证 schema |
| 证书 / private key 操作 | 涉及加密资产 + 可能影响所有签名 | 用户裁决 + 备份 + 撤销操作不可逆 |

### §8.2 灰色区动作（按双核同意处理，承接 MC-9）

| 动作 | 灰色原因 | 处置 |
|---|---|---|
| 修改 `*.pbxproj` | 本地可逆但影响构建 + git 历史污染易 | 按 M-002 §6.1 双核同意（小修可单方，大改双核）|
| 修改 `Package.swift` 依赖版本 | 本地可逆但依赖图可能影响多 target | 双核同意 + 同 PR 跑 build-for-testing 验证 |
| 修改 SwiftLint / 测试 plan 配置 | 本地可逆但影响 CI gate | 双核同意 + 同 PR 跑完整 lint + test |

### §8.3 软清单（M-001 §8 单方窗口可执行）

不在 §8.1 / §8.2 的 iOS 工程动作（如 swiftlint --fix / typo 修复 / import 排序）按 M-001 §8 单方窗口执行。

### §8.4 等待判据（M-006 §8.4 接口）

承接 M-006 §8.4 数据档位 × 用户不可达时长矩阵：

- L0/L1 操作：用户不可达 > 24h → 阻塞等待
- L2/L3 操作：用户不可达 > 24h → 仅可逆动作
- L4 操作：可正常执行
- iOS §8.1 硬清单：所有时长都阻塞等待（不仅 > 24h）
- iOS §8.2 灰色区：用户不可达 > 24h → 阻塞等待

## §9 静默退化触发的回退用户路径（M-005 §C 接口）

### §9.1 硬信号回退路径

承接 M-005 §C.6「硬信号 → 立即标为「逻辑不可用」等同物理不可用回退用户（按 M-004 降级流程）」。具体路径：

1. **该方产出标 `degraded: true`** + 归档到 `docs/archive/audits/m005-static-degradation-evidence/<vendor>-<日期>.md`
2. **该方本轮裁决不采纳**（按 M-005 §C 静默退化逻辑）
3. **触发 §4.2 感知方留痕** + 写入 user-decision-log（如有跨 session 影响）
4. **替代方案**：
   - 该方是冗余 → 跳过，使用其他异源
   - 该方是关键 → 触发 §6 等待用户裁决（不允许智能体替代）
5. **修复尝试**：
   - 切换 vendor 通道（如 CLI → 直接 API）
   - 重新生成任务定义书（确认无 prompt injection）
   - 物理隔离重置（新 worktree / 新 conversation）

### §9.2 局部段落退化处置

承接 M-005 §C.6「局部段落退化 → 要求该方重做并保留退化证据」：

1. **该方产出标 `degraded_partial: true`** + 退化段落引用 + 归档证据
2. **要求该方重做**（同 vendor 同任务，新 conversation）
3. **重做仍退化** → 升级为硬信号处置（§9.1）
4. **重做通过** → 该方产出可继续作为辅助视角（不计强证据）

### §9.3 sign-off 阶段的退化触发

承接 M-005 §C.6「sign-off 阶段：任一退化信号出现，立即暂停 sign-off 并通知用户」：

1. **立即暂停**当前 sign-off 流程
2. **通知用户**：哪个 vendor + 哪个退化信号 + 当前 sign-off 进度
3. **用户裁决**：等待修复 vs 跳过该 vendor（按 #017/#021 实证 2 家 + 用户裁决有效）

## §10 降级日志与复审

### §10.1 降级触发的留痕原则

任何降级触发（§4-§9）都应留痕，留痕粒度按影响范围：

- **本会话内可逆降级**（如单次 API 重试）：记录到本会话上下文 / commit message，不入 user-decision-log
- **跨会话或影响后续工作的降级**（如 vendor 通道故障 / 配额耗尽 / sunset）：必须入 user-decision-log
- **结构性决定**（如 vendor 从异源矩阵移除 / 凭据轮换 / 不可逆动作执行）：必须按 M-002 §10.1 八字段写 user-decision-log + 用户显式裁决
- **静默退化**（§9）：归档到 `docs/archive/audits/m005-static-degradation-evidence/`

### §10.2 复审节奏

| 复审类型 | 节奏 | 触发条件 |
|---|---|---|
| 单 vendor 状态复审 | 30 天 | 通道故障 / 限流 / 配额事件 |
| 异源矩阵整体复审 | 90 天 | M-001 §4.3 异源矩阵 + agent-cli-models.md freshness |
| iOS 不可逆清单复审 | 180 天 | iOS / Xcode / fastlane 版本升级 |
| hook 错误率复审 | 30 天 | hook desensitize-errors.log 累积 |
| user-decision-log 缺口聚合复审 | 90 天 | M-006 §9.3 缺口聚合 |

### §10.3 复审失败的升级

复审发现以下情况 → 升级用户裁决：

- 同 vendor 故障率 > 30% / 季度
- iOS 不可逆动作执行后发现 §8 清单遗漏新增动作（如新 fastlane 命令）
- hook 错误率 > 20% 持续 ≥30 天
- 缺口聚合 ≥5 类同类型未响应
