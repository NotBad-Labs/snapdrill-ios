## 我口述的八点核心命题（原话）

### 1. 为什么单智能体不够

单智能体不够，是因为各家厂商的模型能力不一样，而且随着产品线更新，不同厂商的模型在实际测试或生产环境下的表现也不一样——Opus、GPT、Gemini 都有可能因为模型更新、版本升级，甚至服务中断，导致不能完全依赖单个智能体。

冗余的本质是**能够复现**——布置相同的任务能得到一样的结果，但在呈现结果时能比较出算法、加载策略等其他方面的优劣。冗余是为了选择更优雅、更高效的方式，本质上是**择优录取、择优采纳**。相同的功能，谁的代码最少、谁的响应最快、谁的内存占用低、谁的耦合性最低等等，都是更好的方向。

### 2. 适用边界

适用边界在于服务是否可用。我是 Claude MAX 订阅，但 Codex 和 Gemini 都是 20 美金订阅，因此可能 Claude 还有大量额度时，Codex 和 Gemini 已经达到 5 小时的额度限制。

**服务可用时，都应该坚持多方冗余**。除非某个服务暂时受限，可以两方协同，或者干脆停止等待额度重置，再进行三方协同。

我希望尽可能不降级。不同的交互方式效果可能也不一样——桌面端 chat / cowork / code 三种入口、命令行版本，行为可能有差异。

### 3. 降级条件

我不希望降级。如果 Codex 和 Gemini 额度都用完了，那就采用 Claude 命令行 + DeepSeek API，保持至少两方。

从额度感觉上，Claude 最多（订阅费最高），Gemini 其次，Codex 最少，但这只是感觉。事实上三家都常常重置额度，所以几乎很少碰到额度没有的情况。

### 4. 失败定义

我没有仔细考虑过。我能想到的是**无法达成共识**——就像科学理论或科学实验一样，一般情况是能达成共识的。

至于污染、退化、共谋这类问题，我考虑可以采取「独立工作环境」或不同分支来缓解。具体机制希望参与起草的智能体给出自己的看法。

### 5. 裁决机制

- 用户（我）拥有**最高裁决权**
- Claude 和 Codex 拥有裁决权
- 其他智能体暂时不允许有裁决权
- 如果 Claude 和 Codex 同时支持，可以不询问用户
- 如果 Claude 和 Codex 意见不一致，应让用户裁决

### 6. 元规则的元规则

**实事求是**——无论智能体还是用户，都不能凭空捏造，应该用事实和数据说话，而不是无凭无据谈论。

修改权限：智能体和用户都有权修改，但**更改不是随意的**。管理学有奥卡姆剃刀原理——如无必要，勿增实体。否则规则会越来越膨胀。虽然现代智能体有按需加载技能的机制，但毕竟还是占用上下文 token。

修改元规则及元规则的元规则时，**必须做好记录，必须能溯源**。版本控制系统本身有追踪能力，需要充分利用。

### 7. 与产品 vision 的关系

智能体协作元规则**和产品 vision 一样**，是最基础也是最高的指导思想。

如果两者冲突，必须交给用户本人裁决。

### 8. 期望与最怕

**希望**：
- 元规则每次都能加载
- 智能体在工作时能对元规则及相关体系产生正面的升级或进化（比如把经验及时沉淀为可加载技能等）
- 类似产品文档体系——**层层递进，依赖关系清晰，上位规则管控下位规则**
- 坚守单一权威源（每个概念只有一处定义），不产生语义或其他漂移

**最怕**：变成一堆大杂烩。

## 议题（请独立回答）

1. **核心命题**：用一两句话凝练你理解的「为什么需要多智能体协作」
2. **认识论根基**：冗余的科学/哲学依据，与单智能体的本质差异
3. **适用范围**：哪些工作场景必须多方？哪些可以单方？
4. **降级策略**：服务限额时的降级路径，以及「何时停止等待而非降级」的判据
5. **失败定义与缓解**：什么算协作失败？污染、退化、共谋如何识破？除独立工作环境外还有什么机制？

10. **下游派生**：这份元规则会派生哪些下游元规则？依赖关系建议？
