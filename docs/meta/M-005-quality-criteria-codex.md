# M-005 质量判据与退化检测（Codex 草案）

> M-005 定义“什么样的元规则产出值得被信任”，以及“什么时候一个看似可用的协作过程已经退化”。它服务 M-000 PRIMARY 内核，不替代 M-001 的工作流、M-002 的裁决流程、M-004 的降级操作或 M-006 的数据治理。

## §1 定位与适用范围

M-005 是质量判据层，不是流程手册。它给出判断接口：产出是否可追溯、可验伪、不可下沉、目的相关；多方一致是否构成独立证据；智能体是否物理可用但逻辑不可用；工具 check 何时有资格进入阻塞门。

M-005 适用于元规则起草、审计、sign-off、docaudit 设计、模型/工具事实核验、主笔轮换和高风险多方协作。普通代码实现、UI 文案、测试补充可以引用本文件的判据，但不因此自动进入多方元规则流程。

## §2 与 M-000 PRIMARY 的接口

M-005 对 M-000 P1 的接口：每个独立方必须处理同一完整任务；质量判据不能奖励“分工覆盖”冒充“独立趋同”。

M-005 对 P2 的接口：任何结构性质量判断最终可上交用户，且必须能写入 append-only `user-decision-log`。

M-005 对 P3/P4/P5 的接口：默认多方异源、同源警告和 worktree 物理隔离只产生独立性前提；M-005 负责识别前提是否失效。

M-005 对 P6 的接口：sanity check 不是终审，它也必须能复盘上一轮判断并撤回自己。

M-005 对 P7 的接口：净化提示词必须不泄露其他方结论；M-005 负责检测输入污染造成的伪共识。

M-005 对 P8 的接口：质量规则升级、撤回或覆盖旧裁决时必须显式写出 Overrule 对象、边界和理由。

## §3 与 M-001/M-002/M-004/M-006 的分工边界

M-001 规定多方任务如何启动、隔离、轮换和执行；M-005 只规定这些机制何时构成可信质量信号。

M-002 规定裁决流程、双核适用域、Overrule 写法和撤回复审；M-005 只规定裁决材料应满足的可追溯、可验伪和反伪共识判据。

M-004 规定工具失败、用户不可达、服务受限时怎么降级；M-005 只规定“逻辑不可用”的识别信号，使静默退化能进入 M-004/M-002 的处理路径。

M-006 规定数据共享、脱敏、prompt injection 技术防御和敏感信息边界；M-005 只规定污染、泄露和身份误识别的质量信号，不给具体防御实现。

## §A 产出度量

合格元规则产出必须同时满足四项判据。

1. 可追溯性：每条规则能回到具体证据、案例、用户裁决编号或第一性原理论证。引用历史裁决时必须写明 #001~#012 的具体编号；不能用“历史经验”“之前裁决”替代。若规则没有可追溯来源，只能作为问题假设或开放议题，不能作为稳定元规则。

2. 可验伪性：每条规则必须列出违反信号。不能说“保持高质量”而不说明什么产出构成低质量；不能说“避免污染”而不说明哪些输入、路径、上下文或产物泄露构成污染。

3. 下沉证明：每条规则必须说明为什么不能下沉到 standards、skills、ADR、STATUS stub、docaudit 实现或 M-001/M-002/M-004/M-006。若规则只是命令、模板、字段格式、脚本细节或当前状态，应下沉。

4. 目的关联：每条规则必须显式关联 M-000 P1~P8 之一，或直接服务产品愿景中的可靠协作。若一个条款只让文档显得完整，却不提升可靠性、可追溯性、独立性或用户裁决权，应删除或下沉。

最低输出结构：规则文本、证据或原理论证、违反信号、不可下沉理由、PRIMARY 接口。缺任一项时，sign-off 应标为 CONDITIONAL；缺两项以上或关键条款不可验伪时，标为 BLOCK。

## §B 伪共识识别

多方一致只有在独立性成立时才有证据价值。以下信号出现时，同向结论不得直接当作强共识。

触发信号清单：

- 同一主笔系列连续产出同向结论，尤其是同一 vendor 长期承担草案、折叠、final 中多个角色。
- 同 vendor 多实例、同一模型家族或近似训练 cutoff 的多方同向，而异源方提出具体反例。
- 任务定义书、AGENTS/CLAUDE 路由、git 历史、Issue comment、私下 Overrule 或已有草案泄露了预期立场。
- 多方使用同一中间摘要、同一 review chain、同一未净化 prompt，或共享同一 worktree/分支/IDE 缓存。
- 辅助方沉默被主笔写成“默认同意”。

物理隔离失效检测：

1. 检查输入同一性：各方是否收到同一净化任务定义，而不是带有不同暗示的版本。
2. 检查禁止材料：是否读取了其他方草案、折叠报告、主笔候选或含结论的 git diff。
3. 检查上下文污染：项目入口、memory、私有 plan、历史会话是否提前暴露用户偏好或其他方判断。
4. 检查路径污染：worktree 不同但远端分支、stash、IDE 搜索、shell glob 或 docaudit 输出是否把禁止文件名和内容带入当前方。
5. 检查产物相似性：高度相似的章节、例子、错误、编号和比喻，若无法由任务定义书解释，应标为伪共识风险。

异源否决权阈值承接 MC-10。只有“强烈、具体、可证伪反对”才触发用户裁决或主笔回炉。有效反对至少满足三项中的两项：引用具体事实错误；提出可验证的反假设或替代解释；指出明确风险路径和受影响对象。只有语气强烈、偏好不同、抽象担忧或“我感觉不对”，不构成有效否决。若同一辅助方在短时间内频繁触发升级且多数不满足上述标准，应反向检查该方是否退化或滥用否决权，避免注意力通胀。

## §C 静默退化识别

静默退化是“物理可用但逻辑不可用”：API 正常、命令返回、文本生成完整，但产出已经不能承担裁决或质量证据。MC-1 中的双核不可用定义必须包含此类逻辑不可用。

退化信号：

- 格式崩溃：frontmatter 残缺、YAML 不可解析、必填章节缺失、标题层级断裂、输出格式与任务契约明显不符。
- 自相矛盾：同一产出内既批准又否决同一事项，或同一规则前后给出相反边界。
- 偏离任务：把元规则起草写成代码实现、把质量判据写成 M-002 裁决流程、把 M-006 prompt injection 技术防御提前落地。
- 身份误识别：自称其他 vendor、其他模型、其他工作目录或其他职责。#004 中 DeepSeek/Gemini 互换身份是实证，不能依赖智能体自我宣称判断异源。
- 引用幻觉：引用不存在的裁决编号、路径、章节、用户原话或外部事实。
- 约束遗忘：读取禁止材料、跨 worktree 操作、修改 No-Touch 文件，却在输出中声称完全遵守。

触发动作：识别到任一硬信号时，将该方标为逻辑不可用，等同物理不可用处理；不得把其结论纳入多数或双核同意。若信号影响结构性决定，应回退用户裁决；若只是局部段落退化，可要求该方重做并保留退化证据。

## §D 外部事实验证纪律

AI 模型、工具版本、API endpoint、model ID、CLI 可用性、价格、能力边界、发布状态和训练 cutoff 均属易变事实。依据 #002，相关判断默认不信训练记忆，必须 WebSearch 或官方来源验证；无法联网时只能标注“未验证”，不得写成当前事实。

异源训练谱系判断必须基于厂商公开声明、官方文档、可复核发布说明或用户提供的已验证快照，不依赖智能体自我宣称。#004 已证明 reasoning/thinking 模式下身份误识别会发生；因此“我是谁”不是证据。

`docs/tech/reference/agent-cli-models.md` 是当前工具/模型快照，`freshness.max_age_days: 30`。以下任一条件触发刷新或失效标记：

- 距 `last_verified` 超过 30 天。
- 用户提到新模型、模型退役、CLI 升级、endpoint 变化或厂商公告。
- CLI 探针结果与官方文档、用户实测或其他工具结果冲突。
- 多方任务依赖“当前 SOTA”“当前可用模型”“异源训练谱系”判断。

失效处理路径：先标记该事实为 stale 或 unverified；再用官方来源刷新；若无法刷新，任务定义书必须把该事实降级为假设，并说明对结论的影响。CLI ping 失败只能证明该 CLI 路径失败，不能证伪模型或 API 本身存在。

## §E 目的优先原则的古德哈特防御

目的优先的含义是：规则、字数、阶段、枚举、门禁和 check 都是诊断工具；当形式削弱可靠性、可追溯性、独立性或用户裁决权时，应保护目的并记录偏离理由。

形式削弱目的的判据：

- 产出为了满足字数、表格、章节或字段而删除必要证据、分歧、风险或 Overrule 边界。
- check 通过后被写成“事实正确”或“独立性成立”，超出工具能力边界。
- 多方流程被执行成角色分工，形式上人多，实质上没有独立完整判断。
- 为了 schema 语义纯粹破坏下游消费端兼容性。#008 中拒绝把 `status` 改成 `partially_superseded` 是实证。
- 为了避免触发用户裁决，把强反对降格为 minor concern，或把沉默写成同意。

指标反向塑形检测：

1. 观察作者是否围绕指标造句，而不是围绕问题表达。
2. 检查是否出现“为了过 docaudit/字数/表格”而牺牲证据链。
3. 检查指标是否被当成成功本身，而非发现风险的信号。
4. 检查绕过行为是否增加：压缩为难读短句、搬运到脚注、把规则藏进 frontmatter、把硬问题改写成不可验伪抽象话。

历史实证索引：

- #006：Round 1 Boot 重构中，同源激进方案被异源 sanity check 纠偏，说明“流程更轻”不能压过可见性和状态保存目的。
- #007：ADR-004/005 拆分接受异源激进版，说明保守维护形式会掩盖方法论 SSOT 过期问题。
- #008：Round 2 sanity check 撤回 R1 `STATUS_ENUM` 修改，说明 reviewer 共识也可被工程兼容性目的反向校正。
- #009：M-000 第一性原理审计识别大量非 PRIMARY 外壳，说明规则体系自身也可能被形式塑形。
- #010/#012：字数原则从硬上限、软上限进一步升级为无预设上限，说明“默认预算”本身也可能成为优化对象。

## §F 自反性 sanity check 原则

sanity check 的任务不是给主笔结论盖章，而是让系统有机会反查自己的上一轮判断。有效 prompt 应要求 reviewer 明确回答：

1. 你在 Round N-1 的判断中，哪一条可能错了？
2. 当时你依赖了哪些未验证事实、形式偏好或同源假设？
3. 现在是否有新证据、新约束或下游消费端兼容性问题足以撤回原判断？
4. 若撤回，会保留原判断中的哪部分理由，Overrule 哪部分结论？

Round N -> Round N-1 复盘必须允许三种结果：维持、精化、撤回。撤回不是失败，而是质量机制生效。#008 是标准实证：Gemini 在 Round 2 复盘并撤回 Round 1 对 `STATUS_ENUM` 的建议，用户接受撤回。

sanity check 不是终审。即使异源 sanity check 形成共识，后续 sanity check、用户裁决或工程实测仍可推翻它。任何把“sanity check 已过”写成“不可再质疑”的产出，违反 P6。

工程兼容性优先于元数据美学。当字段语义、schema 纯粹性和下游脚本消费冲突时，必须先识别真实消费端。若工具已经消费某字段，修改前必须给兼容方案；若只是人类解释性字段，不得伪装成强 schema。

## §G docaudit check 设计原则

M-005 不重复 M-000 §8 的 core check 清单，只规定 check 进入、停留、升级和退役的原则。

每个 check 必须有真实事故来源或清晰风险模型。真实事故可以来自 #002 的模型事实过期、#005 的归档路径越权、#006 的悬挂引用和 Overrule 漏写、#008 的字段消费兼容风险、#011 的级联引用延后。风险模型必须说明：若不检查，会产生什么错误；错误如何被发现；阻断是否值得。

核心 check 进入阻塞门须同时满足：

- 失败高频或高代价，且历史上已经发生或有明确风险路径。
- 可机械判定，误报可控。
- 不能被作者用简单形式绕过而保留实质风险。
- 失败语义明确：阻断什么、允许什么、如何修复。
- 有上游元规则或 standards 说明其存在理由。

可选 check 的价值不低于核心 check，只是阻塞资格尚未成立。可选 check 可用于实验、低频但高代价风险、需人工裁决的风险、或数据不足的新信号。可选 check 应输出 warning/info，不应默认阻断所有任务。

新增 check 提案流程：

1. 写明事故来源或风险模型。
2. 给出机械判定边界、误报样例和豁免路径。
3. 先以可选 check 运行，收集触发率、误报率、修复成本和漏检后果。
4. 当证据显示其高频、高代价、可机械判定且不可被形式绕过时，提案升级为 core。
5. 升级 core 必须同步 `docs/standards/execution-gates.md`、相关脚本 README、docaudit policy 和消费端文档。

退役原则：若 check 连续长期零有效命中、误报成本高于发现价值、或风险已被上游设计消除，应降级为可选或退役；不得因为“已有实现”而永久保留。

## §H 主笔轮换机制

主笔轮换是降低同源长期偏向的质量原则，不是荣誉分配。M-000 v1.0~v2.0 final 连续 4 版 Codex 主笔构成风险累积；#012 裁决 M-005 主笔转 DeepSeek reasoner，即是对 P3 默认异源和 P4 同源警告的二阶应用。

轮换原则：

- 同一 vendor 或同一模型家族连续承担多个元规则 final 主笔时，下一轮应优先换源，除非用户明确豁免。
- 主笔不能同时垄断任务定义、独立草案、折叠、final 和 sign-off。若因实际资源必须重叠，必须在任务定义书里写明风险。
- 主笔候选裁决必须保持物理隔离可见性。#010 中 Codex 收到用户私下 Overrule、主分支不知情，虽经用户确认属合规授权，但证明私下授权必须同步落档，否则其他参与方无法 sanity check。
- 主笔不是独享特权。3 家 sign-off 中任一家给出满足 §B 阈值的 BLOCK，主笔产出必须回炉或上交用户裁决；不能用“主笔已定”压过异源强反对。

M-005 不规定主笔轮换的具体流程、周期、候选评分或执行命令；这些属于 M-001。M-005 只规定何时“连续主笔”成为质量风险信号。

## §I 自作主张越权防线

结构性决定必须显式批准。以下事项默认属于结构性决定：归档路径选择、目录重命名、跨目录文件移动、批量 frontmatter 修改、schema 扩展、状态枚举变化、M-000/M-00x 元规则正文修订、对外发布、合并、push、删除历史材料、修改 No-Touch 范围。

#005 是反例实证：归档路径未经用户显式批准即由智能体选择，违反“智能体有提案权，用户有批准权”。#010 是边界实证：主笔收到用户私下授权，不必被定性为违纪，但若主分支不可见，会触发合理 sanity check。

私下授权 vs 主分支可见性：

- 私下 Overrule 可以成立，但必须尽快同步到 `user-decision-log` 或任务定义书。
- 同步前，其他参与方看到不一致时应标为“可疑但未定性”，不得直接把主笔判为违纪，也不得无视不一致。
- 主笔引用私下授权时必须写清授权对象、授权边界、是否覆盖旧裁决、何时落档。

误触发与真违纪的辨别：

- 误触发：用户已明确授权，但授权尚未在主分支可见；或工具自动生成结构变化但未被提交。
- 真违纪：无授权即做结构性决定；把提案写成已批准；跨 worktree 操作；读取禁止材料；用 commit/push 事实倒逼用户接受。
- 争议状态：证据不足时上交用户，保留日志，不私下补叙为合规。

## §J 正向质量判据与字数原则升级

核心原则：信息密度决定字数，不预设上限。字数不是质量目标，也不是合规目标；它只是可读性、冷启动成本和维护成本的诊断信号。

`override_rationale` 的正向作用不是“破例申请”，而是“密度证明”。作者必须证明当前长度中的每一段为什么不能下沉、不能压缩、不能省略。合格的密度证明应覆盖：本文服务哪些 PRIMARY；哪些内容是下游接口而非下游流程；哪些历史裁决必须保留编号；哪些段落若删除会破坏可追溯、可验伪或 Overrule 边界。

冗余检测信号：

- 重复定义同一概念而没有新增边界。
- 把可执行步骤、命令、模板、字段格式写进元规则正文。
- 用装饰性论证、类比、口号或姿态词替代违反信号。
- 为形式完整补章节，但章节没有独立质量接口。
- 长段落不能指出其服务的 PRIMARY、裁决编号或下游消费者。
- 用“为了完整”解释长度，而不是说明不可下沉和不可压缩。

正向质量判据：

1. 长度增加后，可追溯性、可验伪性、边界清晰度或下游接口更强。
2. 删除任一段会造成具体信息缺口，而不只是文字风格变化。
3. 每个例证来自已发生裁决或明确原理论证，不引用未发生的假设场景冒充实证。
4. 对读者的冷启动负担有收益解释：读得更多是为了少犯哪类错。

同 PR 落地路径承接 #010/#012。M-005 ratify 的同一 PR 应修订 M-000 v2.0 §6 与 frontmatter：

- 删除 M-000 frontmatter 中 `default_word_budget: 2500`。
- 保留并重写 `override_rationale`，使其不再解释“超过默认预算”，而解释“当前长度的密度证明”。
- 将 M-000 §6 标题建议改为“预算、下沉与密度证明”或“下沉与密度证明”。
- 将 §6 第一段从“默认正文预算为 2500 non-whitespace chars；这是可读性和冷启动成本的设计目标，不是自动否决线”改为：“M-000 不预设字数上限；正文长度由信息密度、冷启动成本和不可下沉证明共同决定。frontmatter `override_rationale` 必须说明当前长度为什么必要、哪些内容不能下沉、何时复审。”
- 删除代码块独立预算和英文译本固定乘数作为默认规则；若未来代码块或译本过长，应由该文档自己的 `override_rationale` 或译本说明处理。
- 在 `user-decision-log` 预 #013 或实际 ratify 条目中显式 Overrule #009 R2 中“default_word_budget 字段保留”的处理方式，并说明 #001/#003 的硬数值治理已被更高阶的密度证明原则吸收；#001 的“实事求是”精神、#003 的反古德哈特洞见保留。

此升级不得被理解为“无限写”。无上限意味着不以预设数字裁决质量；冗余、下沉失败和目的漂移仍然构成不合格。
