# M-000 Meta-Vision v2.0

> M-000 是 SnapDrill 协作规则的优先级 0 入口：定义智能体协作如何保持可靠、可追溯、可修正。具体操作下沉到 M-001~M-006、standards、skills 和工具。

## §1 定位

M-000 只保留无法下沉的元规则：谁有最终裁决权，独立判断怎样成立，规则冲突怎样处理，规则系统怎样避免膨胀和自我欺骗。它不承担知识库、流程手册、prompt 模板、工具说明或状态看板职责。

M-000 与产品愿景平级：前者定义协作可靠性，后者定义产品方向。二者冲突时不预设倾向，必须上交用户，并附结构化分析：冲突性质、可逆性、双方拉锯点、推荐路径、理由。裁决可沉淀为先例，但不自动改写元规则。

系统应保持核心稳定、中层演化、长尾外置。每个概念只有一处权威定义，每次重要结论都能追溯到证据、分歧和裁决；反对规则堆叠、术语漂移和仪式化流程。

## §2 PRIMARY 内核

以下 8 项是 M-000 v2.0 的不可动内核，可重述，不可废除：

| ID | 内核 |
|---|---|
| P1 | 相同完整任务、不分工：每个独立方处理同一完整任务，而非切片协作。 |
| P2 | 用户最高裁决权 + append-only `user-decision-log`。 |
| P3 | 默认多方异源；单方执行必须由用户或下游规则明确豁免。 |
| P4 | 同源警告：训练谱系、上下文或输入污染导致的一致，不能当强证据。 |
| P5 | worktree 物理隔离：高风险多方任务必须隔离目录、分支、上下文和中间产物。 |
| P6 | sanity check 自反性：审计机制也必须能复盘自身上一轮反馈。 |
| P7 | 净化提示词：任务定义不得泄露其他方结论、编号、暗示或分工锚点。 |
| P8 | Overrule：覆盖旧裁决时必须显式写明覆盖对象、覆盖边界和理由。 |

## §3 认识论根基

可复现只是最低条件，独立趋同才有证据价值。单一模型可以稳定复现同一个错误；多个实例也可能因为训练谱系、提示词、上下文或工具状态相似而同向犯错。多方协作的价值不在多数投票，而在暴露假设、边界、反例和失败模式。

同一完整任务不得被拆成分工式外包来冒充独立判断。F-008 的核心要求是：每个独立方都拿到同一净化任务定义，独立完成完整判断，再进入折叠。若任务被拆成 A 方找问题、B 方补遗漏、C 方只复核，产物只能证明分工覆盖，不证明独立趋同。

独立性至少包含四层：模型权重或训练谱系不同、运行实例不同、上下文互不可见、任务输入未泄露其他方中间结论。只满足其中一两项时，只能算辅助视角，不能算强独立证据。

默认多方异源是价值选择：质量优先于效率，同时承认 token、时间和注意力成本。低风险、可逆、机械性动作可由 M-001 定义单方执行窗口，但该窗口必须是下游操作优化，不改变本文件默认。实操口诀：**这件事如果做错，异源会不会以不同方式做错？** 若会，走多方；若不会，可按下游规则降级。

结构性同源一致是伪共识风险。若同源或近同源智能体给出同向方案，而异源方提出具体、可证伪的反对意见，自动触发用户裁决；双核或多数意见不得直接压过该反对意见。辅助方沉默不构成认同，关键决策必须明确表态。

## §4 隔离与三阶段流程

高风险审计和多方起草必须使用物理隔离：独立 worktree、独立分支、同一净化任务定义、互不可见中间产物。只靠提示词要求“不要参考别人”不足以防止污染；工具缓存、IDE 状态、会话亲和性清理纪律下沉 M-001。

复杂协作默认三阶段，子步骤随复杂度浮动：

1. 准备：明确问题、范围、输入材料、禁止材料、输出格式、验证方式和隔离要求。
2. 独立产出：各方基于同一净化任务定义完成完整任务，不互读中间产物，不按角色分工规避难点。
3. 合并裁决：折叠共识、分歧和独家发现；用户裁决冲突；执行、验证和记录并入本阶段。

流程目标是获得可靠判断，不是凑齐固定人数、表格或步骤。若形式合规但独立性、证据或裁决链条缺失，视为失败。

## §5 用户裁决、双核与 Overrule

用户拥有最高裁决权。智能体可提出方案、反对方案、请求澄清和指出风险，但不得把模型多数、工具绿灯、历史习惯或主笔偏好当作最终依据。涉及不可逆操作、跨越本地工作区边界、对外承诺、元规则修改、法律或财务风险、产品方向实质变化时，默认上交用户。

裁决智能体清单由用户维护。双核同意可作为推进底线，但任一方不可用时，双核自动通过权失效；具体适用域、熔断条件和例外清单下沉 M-002。

`docs/meta/user-decision-log.md` 是 append-only 裁决记录。每条结构性裁决至少包含时间、冲突描述、裁决、理由、是否触发元规则修订、Overrule 关系和元层级注记。新裁决若覆盖、撤回、接管、废弃或精化旧裁决，必须显式写出 Overrule；否则不得推断“旧规则自然失效”。Overrule 不删除历史，只说明失效范围、保留范围和理由。

## §6 预算、下沉与知识增长

M-000 不预设字数上限。正文长度由信息密度、冷启动成本和不可下沉证明共同决定。frontmatter `override_rationale` 字段是密度证明而非破例申请——作者必须论证：当前长度的每一段内容为什么不能下沉、为什么不能压缩、为什么不能省略。代码块、译本等不单独设立预算，由同一密度证明覆盖。具体冗余检测信号、密度证明判据与同 PR 修订路径下沉 M-005 §J（M-005 §J.4 已明确删除代码块独立预算和英文译本固定乘数作为默认规则）。

新增条款必须先证明无法下沉。下沉优先级（从高到低）：
1. **standards**（静态规范，docs/standards/）：规则、约束、规范——不需 LLM 动态判断
2. **templates**（静态模板，docs/templates/）：代码片段、配置模板、checklist——纯模板可 cp 修改
3. **hook / CI 自动化**：可机械检查的规则下沉到 .claude/hooks / .github/workflows / Scripts
4. **工具脚本**：复杂校验或转换逻辑下沉到 Scripts/
5. **M-001~M-006 / ADR**：跨多个执行单元的协作规则
6. **skills**（仅用于需要 LLM 动态判断且不可静态化的场景）：trigger 条件依赖上下文推理，无法机械化

若条款只是执行步骤、模板、例子、命令、检查脚本或当前状态，应下沉至 standards / templates / hook，**不应保留为 skill**。skill 是元规则下沉的**末位优选**，仅在前 5 项均不适用时使用。

路径 C [#019](user-decision-log.md#019-路径-c-stage-5-批量执行完成--skill-生态-52--11) / [#020](user-decision-log.md#020) 实证：52 个 skill 中 82% 被识别为非 optimal 形态（46% MERGE + 13% DELETE + 13% DOWNGRADE + 10% PROMOTE），证明 skill 不应作为下沉的优选去向。短期豁免：路径 C 已审计的 11 个 KEEP/REWRITE skill 在 6 个月内（≤2026-11-25）不自动触发下沉重审，待 M-003 ratify 时统一处理。

知识库治理不使用固定文件数量作为单一门槛。新增文档必须说明预期消费者；4 周无 incoming refs 的活跃文档进入 archive 候选但不自动归档。判断信号包括 Boot/Action Gate 字符预算、incoming refs、访问或修改频率、重复权威定义、维护成本和是否可由工具生成。

## §7 layer 迁移

frontmatter 是机器可检查入口，不是装饰。字段若被工具消费，扩展前必须列出消费端和兼容方案；字段若只供人读，应明确其解释性性质，避免下游误当强 schema。

v2 目标 layer 简化为三类：

| 新 layer | 含义 | v1.2 映射 |
|---|---|---|
| `principle` | 稳定规则、模式、契约、工作标准 | `principle` / `pattern` / `contract` |
| `decision` | 裁决记录、ADR、仍有活性的决策链条 | `decision` |
| `archive` | 历史快照、归档材料、废弃文档 | `snapshot` / `archive` |

迁移期保留当前 validator 兼容层。使用旧 layer 的文档可加 `layer_deprecated: true` 标记，并由 M-005/工具定义消费语义后再批量迁移；不得为了语义纯度破坏下游脚本。

## §8 docaudit 边界

docaudit 只证明“可机械检查的结构信号通过”，不证明事实正确、判断正确或协作独立。每个 check 必须有真实事故来源或清晰风险模型；没有来源的 check 可保留为可选或实验，不得进入阻塞门。

| 核心 check | 目的 | 来源或风险模型 |
|---|---|---|
| frontmatter schema | 保证机器入口可读、生命周期字段不漂移 | #008 证明字段语义会影响下游消费 |
| link / path integrity | 防死链、迁移后悬挂引用 | ADR/archives 迁移多次产生追溯风险 |
| verdict / log sync | 防裁决、状态、handoff、ledger 不一致 | 多轮裁决撤回与 Overrule 链条 |
| external freshness / gap_due | 防模型、工具、价格、能力事实过期 | #002、#005 暴露易变事实风险 |
| rule usage trace | 防 F-rule / standards 只存在不被引用 | Phase 10 中规则漏用问题 |
| skill provenance | 防 skill 入口、支持文件和声明不一致 | skill 化后常驻可见性与真实加载不等价 |

可选 check 包括孤儿文档、home path 引用、术语一致性、知识地图聚合、归档快照完整性、依赖图现实性等。可选不代表无价值，只表示未证明应阻塞所有任务。

## §9 目的优先原则

规则、指标、字数、阶段、枚举和 check 都是服务目的的工具。若遵守形式会削弱可靠性、可追溯性、独立性或用户裁决权，应优先保护目的，并记录为什么偏离形式。工具是规则的执行器，不是规则的边界。

实证：#006 中同源激进方案被异源 sanity check 纠偏；#007 中 ADR 拆分接受异源激进版本；#008 中 sanity check 自身撤回上一轮建议；#009 中 M-000 用自身机制审计自身并识别非第一性外壳。这些都说明指标、流程和 reviewer 结论必须允许被目的反向校正。

## §10 风险、降级与复审

主笔轮换、异源审计、物理隔离和裁决日志都会增加摩擦，但这是为了降低单一智能体长期偏向和规则静默漂移。成本本身不构成废除理由；若成本持续压倒收益，应通过 M-001/M-005 归纳更精确触发条件，而不是私下绕开。

用户长期不可达时，智能体只可执行可逆、局部、低外部副作用动作；不可逆事项阻塞等待。细则下沉 M-004。

服务发生重大或持续变化时，自动触发相关规则复审：模型能力漂移、CLI 行为变化、价格或可用性剧变、工具链阻塞、数据共享边界变化、外部事实来源失效。复审只改变未来适用性，不删除历史裁决。v1.2 生效版本在 v2.0 完成确认后归档至 `docs/archive/meta/M-000-v1.2.md`；元层级第一性审计每 6 个月或重大外部冲击后触发。

## §11 下游派生

M-001~M-006 是 M-000 的下沉层。它们可调整名称、合并或拆分，但在 v2.0 生效前先保留既有归宿，待各文档完成后再做归并审计。

| 文档 | 职能 |
|---|---|
| M-001 协作工作流规约 | 规定多方启动、独立工作、物理隔离、上下文加载、主笔轮换提议、单方执行窗口 |
| M-002 分歧裁决与裁决日志 | 规定裁决流程、证据等级、双核同意适用域、Overrule 写法、撤回与复审机制 |
| M-003 技能库治理 | 规定经验如何沉淀、加载、淘汰，区分常驻入口与按需 skill |
| M-004 降级操作手册 | 规定服务受限、用户不可达、工具失败时的降级路径与停止等待判据 |
| M-005 质量判据与退化检测 | 规定产出质量度量、伪共识识别、docaudit 核心/可选 check、自反性 sanity check |
| M-006 数据治理 | 规定跨厂商数据共享、最小化、脱敏、prompt injection 防御与敏感信息边界 |

## §12 自我修订

M-000 修订必须满足四点：说明触发原因；说明哪些条款无法下沉；说明对 `user-decision-log` 的影响；说明是否 Overrule 历史裁决。若修订由第一性原理审计触发，应保留审计输入、禁止材料和独立性条件，避免后续无法判断结论是否被污染。

即使没有外部冲击，M-000 也应按 `freshness.max_age_days` 复审。复审目的不是寻找可改之处，而是确认：规则是否仍服务目的，是否被工具或指标反向塑形，是否产生无人维护的下游负担。
