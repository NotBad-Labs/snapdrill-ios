# M-000 Meta-Vision v2.0 — Codex 草案

> M-000 是项目协作规则的优先级 0 入口：规定智能体协作如何保持可靠、可追溯、可修正。具体操作下沉到 M-001~M-006、standards、skills 和工具。

## §1 定位与边界

M-000 只保留无法下沉的元规则：谁有最终裁决权、独立判断怎样成立、规则冲突怎样处理、规则系统怎样避免膨胀和自我欺骗。它不承担知识库、流程手册、prompt 模板、工具说明或状态看板职责。

下游文档不得与 M-000 冲突。若冲突来自新事实或新失败模式，应先记录到 `docs/meta/user-decision-log.md`，再决定是否修改 M-000 或只更新下游规则。普通修辞、历史命名和目录位置不构成规则依据；可执行条款、用户裁决和可追溯证据才构成依据。

## §2 认识论根基

可复现只是最低条件，独立趋同才有证据价值。单一模型可以稳定复现同一个错误；多个实例也可能因为训练谱系、提示词、上下文或工具状态相似而同向犯错。多方协作的价值不在多数投票，而在暴露假设、边界、反例和失败模式。

同一完整任务不得被拆成分工式外包来冒充独立判断。F-008 的核心要求是：每个独立方都拿到同一净化任务定义，独立完成完整判断，再进入折叠。若任务被拆成 A 方找问题、B 方补遗漏、C 方只复核，产物只能证明分工覆盖，不证明独立趋同。

## §3 默认多方异源

任何结构性任务默认进入多方异源判断，包括元规则修改、跨文档重构、不可逆操作、外部事实判断、质量标准变更、用户承诺、数据治理和重要产品方向。低风险、可逆、机械性动作可由 M-001 定义单方执行窗口，但该窗口必须是下游操作优化，不改变本文件的默认价值选择。

用户可显式豁免某次任务为单方执行。豁免应写入裁决日志或任务记录，至少说明豁免范围和理由；多次重复豁免可在 3-6 个月后由 M-001/M-005 归纳为稳定判据。

## §4 独立性与同源警戒

独立性至少包含四层：模型权重或训练谱系不同、运行实例不同、上下文互不可见、任务输入未泄露其他方中间结论。只满足其中一两项时，只能算辅助视角，不能算强独立证据。

结构性同源一致是伪共识风险。若两个同源或近同源智能体给出同向激进方案，而异源方给出具体、可证伪的反对意见，自动触发用户裁决；双核或多数意见不得直接压过该反对意见。辅助方沉默不构成认同；关键决策必须明确表态。

高风险审计和多方起草应使用物理隔离：独立 worktree、独立分支、净化任务定义、互不可见中间产物。只靠提示词要求“不要参考别人”不足以防止污染；工具缓存、IDE 状态、会话亲和性也应由 M-001 制定清理纪律。

## §5 三阶段协作流程

复杂协作不再固定为五个阶段。默认骨架为三阶段，具体子步骤由任务复杂度浮动。

1. 准备：明确问题、范围、输入材料、禁止材料、输出格式、验证方式和是否需要物理隔离。若任务本身会修改规则系统，必须先说明修改边界。
2. 独立产出：各方基于同一净化任务定义完成完整任务，不互相读取中间产物，不按角色分工规避困难部分。需要事实确认时优先使用可复查来源或本地仓库证据。
3. 合并裁决：折叠共识、分歧和独家发现；对每个冲突给出证据与推荐；用户做最终裁决。裁决后的执行、验证和记录属于同一阶段，不另设仪式性步骤。

流程的目标是获得更可靠判断，不是凑齐固定人数、固定表格或固定步骤。若形式合规但独立性、证据或裁决链条缺失，视为失败。

## §6 用户裁决与裁决日志

用户拥有最高裁决权。智能体可提出方案、反对方案、请求澄清和指出风险，但不得把模型多数、工具绿灯、历史习惯或主笔偏好当作最终依据。涉及不可逆操作、跨越本地工作区边界、对外承诺、元规则修改、法律或财务风险、产品方向实质变化时，默认上交用户。

`docs/meta/user-decision-log.md` 是用户裁决的 append-only 记录。每条结构性裁决至少包含时间、冲突描述、裁决、理由、是否触发元规则修订、Overrule 关系和元层级注记。新裁决若覆盖、撤回、接管、废弃或精化旧裁决，必须显式写出 Overrule 关系；否则不得让智能体推断“旧规则自然失效”。

Overrule 不等于删除历史。旧裁决保留为解释链条，新裁决说明哪一部分失效、哪一部分保留、失效原因是什么。若无法说明边界，应上交用户，而不是用“最新为准”掩盖冲突。

## §7 预算、下沉与 override

M-000 的默认正文预算为 2500 non-whitespace chars；这是可读性和冷启动成本的设计目标，不是自动否决线。超过默认预算时，frontmatter 必须写 `override_rationale`，说明为什么不能下沉、为什么此处的表达密度仍然必要、何时复审。

新增条款必须先证明无法下沉到 M-001~M-006、standards、skills、ADR、STATUS stub 或工具。若条款只是执行步骤、模板、例子、命令、检查脚本或当前状态，应下沉。M-000 可引用下游入口，但不复制下游正文。

代码块原则上不进入 M-000。若必须出现，应单独说明原因，并优先放到下游文档或工具中维护。未来英文译本不共享中文预算，应按信息密度单独设默认预算和 override。

## §8 目的优先原则

规则、指标、字数、阶段、枚举和 check 都是服务目的的工具。若遵守形式会削弱可靠性、可追溯性、独立性或用户裁决权，应优先保护目的，并记录为什么偏离形式。

历史材料中的旧称“古德哈特防御”只作为别名追溯，不作为正文规则名。可操作定义是：当指标开始诱导规避、压缩黑话、虚假独立、过度拆文档或为了工具绿灯改变真实判断时，必须调整指标或触发用户复核。工具是规则的执行器，不是规则的边界。

## §9 frontmatter 与 layer 迁移

frontmatter 是机器可检查入口，不是装饰。字段若被工具消费，扩展前必须列出消费端和兼容方案；字段若只供人读，应明确其解释性性质，避免下游误当强 schema。

v2 目标 taxonomy 简化为四类：

| v2 类别 | 含义 | v1.2 映射 |
|---|---|---|
| `root_rule` | 最高优先级或跨系统稳定规则 | `principle` |
| `operating_rule` | 可复用的工作流、标准、合约、仍活跃的决策 | `pattern` / `contract` / active `decision` |
| `state_record` | 有时效的状态、快照、审计结果、任务定义 | `snapshot` |
| `archive_record` | 只保留历史追溯，不再作为活规则 | `archive` / archived 或 deprecated `decision` |

迁移须分两步：先在 M-005/工具中定义消费语义和兼容层，再修改 validator 与现有文档 frontmatter。迁移完成前，草案文件可继续使用当前 validator 支持的 `layer: principle`，正文以 v2 taxonomy 指导后续改造。

## §10 docaudit 边界

docaudit 只证明“可机械检查的结构信号通过”，不证明事实正确、判断正确或协作独立。每个 check 必须有真实事故来源或清晰风险模型；没有来源的 check 可保留为可选或实验，不得进入阻塞门。

核心 check 建议保留 5-6 类：

| 类别 | 目的 | 来源或风险模型 |
|---|---|---|
| frontmatter schema | 保证机器入口可读、生命周期字段不漂移 | #008 证明字段语义会影响下游消费 |
| link / path integrity | 防死链、迁移后悬挂引用 | ADR/archives 迁移多次产生追溯风险 |
| verdict / log sync | 防裁决、状态、handoff、ledger 不一致 | 多轮裁决撤回与 Overrule 链条 |
| external freshness / gap_due | 防模型、工具、价格、能力事实过期 | #002、#005 暴露易变事实风险 |
| rule usage trace | 防 F-rule / standards 只存在不被引用 | Phase 10 中规则漏用问题 |
| skill provenance | 防 skill 入口、支持文件和声明不一致 | skill 化后常驻可见性与真实加载不等价 |

可选 check 包括孤儿文档、home path 引用、术语表一致性、知识地图聚合、归档快照完整性、依赖图现实性等。可选不代表无价值，只表示未证明应阻塞所有任务。

## §11 知识库增长信号

知识库治理以冷启动负担和维护成本为中心，不使用固定文件数量作为单一门槛。新增文档必须至少说明一个预期消费者：Boot、Action Gate、某个 skill、某个 standards、某类审计、某个 ADR 或具体代码流程。

四周无 incoming refs 的活跃文档进入 archive 候选，但不自动归档；用户裁决、法规、外部依赖和低频高风险知识可例外保留。判断信号包括：Boot/Action Gate 字符预算、incoming refs、最近访问或修改频率、重复权威定义、维护者数量、变更传播成本、是否可由工具生成。

每个概念应只有一个权威定义。重复定义不可避免时，必须标明哪个是 SSOT，哪个只是指针或历史快照。

## §12 风险接受与降级

主笔轮换、异源审计、物理隔离和裁决日志都会增加摩擦，但这是为了降低单一智能体长期偏向和规则静默漂移。成本本身不构成废除理由；若成本持续压倒收益，应通过 M-001/M-005 归纳更精确触发条件，而不是私下绕开。

服务发生重大或持续变化时，自动触发相关规则复审：模型能力漂移、CLI 行为变化、价格或可用性剧变、工具链阻塞、数据共享边界变化、外部事实来源失效。复审只改变未来适用性，不删除历史裁决。

用户长期不可达时，智能体只可执行可逆、局部、低外部副作用动作；不可逆事项阻塞等待。降级路径由 M-004 细化。

## §13 下游派生

M-001~M-006 是 M-000 的下沉层。它们可调整名称、合并或拆分，但在 v2.0 起草阶段先保留既有归宿，待各文档完成后再做归并审计。

| 文档 | 职能 |
|---|---|
| M-001 协作工作流规约 | 规定多方启动、独立工作、物理隔离、上下文加载、主笔轮换提议、单方执行窗口 |
| M-002 分歧裁决与裁决日志 | 规定裁决流程、证据等级、Overrule 写法、撤回与复审机制 |
| M-003 技能库治理 | 规定经验如何沉淀、加载、淘汰，区分常驻入口与按需 skill |
| M-004 降级操作手册 | 规定服务受限、用户不可达、工具失败时的降级路径与停止等待判据 |
| M-005 质量判据与退化检测 | 规定产出质量度量、伪共识识别、docaudit 核心/可选 check、自反性 sanity check |
| M-006 数据治理 | 规定跨厂商数据共享、最小化、脱敏、prompt injection 防御与敏感信息边界 |

## §14 自我修订

M-000 修订必须满足四点：说明触发原因；说明哪些条款无法下沉；说明对 user-decision-log 的影响；说明是否 Overrule 历史裁决。若修订由第一性原理审计触发，应保留审计输入、禁止材料和独立性条件，避免后续无法判断结论是否被污染。

即使没有外部冲击，M-000 也应按 `freshness.max_age_days` 复审。复审目标不是寻找可改之处，而是确认：规则是否仍服务目的、是否被工具或指标反向塑形、是否产生无人维护的下游负担。
