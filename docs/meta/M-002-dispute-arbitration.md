# M-002 分歧裁决与裁决日志

> M-002 定义「智能体之间分歧如何裁决、用户裁决如何记录、旧裁决如何被覆盖与撤回」的可操作流程。承接 M-000 §5（用户最高裁决权）+ M-000 §11.1 派生职能（裁决流程、证据等级、双核同意适用域、Overrule 写法、撤回与复审机制）。
> **前置依赖**：M-000 v2.0（§2 PRIMARY / §3 异源 / §5 裁决主权 / §8 Overrule）、M-005（§B.3 否决权阈值 / §F 自反性 sanity check / §C 静默退化）。

---

## §1 定位

M-002 是 M-000 §5「用户拥有最高裁决权」的可执行派生。M-000 §5 给出原则（用户主权 + 双核同意 + Overrule + append-only 日志），M-002 给出**判据**：

1. 什么时候触发裁决（§4）
2. 谁是裁决方、证据等级如何认定（§5）
3. 双核同意覆盖哪些事项、不覆盖哪些事项（§6）
4. Overrule 如何写才生效（§7）
5. 撤回与复审的机制（§8）
6. 裁决清单变更的边界（§9）
7. 用户裁决日志的字段 schema（§10）
8. 状态快照如何防漂移（§11）

M-002 不取代任何下游的具体裁决产物（如 ADR、sign-off 报告、Overrule 条目）——M-002 定义这些产物的**结构契约**，让产物可被消费、被引用、被复核。

适用范围：所有 M-000 §3 默认多方异源约束下的产出，含元规则起草、ADR 提案、第一性原理审计、cross-audit、sign-off、用户私下 Overrule 的主分支同步。

## §4 裁决触发条件

### §4.1 默认上交用户的事项

承接 M-000 §5：以下事项**默认上交用户**，不允许智能体绕过：

1. **不可逆操作**：跨越本地工作区边界 + 外部副作用 + 对外承诺（如 `git push` / `fastlane match` / TestFlight 发布 / 删除文件 / 数据库迁移）
2. **元规则修改**：M-000 / M-001~M-006 任一条款的新增、修订、Overrule
3. **法律或财务风险**：合规边界、付费 API 切换、隐私声明变更
4. **产品方向实质变化**：用户故事重写、核心功能取舍
5. **结构性决定**（引 M-005 §I.1）：归档路径、目录重命名、跨目录文件移动、批量 frontmatter 修改、删除文件、修改验证脚本枚举

**违反信号**：以上事项中任一项被智能体单方执行而无显式用户授权 → 按 M-005 §I 「自作主张越权」处理。

### §4.2 异源分歧触发裁决

承接 M-000 §3 + M-005 §B.3：当**异源方提出强烈、具体、可证伪反对**时，自动触发用户裁决：

- **强烈反对三要素**（缺一不可，引 M-005 §B.3）：引用具体事实错误 + 提出可证伪反假设 + 指出明确风险路径
- **触发动作**：折叠主笔在 consensus 报告中显式列出该反对意见 + 待裁决标记 + 上交用户
- **不阻断执行**：M-000 §5 规定智能体提示冲突不阻断执行——非阻断事项可并行推进，阻断事项（不可逆 / 元规则）必须等待裁决
- **否决权滥用联动**：同一异源方 24 小时内高频触发否决（≥3 次）但 ≥2 次不满足三要素时，按 M-005 §B.3 滥用判据自动触发 §C 静默退化扫描；扫描确认退化则按「逻辑不可用」处理（§5.6）

### §4.3 跨厂商数据共享触发裁决

承接 MC-4（M-006 派生）：当任务涉及跨厂商共享用户数据 / 项目代码 / 内部决策时，触发用户批准裁决：

- **默认行为**（用户未定义脱敏策略时）：最小披露 + 不跨厂商共享 + 记录缺口（缺口纳入裁决日志，触发用户后续补充）
- **裁决产物**：批准范围（全局 / 仅当前任务）+ 数据类型清单 + 期限
- **归宿**：M-006 起草时承接技术细节，M-002 仅定义批准入口

### §4.4 不触发裁决的事项（单方执行窗口）

以下事项可由智能体单方执行（M-001 单方执行窗口清单的元规则层定义）：

- **可逆、局部、低外部副作用**的机械操作（如 lint 修复、import 排序、**非结构性、可逆的本地文件改名**）
- 已有显式用户授权的批量动作（授权范围内）
- 已 ratify 的规则要求的强制动作（如 docaudit check 强制阻塞）

**排除清单**：以下动作即使表面是「本地操作」也**不**属于单方执行窗口——必须按 §4.1 / M-005 §I.1 上交用户：
- 归档路径决定 / 目录重命名 / 跨目录文件移动 / 删除文件
- 批量 frontmatter 修改 / 修改验证脚本枚举
- 任何会触发 git pre-commit hook 失败或下游消费端语义变化的本地动作

**判据**：「这件事如果做错，是否需要用户介入恢复？」若答案是「否」（可一键回滚 / 无外部副作用 / 不破坏裁决链）→ 单方执行；否则上交用户。

## §5 证据等级与裁决方

### §5.1 三档证据等级

| 等级 | 定义 | 处置 |
|---|---|---|
| **强独立证据** | 满足 P1 同任务 + P3 异源 + P4 非同源 + P5 物理隔离 + P7 净化提示词 | 直接进入折叠裁决，无需用户介入（除非触发 §4） |
| **辅助视角** | 缺 P1/P3/P4/P5/P7 任一项（如分工外包、同 vendor 多端点聚合、隔离失效信号触发） | 不构成强证据，但可作为参考；与强证据冲突时强证据优先 |
| **伪共识** | M-005 §B 触发信号成立（连续同源主笔 / 多实例同 cutoff / 多端点聚合 / 身份漏泄 / 消费偏向） | 折叠报告显式标注权重折扣（0.5 或更低）+ 上交用户复核 |

### §5.2 强证据要件

一份独立产出要被认定为强证据，必须同时满足：

1. **任务定义书一致**（P1）：所有方收到同一净化任务定义，无中间产物泄漏
2. **训练谱系异源**（P4）：基于厂商公开声明（不依赖智能体自我宣称，引 M-005 §D.2）
3. **物理隔离**（P5）：独立 worktree / 分支 / context；无 .claude.md 横向扩散（M-005 §B.2 5 条检测路径）
4. **净化提示词**（P7）：任务定义不含「参考其他方」「我们之前决定」等暗示

任一项失败 → 降级为辅助视角，记录降级原因。

### §5.3 证据等级降级触发

承接 M-005 §B.2 物理隔离失效检测：以下信号触发证据等级降级：

- 提示词污染 / git 历史横向引用 / .claude.md 横向扩散 / agent 内部推理链泄漏 / 产物相似性
- 触发后该方产出标记为「辅助视角」；若该方原本是关键异源反对方 → 自动升级用户裁决（§4.2）

### §5.4 伪共识识别

直接引用 M-005 §B.1 触发信号清单（5 条），不重复定义。M-002 仅定义裁决后果：

- **升级类信号**（连续同源主笔 / 多实例同 cutoff / 多端点聚合 / 身份漏泄硬模式）→ 自动用户裁决
- **折扣类信号**（thinking 模式身份漏泄 / 主笔消费偏向）→ 折叠报告显式标注 0.5 权重折扣，不强制阻塞
- 折扣可叠加（如 0.5 × 0.5 = 0.25）

### §5.5 裁决方资格

裁决方分两类：

1. **用户**：所有 §4 触发的裁决，用户是唯一终审方
2. **异源 reviewer**：用户授权范围内的 sign-off 复核（如 M-003 §7 N≤2 异源审查终止规则）

**主笔不裁决**：主笔产出的产物，由主笔以外的异源方审议；主笔可作为辅助 reviewer 出席，但不下场裁决（M-005 §H.2 物理隔离要求）。

### §5.6 裁决方不可用时的处置

承接 M-000 §5「任一方不可用时，双核自动通过权失效」+ MC-1：

- **物理不可用**（API 报错 / 超时 / CLI 死锁）→ 双核失效，按 M-004 降级流程
- **逻辑不可用**（M-005 §C 静默退化硬信号）→ 等同物理不可用，回退用户
- **用户长期不可达**（>24 小时无响应）→ 仅执行可逆、局部、低外部副作用动作；不可逆事项阻塞等待（M-004 派生具体等待判据）

## §6 双核同意适用域（承接 MC-1）

### §6.1 双核同意默认通过的适用范围

双核（两家异源方）同意可作为推进底线，但**仅覆盖以下事项**：

1. **普通**：不属于 §4.1 默认上交用户清单（不可逆 / 元规则 / 法律财务 / 产品方向 / 结构性决定）
2. **可逆**：可一键回滚 / 无对外承诺 / 不破坏裁决链
3. **低外部副作用**：不影响其他智能体 / 不污染共享状态 / 不消耗外部配额

三条件缺一不可。任一条件不满足 → 即使双核同意，也必须上交用户。

### §6.2 双核同意不通过的事项

以下事项**双核同意无效**，必须用户裁决：

- §4.1 默认上交用户的全部 5 类
- §4.2 异源强烈反对触发的事项
- §4.3 跨厂商数据共享
- §5.4 伪共识升级类信号触发的事项
- §5.6 裁决方不可用导致双核失效的事项

### §6.3 双核同意的记录要求

双核同意推进的事项**仍须留痕**：

- 折叠报告记录两家同意意见 + 任务定义书 + 隔离条件
- 不进入 user-decision-log（只有用户裁决进入）
- 留存在 PR description / commit message / docs/audits/ 子目录

留痕的目的：事后若被异源 sanity check 撤回（§8），需追溯当初证据。

## §7 Overrule 写法

承接 M-000 §5 + §8：新裁决覆盖、撤回、接管、废弃或精化旧裁决，必须显式写出 Overrule。Overrule 的可验伪 schema：

### §7.1 必填字段

```yaml
Overrule 关系: Overrule <旧裁决编号 + 条款>
Overrule 对象: <被覆盖的具体条款 / 字段 / 数值>
Overrule 范围: <覆盖范围 + 保留范围（哪些不受影响）>
Overrule 生效时刻: <时间点 / 条件>
理由: <为什么覆盖（实证 / 第一性原理 / 新证据）>
```

四个字段（关系 / 对象 / 范围 / 理由）缺一不可。生效时刻默认「本条目录入时同步生效」可省略，但其他四字段必填。

### §7.2 Overrule vs 精化的区别

- **Overrule**：完全覆盖旧裁决的某条款（即旧条款失效）
- **精化**：旧裁决的核心精神保留，仅精化数值 / 边界 / 措辞（如 #003 精化 #001 字数定义，1500→2500，但「放宽气口」方向不变）

精化也必须显式声明「精化 #编号」+ 精化对象 + 保留范围，但不需要写「Overrule」字样。

### §7.3 Overrule 不删除历史

Overrule 只说明失效范围 + 保留范围 + 理由，**不删除旧裁决条目**。旧条目永远在 user-decision-log 中可追溯，新条目通过 Overrule 关系链接到旧条目。

### §7.4 默认通过的隐含 Overrule

若新裁决与旧裁决在事实层冲突（如 #015 字数原则升级与 #009 R2 字段保留冲突），但新裁决未显式 Overrule → **不得推断旧规则自然失效**（M-000 §5 原则）。必须补写显式 Overrule 条目。

**违反信号**：user-decision-log 中两条条目事实层冲突但无 Overrule 链接 → 触发裁决日志一致性 docaudit check（M-005 §G.5 可扩展）。

## §8 撤回与复审

### §8.1 sanity check 不是终审

直接引用 M-005 §F.2：异源 sanity check 共识也可被后续 sanity check 撤回。撤回时必须：

1. 显式写出 Overrule 范围（§7.1 schema）
2. 引第一性原理 / 工程兼容性 / 新证据作为撤回理由
3. 不自动销毁原产出 → 加 `sanity_check_blocked` 标记后回退用户裁决

### §8.2 复审触发条件

以下情况自动触发已 ratify 裁决的复审：

1. **新实证出现**：与原裁决前提冲突的新事故 / 用户反馈
2. **依赖前提失效**：原裁决依赖的外部事实（如模型可用性 / API 行为）发生变化
3. **下游派生发现缺口**：M-001~M-006 起草过程中发现原裁决未覆盖的场景
4. **freshness 到期**：frontmatter `freshness.max_age_days` 到期触发例行复审

### §8.3 复审入口

复审通过提交「复审提案」进入 M-002 裁决流程：

- 提案文档路径：`docs/audits/recheck-<裁决编号>-<日期>.md`
- 必填内容：被复审裁决编号 + 复审触发条件 + 新证据 + 提议处置（保留 / 精化 / Overrule / 撤回）
- 至少 1 家异源方评估后进入用户裁决入口

### §8.4 撤回与 PR 作废

引 M-005 §I.3 + #014 D7：

- PR 中夹带结构性变更但无相应 user-decision-log 记录 → 自动作废该 PR
- 复审撤回的裁决在 user-decision-log 中标记 `superseded_by: #NNN`，原条目不删除

## §9 裁决清单变更（承接 MC-5）

### §9.1 变更类型分级

裁决智能体清单的变更分两级：

| 变更类型 | 示例 | 处置 |
|---|---|---|
| **版本升级**（同 vendor） | Gemini 2.5 → 3.5 / Claude Opus 4.6 → 4.7 / DeepSeek V3 → V4 | 仅 `agent-cli-models.md` 更新 `last_verified`；不进入 user-decision-log |
| **能力跃迁**（同 vendor） | 推理能力大幅提升导致裁决资格变化（如 GPT-4 → GPT-5 reasoning 模式） | 在裁决日志补一行说明，但不算正式清单变更 |
| **跨 vendor 替换** | GPT 替换 Gemini / 新增 DeepSeek 到清单 | 走完整 user-decision-log 流程 + 元规则修订评估 |
| **新增 / 移除模型** | 加 / 移 vendor | 同跨 vendor 替换 |

### §9.2 判据

- **判据 1**：是否引入新的训练谱系（M-005 §D.2 厂商公开声明）→ 是 = 跨 vendor 变更
- **判据 2**：是否导致 §5.1 异源矩阵的「异源数量」变化 → 是 = 跨 vendor 变更
- **判据 3**：是否仅是同 vendor 内的版本升级 → 是 = 版本升级（轻量记录）

### §9.3 实证锚定

- **预备实证（待 user-decision-log 锚定）**：本会话（2026-05-25）发现 AGY CLI（Antigravity / Gemini 3.5 Flash GA via `/opt/homebrew/bin/agy`）确认可用，与 Antigravity GUI 同 vendor 同模型，仅端点变化 → 按 §9.1 / §9.2 判据属「版本升级」级别（同训练谱系 + 不改变异源数量）。本实证将在 M-002 ratify 同 PR 中以 user-decision-log 新条目 + `docs/tech/reference/agent-cli-models.md` 同步落档；落档前为 §9 判据的活体测试，不构成已 ratify 裁决锚。
- **#013 实证**：Gemini model ID 误用事故 → SSOT 注入 + subagent 验证 + 代码同步纪律下沉 M-005 §D.4，不归 M-002。

## §10 user-decision-log 字段 schema

承接 M-000 §5：append-only 裁决日志的最小必填字段集。

### §10.1 必填字段

```yaml
编号: #NNN（自增整数，跨日期连续编号）
时间: YYYY-MM-DD（日期粒度，时分秒可选）
冲突描述: <一段或多段文本，描述触发裁决的具体冲突>
裁决: <用户最终决定的具体内容>
理由: <用户裁决的依据（用户原话引用 / 第一性原理 / 实证）>
是否触发元规则修订: ✅ 是 / ❌ 否（+ 修订对象）
Overrule 关系: 无 / Overrule #NNN（按 §7.1 schema）
元层级注记: <本裁决对治理体系的元层级意义（如「第一次实战检验」「同源风险实证」「PRIMARY 内核新证据」）>
```

**八个字段缺一不可**（承接 M-000 §5 「至少包含」清单的全部 7 项 + 编号）。

**兼容历史条目**：存量 #001-#024 已包含「元层级注记」字段；未来新条目缺失该字段视为 schema 违反，触发裁决日志一致性 docaudit check（M-005 §G.5 可扩展）。

### §10.2 可选字段

- **归档关联**：本裁决关联的归档目录 / sign-off 报告路径
- **后续 backlog 关联**：本裁决衍生的 backlog 编号（如 MC-1 ~ MC-N）

### §10.3 编号规则

- 编号跨日期连续（不按日期重置）
- 当前最新 #024（2026-05-25 ratify），下一条 #025
- 编号不复用 / 不跳号；若条目作废，标记 `status: voided` + Overrule 链接，但编号保留

### §10.4 撤回与超废

- 被复审撤回的条目：标记 `superseded_by: #NNN` + 保留原内容
- 显式作废的条目：标记 `status: voided` + Overrule 链接 + 不删除

## §11 sync-status 双向维护（承接 MC-11）

### §11.1 STATUS.md 的定位

引 #006 裁决：STATUS.md 保留为 **minimal stub**，长期权威状态**不依赖手动复制**，也不在 Boot 阶段加载旧的大型状态快照。STATUS.md 的角色：

- 极简手动入口（≤500 nwc）
- 指向权威状态源（user-decision-log / backlog / git / GitHub）
- 等待 `sync-status` skill 双向自动维护

### §11.2 sync-status skill 的元规则层职责

**注**：sync-status skill 的实现细节归 M-001（具体提名流程 + 实现规约 + 触发条件），M-002 仅定义元规则层职责：

1. **session start**：读取 user-decision-log、backlog、git / GitHub 状态，生成当前状态视图
2. **session end**：写回 STATUS.md 极简手动条目，避免软状态漂移
3. **冲突优先级**：user-decision-log > backlog > git / GitHub live state > STATUS stub
4. **缺口记录**：无法自动判定的状态，不擅自把推论写成事实，记录为 `gap_due` 字段

### §11.3 状态漂移识别信号

以下信号触发 sync-status 强制刷新：

- STATUS.md 与 user-decision-log 最新条目超过 7 天未同步
- git log 中出现 user-decision-log 未记录的元规则相关 commit
- GitHub PR / Issue 与 STATUS.md 「当前焦点」不一致

### §11.4 与下游接口

- **M-001**：sync-status skill 的具体提名流程（哪个 vendor 主笔 / 触发条件 / 实现规约）
- **M-003**：sync-status skill 的入库门槛（§2.4 三条全满足）、生命周期审计
- **M-005**：sync-status 输出的质量判据（§A 可追溯 / 可验伪 / 下沉 / 目的关联）
