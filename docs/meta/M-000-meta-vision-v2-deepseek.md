# M-000 Root Rule —— 项目最高协作规则集

> 本文档定义规则系统的设计原则、裁决机制及演进约束，是智能体协作的最高优先级规范。
> 与产品 vision 平级：前者定义协作可靠性，后者定义产品方向。冲突时不预设倾向，必须上交用户，并附结构化分析。
> 正文≤4000 non‑whitespace chars（含此句前部分），具体条款下沉至 M‑001~M‑006。

## 1. 定位与适用范围

本文档是**元规则**：规定规则系统如何保持可靠、可演进、可追溯。所有协作任务默认适用本文档及其派生规则（M‑001~M‑006）。用户可显式豁免特定场景为单方，豁免须写入裁决日志并事后归类，允许 3‑6 个月后自然涌现判据。

## 2. 核心原则（PRIMARY 内核保留）

以下原则是体系的第一性根基，任何派生规则不得与之冲突；允许文字重述，但实质不得改动。

- **P1：相同完整任务、不分工** —— 每个参与方接收相同的完整任务描述，不得提前分工或指定角色。
- **P2：用户最高裁决权 + append‑only 裁决日志** —— 用户是最终裁决者，所有裁决逐条追加至 `docs/meta/user-decision-log.md`，不可改写历史。
- **P3：默认多方异源** —— 协作默认至少两方来自不同训练谱系、独立模型权重、独立运行实例、独立上下文。异源 = 互不可见中间产物 + 独立推理路径。
- **P4：同源警告** —— 若参与方训练同源且结论一致，构成伪共识风险，必须触发用户裁决。
- **P5：worktree 物理隔离** —— 各方在独立工作目录、独立上下文环境执行，不得共享中间产物。
- **P6：sanity check 自反性** —— 规则系统必须能应用于自身审计（如第一性原理审计），审计结果暴露其非第一性部分时不视为失败，而是健康反馈。
- **P7：净化提示词** —— 任务指示中不得携带其他参与方的推理路径、中间输出或判断倾向；使用去污染模板。
- **P8：Overrule 机制** —— 新裁决与历史裁决冲突时，必须显式声明对历史决策的 Overrule 关系，否则无效。Overrule 记录于裁决日志，不自动改写元规则；改写走正式流程。

## 3. 默认多方异源与物理隔离

### 3.1 默认多方
任何协作任务默认采用两方或更多异源智能体。用户可豁免单方场景，但须事后记录理由。默认多方是价值选择：质量优先于效率，同时承认 token、时间、注意力成本，不假装无成本。

### 3.2 独立工作条件
- 每个智能体拥有独立运行实例、独立上下文 buffer、独立工作目录（worktree 物理隔离）。
- 任务指示净化：不得包含其他方的推理路径、中间结论或判断倾向。
- 各方不能访问对方临时文件、痕迹或日志。

### 3.3 同源警报触发
若出现以下情况，视为结构性同源一致或伪共识风险：
- 参与方来自同一模型供应商，且训练谱系可追溯至同一基模型；
- 各方的结论高度一致且缺乏独立论证痕迹；
- 辅助方沉默（未明确表态）。沉默不构成认同，关键决策须辅助方明确表态；无表态默认上交用户。

当满足以上任一情形时，双核自动通过权失效，触发用户裁决。

## 4. 用户裁决权与裁决日志

### 4.1 用户最高裁决
任何冲突的最终裁决权属于用户。裁决智能体清单当前为 Claude + Codex，由用户维护；清单变更记录于裁决日志。

双核同意默认通过；当任一方不可用时，双核自动通过权失效，所有事项回退用户裁决。

不可逆操作定义为：跨越本地工作区边界、产生外部副作用、对外承诺；修改本文档、法律或财务承诺、产品方向实质改变必须上交用户。

### 4.2 裁决日志
裁决记录位于 `docs/meta/user-decision-log.md`，append‑only，字段为：时间、冲突描述、裁决、理由、是否触发元规则修订。

Overrule 规则（P8）适用于任何新裁决与历史裁决冲突的情况。若未显式声明 Overrule 关系，该裁决无效。

### 4.3 下沉与演进
新增条款必须证明无法下沉到 M‑001~M‑006 或 skill。不强制一进一出，允许新情况进入，但总量由 `default_word_budget` + `override_rationale` 机制自然约束。

## 5. 字数预算与覆盖机制

### 5.1 软上限
本文档正文（不含 frontmatter、§11 派生表；代码块单独预算 ≤400 nwc）默认软上限为 2500 non‑whitespace chars。若实际超出，须在 frontmatter 中声明 `override_rationale` 并说明原因。

### 5.2 派生规则字数
M‑001~M‑006 各文档应遵循类似的软上限原则，具体数字由各自文档定义，但不得与本文档冲突。

### 5.3 未来英文译本
英文译本使用独立乘数，约 4000 nwc 软上限，以应对中英文信息密度差。同样支持 `override_rationale`。

## 6. 起草流程（替代原 5 phases）

### 6.1 标准化流程（3 phases，可浮动）
任何重要起草或修订应遵循以下阶段：

| Phase | 名称 | 内容 |
|-------|------|------|
| P1 | 议题准备 | 对齐问题定义、明确改造目标、确定参与方数量及物理隔离配置 |
| P2 | 独立产出 | 各家物理隔离执行，按净化提示词独立撰写草案或修改 |
| P3 | 合并裁决 | 中立主笔折叠共识与分歧，用户裁决冲突，选定主笔产出最终版，签署生效 |

Phase 数随议题复杂度浮动：简单修订可合并 P1+P2 或 P2+P3；重大重构可增设「匿名评审」「社会性验证」等额外阶段。但最少不得低于 3 阶段，最多不得高于 6 阶段。

### 6.2 签署与归档
最终版本经所有参与方签署后，用户 ratify 并追加至 `user-decision-log`。旧版本归档至 `docs/archive/`，保留 git 历史。

## 7. 审计与检查（核心 Check 清单）

审计检查锚定实际风险来源，不作抽象堆叠。核心 Check（5‑6 项，必须每次审计覆盖）附真实事故来源或风险模型：

| # | 检查 | 风险模型/事故来源 | 类型 |
|---|------|-------------------|------|
| 1 | **同源一致警告** | 伪共识导致错误被集体确认（实证：#009 审计自身时的结构性一致） | 核心 |
| 2 | **物理隔离完整性** | 推理路径泄漏导致独立性丧失（实证：早期协作因共享上下文产生锚定偏差） | 核心 |
| 3 | **净化提示词合规** | 外来信息污染导致判断偏差（实证：非净化提示词下各向输出趋向一致） | 核心 |
| 4 | **裁决日志追索性** | Overrule 未显式声明产生歧义（事故：#009 之前 #007 隐含 Overrule 被忽略） | 核心 |
| 5 | **第一性密度评审** | 70% 以上内容为隐喻/借用的风险（实证：#009 识别 M‑000 v1.2 ～70% 非 PRIMARY） | 核心 |
| 6 | **下沉检查** | 条款应下沉而未下沉导致文档膨胀（风险：缺乏下沉强制导致元规则膨胀） | 核心 |

可选 Check（非强制，根据上下文选择性执行）：
- 字数预算合规性（如需判断是否触发 override）
- 术语一致性（无重叠定义）
- 外部冲击触发 review 条件已满足
- 派生规则与 M‑000 无冲突
- 历史裁决中未标注 Overrule 的冲突对应当前决策无影响

每个可选 Check 必须附引用来源或风险模型才能纳入审计范围。

## 8. 知识库治理（取代硬数字阈值）

不设硬性文件数量上限。知识库质量信号包括：
- **Boot 字符预算**：每次 Boot 加载的基础文档总字符数不应超过用户设定的警戒线（当前建议 8000 chars）；
- **引用度**：每个知识条目必须记录引用次数；若连续 4 周无新 incoming references，自动标记为 archive 候选；
- **访问频率**：过去 30 日内未被访问的条目视为低活跃度，进入 review 队列；
- **新增条目要求**：新增知识条目必须提供至少一个引用方（引用该条目的文档或 task），否则不予入库。

上述指标用于智能推荐归档或精简，不由任何单一指标决定删除行动；操作需要用户确认。

## 9. 目的优先原则（原名“古德哈特防御”）

**定义**：当规则或度量被用作优化目标时，该度量会失去其作为指标的有效性，导致系统行为偏离设计初衷。
**原则**：在任何规则制定中，优先明确规则要服务的实质目的，而非拘泥于固定形式或数字。若规则本身成为追求表面合规的借口，即应回归目的审查。

别名：“古德哈特防御”（保留作为别名，但正式名称以“目的优先原则”为准）。

## 10. 外部冲击与风险接受

### 10.1 外部冲击触发 review
服务发生重大或持续性变化（关停、严重降级、价格跳变、能力实质漂移）时，自动触发本文档 review；历史裁决日志保留，适用性可复审。

### 10.2 主笔轮换风险接受
主笔轮换存在认知摩擦与质量波动风险，但此风险不构成放弃轮换的理由；单一主笔的累积偏向代价更高。系统提醒轮换，是否轮换由用户最高裁决，不强制。

## 12. 附录：layer 枚举迁移（R3 改造说明）

旧 v1.2 使用 6 层枚举：principle / pattern / snapshot / archive / decision / contract。
新体系简化为 3 层枚举，适用于本文档及所有派生文档：

| 新枚举 | 说明 | 旧枚举对应关系 |
|--------|------|----------------|
| `principle` | 原则性规则、元规则 | principle, pattern（pattern 降级为 principle 的子实践） |
| `decision` | 裁决记录、决策文档 | decision, contract（contract 视为附带约束的 decision） |
| `archive` | 历史版本、归档 | archive, snapshot（snapshot 并入 archive） |

本文档 `layer: principle`，符合新枚举。所有已存档的老文档可在 frontmatter 保留旧枚举，但须在元数据中标注 `layer_deprecated: true` 并迁移至新枚举（由 M-002 实施）。
