# SnapDrill iOS 项目文档体系审计报告

**审计日期:** 2026-04-09
**总体评分:** 7.2/10

## 总体评估

SnapDrill iOS 项目文档体系整体质量较高，产品定位清晰、技术架构合理、合规意识较强。架构采用合理的 5 层结构，且明确了零 PII、独立开关等数据合规基线要求。文档中涉及的需求、边界案例以及用户旅程都比较详尽。

但审计也发现了若干不可忽视的风险点，主要表现为：**合规漏洞**（如 COPPA 证据链和持久化 ID 收集相矛盾）、**技术与产品规划未对齐**（iCloud 同步、Word 导出、AI 辅助等 Pro 核心功能缺少落地技术方案）以及 **工程质量保障缺失**（测试体系未建立，关键性能指标验证缺失）。

建议优先修复 P0 和 P1 级别的问题，以保证项目合法合规且能顺利推进开发。

---

## 详细维度审计

### 1. 文档体系完整性 (7/10)
- **[Critical] 测试文档缺失**：无测试计划、测试用例设计、覆盖率要求，及 OCR/SM-2 核心功能的专项测试说明。
- **[Major] UI/UX 设计文档缺失**：有“底部5个Tab”等描述，但无线框图、交互流程图和状态机设计（建议补充 `docs/design/ui-specs.md`）。
- **[Major] 数据模型详细设计缺失**：只有 `ReviewItemModel` 字段列表，缺少 ER图、SwiftData 关系定义及索引策略。
- **[Major] 运维与监控文档缺失**：缺乏运行时监控、错误日志和崩溃收集方案。
- **[Major] 支持与入职文档缺失**：缺少对新开发者的 `onboarding` 文档，以及面向用户的 FAQ 与帮助中心支持文档。

### 2. 文档间一致性 (6/10)
- **[Critical] OCR 状态与指标描述不一致**：`product-requirements.md` 提及已实现，但 API 文档无状态说明。且性能要求 <2s 未明确遇到复杂处理时是同步阻塞还是异步降级处理。
- **[Critical] Profile 切换中断策略缺失**：`product-cases.md` 要求在多态下有安全检查，但架构文档中 `ProfileManager` 无相应的 `switchProfile` 切换干预设计。
- **[Critical] 测试架构与边界案例不匹配**：声明 “View(不测)”，但边界案例涉及的大量权限拒绝场景必须通过 UI 测试验证。
- **[Major] COPPA 声明与用户定位矛盾**：合规文档声明 4+ 年龄和非儿童导向，但用户群其实包含中学生/儿童群体。

### 3. 产品逻辑健全性 (8/10)
- **[Major] 价值链与商业模式不一致**：愿景声明“复习是附加值”，但基础免费版提供了这部分功能；Pro 版试图以 iCloud 为核心卖点，但 iCloud 同步容易被手动备份替代，降低了付费吸引力。
- **[Minor] “绝对不限制录入数量”可能影响付费转化**：免费版核心产品太完善，商业可持续性需要再验证，可以考虑增加部分高级功能或导出限制作为区分。

### 4. 技术-产品对齐 (7/10)
- **[Critical] iCloud 同步未实现**：作为 Pro 核心卖点之一，架构文档尚未定义 CloudKit 相关的 Service 或 Repository 设计。
- **[Critical] 性能承诺未验证**：要求的 OCR<2s、列表<500ms、PDF生成<5s 等指标，目前没有技术论证和实测基准。
- **[Major] 多项 Pro 高级功能技术方案缺失**：Word 导出、AI 辅助拆题 PoC、手写体识别增强 PoC 等细节依赖模糊，未明确技术选型。
- **[Minor] SM-2 算法实现盲区**：缺乏具体的算法参数定义以及数据模型设计，且其后台长效计算可能与现有 SwiftData 的数据并发产生冲突。

### 5. 合规风险 (6/10)
- **[Critical] COPPA 合规面临矛盾**：使用了 Firebase `app_instance_id` 作为持久标识符，这在 COPPA 语境下属于个人隐私信息。App 受众涉及儿童群体，在缺少家长同意机制的情况下可能面临合规审查和罚款风险。
- **[Major] GDPR 与数据跨境传输未说明**：Firebase 数据默认存储在美国，需明确跨境数据控制及合规声明。
- **[Major] Analytics 独立开关功能缺失**：虽然提到了开关配置，但 `AnalyticsService` 没有真正实现 `isEnabled` 的隔离设计逻辑。

### 6. 可执行性 (8/10)
- **[Critical] 缺少质量门禁和完整的测试体系**：当前流程要求了 `swiftlint 0 violations`，但无明确的代码覆盖率指标（推荐 Repo>=80%、Service>=70%）以保障基本代码盘变动安全。
- **[Major] 软删除 (Soft Delete) + Undo 被杀处理未覆盖**：Undo 仅靠当前定时器延期，App 如果在此期间崩溃或者被杀后台，可能会导致数据不一致。
- **[Major] 存储基准未考虑极值增长**：未对题库超过极值（如大于 5000 题）所带来的存储告警和旧题压缩、归档策略做说明。

## 优先修复建议 (行动计划)

### P0（立即修复，建议1-2周内完成）
1. **COPPA 合规方案确立与排险**：立即确定策略（可以引入家长同意流程/移除 Firebase Persistent ID 或改用全本地策略 / 把应用纯粹限定为严苛中学生群体并移除引起相关误解的表述）。
2. **建立测试体系与核心性能基准**：补充 `docs/testing/test-plan.md`，并在工作流清单中加入测试用例编写，收集一次真实的 OCR 时长基准存入 `performance-benchmarks.md` 中。
3. **补充核心功能技术说明**：明确 OCR 建议使用的 Vision 技术方案并记录；规范 SM-2 算法核心控制数据库模型，解除开发端的技术封锁。

### P1（高优先级，1个月内完善）
1. **iCloud 同步技术落地**：完成 `icloud-design.md` 设计书，明确跨端数据合并及冲突解决。
2. **Profile 切换中断与异常保护策略**：编写跨身份操作时的数据保护防串联文档。
3. **备份版本向下兼容机制**：为 `.snapdrill` 格式化制定迁移策略，`BackupService` 接入 `Manifest` 版本追踪；填补意外退出时的数据恢复设计漏洞。

### P2（中等优先级，2个月内规划）
- 细化 UI/UX 设计规格书（交互与状态流）。
- 确立并细化 Data Model，明确索引策略，确认第三方 Word 文档操作库的选型与 AI 组件依赖。
- 详细说明被剥离的 EXIF 信息类别（防位置信息泄漏）。

### P3（低优先级，3个月内查缺补漏）
- 定制面向开发者的 `Getting Started` （Onboarding） 和最终用户的FAQ。
- 规定各类文档知识地图在各个迭代结尾进行最后修订时间标签维护等。
