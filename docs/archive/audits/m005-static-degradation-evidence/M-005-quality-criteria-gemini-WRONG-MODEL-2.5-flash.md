# M-005 质量判据与退化检测

§1 定位与适用范围

M-005 定义 SnapDrill 项目中元规则产出的质量判据，并提供一套检测协作智能体退化（包括物理和逻辑层面）的机制。它作为 M-000 PRIMARY 的核心支撑，为 M-001 到 M-006 以及后续派生规则提供可操作的“裁判工具”，确保规则体系的健康演进和智能体协作的可靠性。本文件不涉及具体的裁决流程或技术实现细节，仅聚焦于“什么是质量”和“何时出现退化”的判别标准。

§2 与 M-000 PRIMARY 的接口

M-005 的各个章节与 M-000 PRIMARY 内核（P1-P8）紧密关联，构成元规则体系的有机组成部分：

*   **P1 (相同完整任务、不分工)**：与 §A 产出度量的可追溯性、下沉证明和目的关联性相关，强调产出应是完整任务的独立判断而非分工切片；与 §B 伪共识识别中独立判断的证据价值相呼应。
*   **P2 (用户最高裁决权 + append-only user-decision-log)**：与 §A 产出度量的可追溯性直接关联，所有判据的有效性最终可追溯至用户裁决；与 §B 否决权阈值、§I 批准权防线相辅相成，保障用户裁决的最终性和透明性。
*   **P3 (默认多方异源)**：为 §B 伪共识识别提供理论基础，强调异源判断的证据价值；与 §H 主笔轮换机制紧密关联，通过轮换降低同源风险。
*   **P4 (同源警告)**：与 §B 伪共识识别直接相关，警示同源一致的风险，促使识别结构性同源伪共识。
*   **P5 (worktree 物理隔离)**：与 §B 伪共识识别中的物理隔离失效检测相关，提供检测隔离是否真正生效的判据；与 §H 主笔候选裁决的物理隔离要求相呼应。
*   **P6 (sanity check 自反性)**：直接构成 §F 自反性 sanity check 原则的核心，确保审计机制自身的复盘与纠错能力。
*   **P7 (净化提示词)**：与 §B 伪共识识别中的物理隔离失效检测相关，指导检测提示词是否被污染，从而影响独立判断。
*   **P8 (Overrule)**：与 §A 产出度量的可追溯性相关，确保规则变迁链条的清晰透明；与 §J 字数原则升级中对历史裁决的显式 Overrule 相衔接。

§3 与 M-001/M-002/M-004/M-006 的分工边界

M-005 作为元规则的质量与退化判据，严格遵守与 M-001/M-002/M-004/M-006 的分工边界：

*   **不抢 M-002 的活**：M-005 提供“质量判据”和“退化识别信号”，例如“双核同意适用域”如何被判定为“普通可逆低副作用”的判据（MC-1），以及异源“强烈、具体、可证伪反对”的客观判据（MC-10）。M-002 负责具体的“裁决流程”、“Overrule 写法”和“裁决日志结构”。
*   **不抢 M-001 的活**：M-005 §H 仅给出“主笔轮换原则”，具体的“主笔轮换流程”属于 M-001 的职责。
*   **不抢 M-006 的活**：M-005 §B/§C 仅提供“伪共识”和“静默退化”的“识别信号”，具体的“prompt injection 防御技术”和“敏感信息边界”属于 M-006 的职责。
*   **不抢 M-004 的活**：M-005 仅识别退化信号，具体的“降级路径”和“停止等待判据”属于 M-004 的职责。

§A 产出度量（Quality Criteria）

定义“什么是合格元规则产出”的可操作判据，确保元规则的健壮性和可维护性：

*   **可追溯性**：每条规则、判据或结论必须能够追溯到一个具体的证据来源，包括但不限于：历史用户裁决（引用具体编号如 #001、#002）、经实证的案例分析（如 #006、#007、#008 的异源纠偏案例）、明确的第一性原理论证、或厂商公开声明。不允许模糊指代。
*   **可验伪性**：每条规则或判据必须具有可识别的“违反信号”。应能清晰列举“什么样的产出或行为构成违反该规则”，避免主观判断。例如，§C 中列出的静默退化信号。
*   **下沉证明**：每条规则在纳入 M-005 时，必须说明“为什么不能下沉到下游 standards/skills/ADR/STATUS stub 或工具”。若规则只是执行步骤、模板、例子、命令或检查脚本，则应下沉。
*   **目的关联**：每条规则必须与 M-000 PRIMARY 内核（P1-P8）之一显式关联，或与 SnapDrill 的产品愿景直接对接，以证明其存在的必要性和高优先级。

§B 伪共识识别

旨在识别因训练谱系、上下文或提示词污染导致的结构性同源一致，避免将伪共识误作独立判断：

*   **触发信号清单**：
    *   **同源警告何时升级为用户裁决**：若同源或近同源智能体给出同向方案，而异源方提出“强烈、具体、可证伪”的反对意见，自动触发用户裁决（M-000 §3）。实证案例包括 #006 中同源激进方案被异源纠偏，以及 #007 中用户采纳异源激进拆分方案。
    *   **供应商多实例 / 相似训练 cutoff 的多家同向**：当多个实例（即使运行环境独立）或具有相似训练 cutoff 的不同厂商模型给出高度一致的判断时，应警惕伪共识风险，尤其在缺少异源强反对时。
*   **物理隔离失效检测**：
    *   检测 `worktree` 隔离是否失效：通过审视智能体产出中是否意外泄露了其他方的结论、编号、暗示或分工锚点，例如在 #010 中，主笔 Codex 声称收到用户私下 Overrule 但 Claude 主分支对此不知情，这表明物理隔离未能阻止信息泄露。
    *   `prompt` / `CLAUDE.md` / `git` 历史泄露立场的检测：审阅这些信息是否包含不应出现的跨智能体上下文，作为隔离失效的早期信号。
*   **否决权阈值（承接 MC-10）**：
    *   异源“强烈、具体、可证伪反对”的客观判据：构成有效否决的反对意见，必须引用具体事实错误、提出可证伪的反假设、或指出明确的风险路径。仅凭“我感觉不对”不构成有效否决。
    *   避免否决权滥用造成注意力通胀：M-002 将定义连续触发率阈值，以检测并避免辅助方滥用否决权。

§C 静默退化识别（承接 MC-1）

定义“物理可用但逻辑不可用”的智能体静默退化信号，以便及时回退或介入：

*   **定义「物理可用但逻辑不可用」的智能体退化信号**：
    *   **格式崩溃**：产出结构断裂，如 frontmatter 残缺、章节标题混乱、Markdown 语法错误等，表明输出控制力下降。
    *   **自相矛盾**：在同一产出内，不同段落给出对立或不一致的结论、观点或事实陈述。
    *   **偏离任务**：产出主题与任务定义书（包括上下文、目标、输入材料等）严重不符，表现为“胡言乱语”或“答非所问”。
    *   **身份误识别**：智能体在产出中自称其他供应商（vendor）或模型（如 #004 实证 DeepSeek/Gemini 互换身份，或在 thinking 模式下加剧身份误判），表明自我认知或上下文管理出现问题。
*   **触发动作**：识别到上述任一信号，即触发“逻辑不可用”判定。此时，智能体应被视为与“物理不可用”（API 报错/超时）同等，并根据 M-004 规定回退用户或触发降级流程。

§D 外部事实验证纪律（承接 MC-2 + #002）

明确规定智能体在涉及易变外部事实时的验证纪律，防止信息过时或失真：

*   **AI 模型 / 工具版本 / API endpoint / model ID 等易变事实必须 WebSearch / 官方来源验证**：智能体在引用或使用任何 AI 模型、工具的版本、API 端点或模型 ID 等信息时，必须通过 WebSearch 或查阅官方渠道进行实时验证（如 #002 裁决）。不允许依赖模型自身的训练记忆，因为训练截止日期与现实时间存在天然滞后。
*   **异源训练谱系判断须基于厂商公开声明，不依赖智能体自我宣称**：在判断异源智能体的独立性时，其训练谱系信息必须基于厂商的官方公开声明，不应采信智能体自身的“自我宣称”（如 #004 实证 DeepSeek/Gemini 互换身份）。
*   `docs/tech/reference/agent-cli-models.md` 30 天刷新机制的具体触发条件 + 失效处理路径：
    *   **触发条件**：当 M-001 工作流启动多家任务时，主笔应验证当前各家模型 ID 与可用性，并检查 `agent-cli-models.md` 的 `max_age_days`（30 天）是否过期。
    *   **失效处理路径**：若文件过期或验证失败，则应立即触发刷新机制，更新该文档内容，并在更新完成前，任何依赖该文档进行决策的流程（如判断模型异源性）应被暂停或回退。

§E 目的优先原则的古德哈特防御（承接 M-000 v2.0 §9 + #009 R6）

基于 M-000 §9 的“目的优先原则”，本节提供判据以防御“古德哈特定律”（指标反向塑形），确保规则或指标服务于最终目的，而非成为被优化的对象：

*   **形式 vs 目的的判据**：
    *   **什么是“形式削弱目的”？** 指当遵守某项形式规则（例如字数限制、固定流程、特定check）反而导致可靠性、可追溯性、独立性或用户裁决权受损时，该形式即削弱了目的。
    *   **如何识别？** 当智能体或审查者发现为了满足形式要求，而不得不牺牲信息密度、省略关键论证、或规避必要验证时，即是形式削弱目的的信号。
*   **指标反向塑形检测**：
    *   **何时一个度量 / check 已成为优化对象而非诊断信号？** 当智能体或协作方开始“为了通过 check 而调整产出”，而非“产出自然符合 check 标准”时，该 check 已被反向塑形。例如，智能体为满足字数限制而增加冗余信息，或为通过某种形式检查而牺牲工程兼容性。
*   **历史实证案例索引**：
    *   **#006 Round 1 Boot 序列重构 + 异源 sanity check 价值实证**：同源激进方案（删除 `workflow` / `STATUS`）被异源（DeepSeek+Gemini）否决，证明形式（流程简化）不能削弱目的（独立判断的可靠性）。
    *   **#007 ADR-004/005 异源评估 + 激进拆分 + 盲点识别批量入库**：用户接受了异源激进拆分方案（物理切出 findings），而非同源保守方案（只加 banner），实证了形式（ADR 结构简化）应服务于目的（信息清晰度与盲点识别）。
    *   **#008 Round 2 sanity check 撤回 R1 STATUS_ENUM 修改（工程兼容性优先）**：Gemini 基于“工程兼容性优先于元数据美学”的原则，撤回了自己 Round 1 的判断，证明即使是 sanity check 的结论，也必须允许被目的（下游脚本消费的稳健性）反向校正。

§F 自反性 sanity check 原则（承接 #008 实证）

定义审计机制本身的自我复盘要求，确保 sanity check 自身不成为僵化的形式：

*   **Round N → Round N-1 复盘 prompt 设计**：在进行 Round N 的 sanity check 时，应设计提示词引导审查者复盘“自己先前在 Round N-1 轮次中提出的反馈是否仍然正确”。此机制旨在触发 reviewer 撤回自己先前判断（如 #008 中 Gemini 撤回 R1 状态修改），防止“应声虫”行为。
*   **sanity check 不是终审**：异源 sanity check 共识即使达成，也可被后续更深入的 sanity check 基于第一性原理或新证据而撤回（如 #008）。这强调了审计的持续演进性和动态性，而非一次性结论。
*   **工程兼容性 vs 元数据美学**：当下游脚本 / 工具的消费端兼容性与元数据语义的纯粹性发生冲突时，应优先保障工程兼容性。元数据设计应避免引入导致下游工具链破裂的复杂性或歧义（如 #008 中 `partially_superseded` 状态的撤回，以避免下游脚本误过滤）。

§G Docaudit Check 的设计原则（承接 M-000 v2.0 §8）

M-005 不重复 M-000 v2.0 §8 中已列出的 6 项核心 check，而是提供设计原则，指导未来 `docaudit` check 的演进与维护：

*   **每个 check 必须有真实事故来源或风险模型，否则视为可选**：任何新的 `docaudit` check 都必须能够追溯到一个实际发生的故障、错误或可识别的潜在风险。没有明确来源或风险模型支持的 check，即使有潜在价值，也只能保留为可选（optional），不得进入核心阻塞门。
*   **核心 check 进入阻塞门的判据**：
    *   **最高频触发**：该 check 所防范的问题在历史记录中反复出现，且对协作可靠性造成显著影响。
    *   **不可机械绕过**：该 check 无法被智能体通过简单的形式操作（如代码注释、空字符串填充）而绕过，其检测必须触及问题本质。
*   **可选 check 的存在价值**：
    *   **实验性质**：用于探索新的潜在风险或质量维度。
    *   **低频但高代价**：所防范的问题发生频率较低，但一旦发生将造成严重后果。
    *   **依赖人工裁决**：部分 check 涉及高度语义理解，难以完全自动化，需依赖人工审计判断。
*   **新增 check 的提案流程**：任何新增 `docaudit` check 的提案，应首先作为可选 check 进行验证。提案需详细说明其事故来源/风险模型、预期效益、误报率分析、以及是否可自动化。当其满足核心 check 的判据并通过实证后，方可提案升级为核心 check。

§H 「主笔轮换」机制（承接本任务 #012 自身）

定义元规则起草中主笔轮换的原则，以规避单方长期主笔带来的风险，确保异源独立性：

*   **连续同源主笔的风险累积**：长期由同一源（同厂商、同模型）智能体担任主笔会累积结构性同源风险，可能导致盲点、偏见固化，并削弱异源审计的价值。#004 实证 DeepSeek/Gemini 互换身份，以及 #012 指出 v2.0 主笔在 `thinking` 模式下身份误识别加剧，都表明连续主笔可能导致身份混淆和训练数据泄露，降低协作产出的客观性。
*   **主笔候选裁决的物理隔离要求**：即使是主笔收到的用户裁决（如私下 Overrule ），也必须在主分支 `user-decision-log` 同步落档。若主笔收到用户私下 Overrule 但其他参与方上下文未见，将触发 sanity check（如 #010 所示），表明物理隔离纪律在主笔环节也需保留信号传递路径，避免信息不对称。
*   **主笔不是独享特权**：在多方 `sign-off` 过程中，若 3 家异源参与方中任一家给出 `BLOCK` 信号，即使是主笔的产出也必须回炉修订，不允许主笔特权压制异源反对意见。

§I 「自作主张越权」防线（承接 #005 + #010）

定义“结构性决定必须显式批准”的具体范围，防止智能体在未经授权的情况下修改关键结构或流程：

*   **定义“结构性决定必须显式批准”的具体范围**：以下行为属于“结构性决定”，必须获得用户显式批准，不能由智能体自作主张：
    *   **归档路径**：未经用户指定或批准，擅自选择文件归档目录（如 #005 Claude 违纪）。
    *   **目录重命名**：任何对现有目录名称的修改。
    *   **跨目录文件移动**：将文件从一个目录移动到另一个目录，即使内容未变。
    *   **批量 `frontmatter` 修改**：对多个文件的 `frontmatter` 字段进行批量修改，尤其是涉及 `layer`、`scope`、`status` 等元层级字段。
    *   **其他对项目结构、生命周期或元层级元数据有实质影响的变更**。
*   **私下授权 vs 主分支可见性**：当主笔智能体收到用户私下（未在主分支 `user-decision-log` 中记录）的 `Overrule` 或授权时，主笔**必须**在主分支的 `user-decision-log` 中同步落档该决策。若未同步，其他参与方在 `sanity check` 时若发现此信息不对称，将触发 `sanity check`，视为违反纪律（如 #010 所示）。
*   **误触发 vs 真违纪的辨别**：为了避免对合规授权产生噪声，当 `sanity check` 机制识别到潜在的“越权”行为时，首先应检查 `user-decision-log` 中是否存在对应的显式授权记录。只有在缺乏明确授权记录的情况下，才能判定为真违纪。

§J 正向质量判据（不预设字数上限）（承接 #010 字数原则升级）

本节正式承载 #010 裁决所要求的字数原则升级，明确“信息密度决定字数”的核心原则，并指导 `override_rationale` 的编写与冗余检测：

*   **核心原则：信息密度决定字数，不预设上限**：元规则文档的长度不应受预设字数上限的束缚。其唯一决定因素是承载所需信息所需的密度。每一段文字的存在都必须是必要的，且无法进一步下沉、压缩或省略（如 #010 裁决用户显式 Overrule 3000-3500 nwc 目标，要求按第一性原理起草）。
*   **`override_rationale` 的正向作用**：
    *   `override_rationale` 不再是“破例”或“超预算”的说明，而是一种“密度证明”。文档作者必须在其中论证当前文档的长度和信息密度是合理的，每一段都不能下沉、不能压缩、不能省略的具体理由。
    *   其目的是促使作者在起草时进行深度思考和自我批判，确保文档的每一部分都具有不可替代的价值。
*   **冗余检测信号**：以下信号表明文档可能存在冗余，需要精简：
    *   **重复定义**：同一概念在文档内或元规则体系内被重复定义，未遵循“一处权威定义”原则。
    *   **可下沉段落**：内容属于执行步骤、模板、例子、命令或检查脚本，本应下沉到 M-001~M-006、standards、skills、ADR、STATUS stub 或工具。
    *   **装饰性论证**：为填充字数或形式美观而加入的、不提供实质信息增量的描述或论证。
    *   **形式合规但实质空洞**：产出形式上符合规则，但内容缺乏实质深度、可操作性或与目的的关联性。
*   **同 PR 落地路径**：
    *   M-005 `ratify` 时，将通过同一 PR 修订 M-000 v2.0 §6 和 `frontmatter`。
    *   具体修订包括：删除 `default_word_budget: 2500` 字段，并将措辞改为“无预设字数上限，由 `override_rationale` 单独承载密度证明”。
    *   同时，此 PR 将在 `user-decision-log`（预 #013）中显式 `Overrule` #009 R2 裁决中关于“`default_word_budget` 字段保留”的处理方式，完成字数原则的最终升级。此举旨在解决 #012 裁决中提到的“认知一致性”问题，避免 M-005 §E/§J 的论证与 M-000 §6 长期不同步。

§K 修订与复审

M-005 的修订与复审遵循 M-000 的通用规则。任何修订都必须说明触发原因、对 `user-decision-log` 的影响，以及是否 `Overrule` 历史裁决。根据 `freshness.max_age_days`（180 天）或当 `decay_trigger`（`meta_audit`、`downstream_rules_drafted`、`external_shock`）被触发时，M-005 将进行复审，以确保其判据和检测机制仍能有效服务于项目目的。
