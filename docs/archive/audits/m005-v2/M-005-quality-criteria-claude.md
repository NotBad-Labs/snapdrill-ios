# M-005 质量判据与退化检测

> M-005 给"什么是合格元规则产出 / 什么是退化"提供可操作判据。它不规定流程（M-001 / M-002）、不规定降级路径（M-004）、不规定数据治理（M-006），但所有这些规则在裁决"产出是否可信"时回到 M-005。

## §1 定位与适用范围

M-005 服务一个具体问题：**多方协作时，怎么知道某次产出是真共识、伪共识，还是退化产物**。它不是流程书、不是降级手册，也不是 docaudit check 的全量清单。它只回答：

- 什么样的判据可被消费方机械引用而不需要再问主笔
- 什么样的信号触发"逻辑不可用 → 回退用户"
- 什么样的指标已经反向塑形了产出本身（古德哈特）
- 什么样的 sanity check 不再可信（自反性失效）

M-005 适用范围：所有受 M-000 v2.0 §3 默认多方异源约束的产出（含 M-000 / M-001~M-006 元规则起草、ADR 提案、第一性原理审计、cross-audit 报告、code review 共识、规模化文档变更）。M-005 不约束「单方执行窗口」内的低风险机械操作（具体豁免清单由 M-001 定义）。

M-005 与 M-002 的关系：M-005 给判据（什么算"质量合格"、什么算"退化"），M-002 给流程（裁决怎么走、Overrule 怎么写、撤回怎么记）。M-005 不抢 M-002 的流程职能；当两者表述冲突时，M-002 走流程、M-005 走判据，由用户裁决合并写法。

## §2 与 M-000 PRIMARY 内核的接口

M-000 v2.0 §2 列出 P1~P8 PRIMARY 内核。M-005 各章与 PRIMARY 的对接如下：

| M-005 章 | 主对接 PRIMARY | 接口角色 |
|---|---|---|
| §A 产出度量 | P1（相同完整任务） | 判定一份产出是否构成"完整任务"产出，而非分工式切片 |
| §B 伪共识识别 | P3（默认多方异源）+ P4（同源警告） | 给 P4 同源警告提供可执行的触发信号 |
| §C 静默退化 | P3 + P4 | 给 M-000 v2.0 §4.3 「不可用」定义补"逻辑不可用"分支 |
| §D 外部事实验证 | P3 + P4 | 把 user-decision-log [#002](user-decision-log.md#002-ai-模型工具版本信息一律-websearch-验证) WebSearch 纪律提升为质量判据 |
| §E 古德哈特防御 | P6（sanity check 自反性）+ M-000 §9（目的优先） | 监测指标本身的反向塑形 |
| §F 自反性 sanity check | P6 | 给 P6 提供可执行的"复盘上一轮"prompt 设计 |
| §G docaudit check 设计 | 全 P1~P8（机器入口） | 限制 docaudit 自身膨胀，防 check 数量增长不带来收益 |
| §H 主笔轮换 | P1（相同完整任务） | 防"主笔即特权"的同源累积 |
| §I 自作主张越权防线 | P2（用户裁决权） | 给 P2 划清"什么算结构性决定必须显式批准" |
| §J 正向质量判据 | M-000 §6（字数预算）+ §9（目的优先） | 把 [#010](user-decision-log.md#010-m-000-v20-final-候选追认--字数上限第一性原理升级待-m-005-处理-status_enum-加-draft) 字数原则升级落到 M-000 §6 + frontmatter |

M-005 不重述 P1~P8 内容；引用时直接用 P 编号 + 章节锚点。

## §3 与 M-001/M-002/M-004/M-006 的分工边界

M-005 给"质量判据 / 退化信号"，下游派生规则各自给具体流程。明确分工：

| 议题 | M-005 给 | 下游给 |
|---|---|---|
| 主笔轮换 | §H 轮换原则 + 同源累积识别信号 | M-001 给具体轮换流程 + 提名 + 撤换路径 |
| 双核同意适用域 | §A.4 + §C 判定"普通可逆低副作用"的可机械信号 | M-002 给适用域熔断条件与例外清单 |
| Overrule 写法 | §F 自反性可撤回原则 | M-002 给 Overrule 字段结构 + 撤回链条记录 |
| 静默退化处理 | §C 识别信号 + 触发判定 | M-004 给「逻辑不可用」时的降级路径（同物理不可用回退用户） |
| 异源否决权阈值 | §B.3 强反对的客观判据 + 否决率监测 | M-002 给"连续触发率超阈值"的用户介入流程 |
| Prompt injection 防御 | §C.5 输出污染识别信号 | M-006 给具体防御技术 + 跨厂商共享脱敏边界 |
| 主笔自作主张 | §I 结构性决定清单 + 主分支可见性要求 | M-002 给"未授权自作主张"的事后追认或废弃流程 |

边界冲突时按 M-000 v2.0 §9 目的优先：若 M-005 判据与 M-002 流程冲突，先保护"可识别 / 可追溯 / 可裁决"目的，再调和文本。

## §A 产出度量

「合格元规则产出」必须同时满足以下 5 项可机械检查指标。任一不满足，消费方有权拒绝引用并要求回炉。

### §A.1 可追溯到证据

每条规则、判据、阈值、清单必须能回到下列至少一项：
- 一条具体 user-decision-log 编号（#NNN）
- 一份具体 docs/audits/ 报告路径
- 一段第一性原理论证（不引用其他智能体结论作为"权威"，必须自洽）
- 一个外部公开事实（厂商声明 / API 文档 / 测试数据）

不允许"按惯例 / 历史经验 / 通常做法"等模糊指代。**实证**：[#003](user-decision-log.md#003-字数计量单位精化b-方案non-whitespace--代码块独立--译本乘数) Gemini 引入"古德哈特定律"作为字数单位裁决依据，明确来源于经济学公开概念；这是合格证据；若仅说"经济学常识"则不合格。

### §A.2 可验伪的违反信号

每条规则必须给出"什么样的产出/行为构成违反"的可识别信号：
- 不允许"应当 / 务必 / 力求"等无判据的规范性表述
- 必须给"违反信号 → 触发动作"的双段式表述

**反例**：v1.2 §7.3「服务发生重大或持续性变化时，自动触发 M-000 review」——"自动触发"无可识别信号且无监控基础设施，[#011](user-decision-log.md#011-m-000-v20-ratified--v12-归档) backlog MC-7 已指出此项实质为手动；v2.0 §10 已修订为"应触发"+ 列出触发条件清单。

### §A.3 下沉证明

每条规则必须显式说明"为什么不能下沉到 M-001~M-006 / standards / skills / ADR / STATUS stub / 工具"。下沉证明至少包含：
- 该规则是否被多个下游消费——若只被一个消费方使用，应下沉到该消费方
- 该规则是否随技术栈变化——若是，应下沉到 standards 或 skills
- 该规则是否是裁决执行细节——若是，应下沉到 M-002

**实证**：M-000 v2.0 §6「新增条款必须先证明无法下沉」就是 §A.3 的元层表述；M-005 §H 主笔轮换原则不下沉到 M-001 流程，因为它是"防同源累积"的判据本身，M-001 只消费判据不重写。

### §A.4 目的关联

每条规则必须显式指向 M-000 P1~P8 中至少一项 PRIMARY 内核，或与产品愿景（"练习题数字化效率工具"）直接对接。无 PRIMARY 关联的规则视为"装饰性"，应下沉或删除。

### §A.5 可机械检查的最小子集

§A.1~§A.4 中至少有一项必须可被 docaudit / validate_frontmatter 等工具机械检查。完全依赖人类阅读的规则视为"提示性"，不进入阻塞门。

**实证**：M-000 v2.0 §8 已列 6 项 core check，每项都对应可机械检查的 frontmatter / link / verdict / freshness 字段。

## §B 伪共识识别

**伪共识**：表面上多方一致、实际上由同源驱动、同源污染、辅助方沉默或单方逼迫产生的"非独立趋同"。

### §B.1 触发信号清单

以下任一信号出现时，多方一致结果**不构成强证据**，必须升级用户裁决：

1. **同主笔系列**：连续 ≥3 版主笔为同一 vendor（**实证**：M-000 v1.0/v1.1/v1.2/v2.0 final 主笔连续 4 版 Codex，[#012](user-decision-log.md#012-m-005-起草启动--主笔轮换-deepseek--010-字数升级同-pr-落地) 触发轮换）
2. **同 vendor 多实例**：审计参与方中 ≥2 家来自同一厂商（如同时 Claude Sonnet + Claude Opus）
3. **训练 cutoff 相近**：参与方训练截止日期相差 <90 天，且议题涉及该时间窗内的新知识
4. **提示词渗透**：任务定义书含"参考某家结论 / 借鉴某方案 / 在 X 基础上"等锚点
5. **辅助方沉默**：在指定回应窗口（M-001 定义）内未明确表态，等同未参与（[#011](user-decision-log.md#011-m-000-v20-ratified--v12-归档) 已确立）
6. **物理隔离失效**：worktree 之间共享 git 历史 / Claude.md / IDE 缓存，且产物结构高度同构
7. **同源激进**：Claude+Codex 同向激进方案被 DeepSeek+Gemini 同向反对（[#006](user-decision-log.md#006-round-1-boot-序列重构--异源-sanity-check-价值实证) / [#007](user-decision-log.md#007-adr-004005-异源评估--激进拆分--盲点识别批量入库) 实证）

任一信号触发 → 进入 §B.2 升级流程。

### §B.2 升级流程

触发 §B.1 信号后：
1. 主笔在产出 frontmatter 显式记录信号编号（如 `pseudo_consensus_flags: [B1.1, B1.4]`）
2. 主分支 user-decision-log append 一条"伪共识警示"记录（不阻断推进，但要求用户裁决前显式确认）
3. 用户裁决前禁止合并到主分支 active 文件
4. 若用户裁决确认伪共识，产物回炉重起草（不是修订）

### §B.3 强反对的客观判据（防否决权滥用）

承接 backlog MC-10。"异源辅助方强反对"必须满足以下 ≥1 项才触发用户裁决，否则视为普通反对意见进入折叠段：

- **引用具体事实错误**：能指出产出中某段事实陈述的具体错误来源（带 URL / 公开数据 / 测试结果）
- **可证伪的反假设**：提出与产出相反的具体假设，并给出可验证路径
- **明确风险路径**：指出"按当前产出执行会触发的具体不可逆风险"的因果链

不构成强反对的：
- "我感觉不对"、"风格不喜欢"、"看起来不够严谨"
- 仅指出修辞瑕疵 / 错别字 / 章节顺序
- 无具体依据的方向性质疑

### §B.4 否决率监测

任一辅助方在 24 小时窗口内触发强反对升级 ≥5 次，自动触发"辅助方退化或滥用否决权"复审（M-002 定义具体流程）。监测数据由 user-decision-log 编号 + 时间戳得出，不依赖单独日志。

## §C 静默退化识别（承接 backlog MC-1）

**静默退化**：智能体在物理可用（API 返回 200 / 工具不报错）的情况下，输出逻辑不可用（无法承担当前任务）。

### §C.1 退化信号清单

智能体输出出现以下任一信号 → 触发"逻辑不可用"判定：

| 信号 | 识别方法 | 历史实证 |
|---|---|---|
| **格式崩溃** | frontmatter 残缺 / 章节标题缺失 / 表格语法错位 / 代码块未闭合 | commit 7487cf80 修复 Gemini v2 草案被 ```yaml...``` 包裹的事故 |
| **自相矛盾** | 同一产出内不同段落给出对立结论 | [#008](user-decision-log.md#008-round-2-sanity-check-撤回-r1-status_enum-修改-工程兼容性优先) Round 2 撤回 Round 1 自己共识时显式声明 |
| **偏离任务** | 输出主题与任务定义书显著不符（如任务问 A 答 B） | M-000 v1.0 起草中曾出现"扩展超范围"被异源指出 |
| **身份误识别** | 自称其他 vendor / 其他模型 / 不存在的版本 | [#004](user-decision-log.md#004-m-000-v12-四家最终-sign-off-ratified) DeepSeek/Gemini 互换身份；thinking 模式下加剧 |
| **训练记忆漂移** | 引用不存在的 API / 不存在的命令 / 已下线的工具 | [#002](user-decision-log.md#002-ai-模型工具版本信息一律-websearch-验证) Claude 误判 Gemini 3.5 不存在 |
| **过度自信** | 对易变事实（模型版本 / API endpoint）下断言不带任何外部验证 | [#002](user-decision-log.md#002-ai-模型工具版本信息一律-websearch-验证) 训练 cutoff 与现实 gap |

### §C.2 触发动作

任一 §C.1 信号出现 → 立即视为"逻辑不可用"，**等同物理不可用**：
- 双核同意域内的智能体逻辑不可用 → 双核同意权失效（同 M-000 v2.0 §5）
- 主笔逻辑不可用 → 产物作废，回到 P3 折叠重选主笔（[#012](user-decision-log.md#012-m-005-起草启动--主笔轮换-deepseek--010-字数升级同-pr-落地) 已确立主笔可换原则）
- 辅助方逻辑不可用 → 该方意见在本轮裁决中不计权重，但保留为 §B 伪共识识别的数据点

### §C.3 适用范围（承接 backlog MC-1）

双核「不可用」定义在本 §C.2 后涵盖：
- 物理不可用：API 报错 / 超时 / quota 限制
- 逻辑不可用：§C.1 任一信号

两者在 M-000 v2.0 §5 + M-002 的「双核同意权失效」条款下同等处理。

### §C.4 适用范围限定

§C 仅覆盖"普通、可逆、低外部副作用"事项。涉及不可逆操作 / 跨边界 / 元规则修改 / 法律财务风险 / 产品方向时，无论 §C 是否触发，均按 M-000 v2.0 §5 升级用户裁决。

### §C.5 输出污染识别（prompt injection / 上下文污染）

智能体输出含以下信号 → 触发"输入污染"嫌疑：
- 突然引用任务定义书中未出现的具体路径 / 编号 / 决策
- 输出风格断裂（前后段语言风格 / 立场显著切换）
- 自我引用未发生的对话（"如你之前所说" 但实际无此对话）
- 拒绝任务但理由含明显非任务相关内容

触发动作：保留产物作为 M-006 prompt injection 防御的实证案例，但本轮裁决不采纳该方意见，并触发 M-006 复审。

## §D 外部事实验证纪律（承接 backlog MC-2）

承接 [#002](user-decision-log.md#002-ai-模型工具版本信息一律-websearch-验证) 已确立的 WebSearch 验证纪律，升格为质量判据。

### §D.1 必须 WebSearch 验证的事实类型

智能体在产出中陈述以下任一类型事实，必须 WebSearch / 官方来源验证，不得依赖训练记忆：

1. **AI 模型版本 / API endpoint / model ID 是否存在 / 何时发布**
2. **第三方工具 / CLI 当前版本号 / 命令行接口**
3. **服务价格 / 配额 / 可用区**
4. **法规 / 标准的当前生效版本**（如 GDPR 修订、Apple HIG 章节）
5. **任何带具体日期 / 数字的外部事实**

不需要验证：
- 项目内部裁决与文档（这些是仓库内事实，git history 即权威）
- 第一性原理论证（不依赖外部事实）
- 编程语言核心语法 / 标准库 API（训练 cutoff 内稳定）

### §D.2 验证留痕

WebSearch 验证结果必须以下列任一形式留痕：
- frontmatter `external_refs: [<url>, <url>]`
- 正文 inline 引用 `<source: url, fetched: YYYY-MM-DD>`
- 提交至 `docs/tech/reference/agent-cli-models.md`（30 天刷新机制）

无留痕的外部事实陈述视为 §C.1 训练记忆漂移信号。

### §D.3 异源训练谱系判断（承接 backlog MC-2）

§B.1.2 "同 vendor 多实例" 与 §B.1.3 "训练 cutoff 相近" 的判断必须基于厂商公开声明，不依赖智能体自我宣称。**实证**：[#004](user-decision-log.md#004-m-000-v12-四家最终-sign-off-ratified) DeepSeek 自称"Gemini 2.5 Pro"，Gemini 自称"Claude 3.5 Sonnet"——自我宣称在 thinking 模式下尤其不可信。

异源判断数据来源固定到 `docs/tech/reference/agent-cli-models.md`（max_age_days: 30 强制刷新）。该文件失效时，启动新审计前必须先刷新该文件。

## §E 古德哈特防御（目的优先原则的指标反向塑形监测）

承接 M-000 v2.0 §9 + [#009](user-decision-log.md#009-m-000-第一性原理审计--7-红旗接受改造--3-primary--3-分歧全保留--启动-v20-起草) R6。「目的优先原则」原名"古德哈特防御"，机制保留。

### §E.1 形式 vs 目的的判据

判断一项指标 / check / 流程已经成为"被优化对象"而非"诊断信号"：

| 信号 | 含义 |
|---|---|
| 产出在指标边界附近聚集 | 字数刚好压到 2499 / check 刚好通过 / 拒绝率刚好低于阈值 |

## §F 自反性 sanity check 原则（承接 P6 + [#008](user-decision-log.md#008-round-2-sanity-check-撤回-r1-status_enum-修改-工程兼容性优先) 实证）

sanity check 不是"终审"——它本身也可被后续 sanity check 撤回。

### §F.1 自反性 prompt 设计

sanity check 启动 Round N 时，必须在任务定义书显式包含"复盘 Round N-1 反馈"提示词：

> "请复盘 Round N-1 sanity check 中你（或同方）提出的反馈。逐条评估：(1) 当前的产物是否已落实；(2) Round N-1 反馈本身是否仍然正确；(3) 是否需要撤回 / 修订 Round N-1 反馈。撤回理由必须基于第一性原理或新证据，不得仅凭"想法变了"。"

**实证**：[#008](user-decision-log.md#008-round-2-sanity-check-撤回-r1-status_enum-修改-工程兼容性优先) Gemini Round 2 撤回 Round 1 自己共识的 R1 STATUS_ENUM 修改建议，撤回理由是"status 二元生命周期 + 下游脚本兼容"——基于第一性原理的撤回，是 §F 的标准实证。

### §F.2 sanity check 不是终审

异源 sanity check 共识 ≠ 最终裁决。在以下情况下，sanity check 结论仍可被后续 sanity check 推翻：

- 工程兼容性 vs 元数据美学冲突（[#008](user-decision-log.md#008-round-2-sanity-check-撤回-r1-status_enum-修改-工程兼容性优先) 实证）
- 第一性原理审计识别"sanity check 自身基于 ANALOGY 而非 PRIMARY"
- 新外部事实出现（如模型升级 / 工具变化）

最终裁决仍由用户行使（M-000 v2.0 §5 P2 PRIMARY）。

### §F.3 工程兼容性优先原则

当 sanity check 结论与下游脚本 / 工具 / CI 兼容性冲突时，**工程兼容性优先**。理由：元数据美学的代价是"读起来不爽"，工程兼容性失效的代价是"下游脚本静默错过审计"。

**实证**：[#008](user-decision-log.md#008-round-2-sanity-check-撤回-r1-status_enum-修改-工程兼容性优先) 拒绝把 `status: partially_superseded` 写入 frontmatter，改用 `status: active` + 侧通道字段 `supersession_status: partially_superseded`——纯粹是为了下游消费 `active` 的脚本不误过滤。

### §F.4 与 M-002 的衔接

§F 给"sanity check 自身可撤回"的原则；M-002 给"撤回怎么写、撤回链条怎么记、撤回如何级联到下游"的具体流程。两者不重复。

## §G docaudit check 设计原则

承接 M-000 v2.0 §8。M-005 不重复 §8 已列的 6 项 core check，而是给出**新增 check 的设计原则**——防止 docaudit 自身膨胀。

### §G.1 core check 必备条件

进入 docaudit core 阻塞门的 check 必须同时满足：

1. **真实事故来源或风险模型**：能指向一次 user-decision-log 事故，或可证明的风险路径（[#008](user-decision-log.md#008-round-2-sanity-check-撤回-r1-status_enum-修改-工程兼容性优先) 证明 frontmatter 语义影响下游消费——这是 core check 的合格事故来源）
2. **高频触发**：在过去 ≥30 天内 ≥3 次因此 check 抓出真实问题
3. **不可机械绕过**：检测项不能通过简单字符串替换绕过

不满足任一项 → 视为可选 check（实验、低频、依赖人工裁决），不进入阻塞门。

### §G.2 可选 check 的存在价值

可选 check 不代表无价值，它的存在用于：
- 实验：观察是否值得升核心
- 低频但高代价：某类 bug 罕见但发生时破坏性大
- 依赖人工裁决：机械检查能给信号但需要人判定

可选 check 不进入 preflight hook 阻塞门，只在显式调用时报告。

### §G.3 从可选升级为核心的提案流程

提案路径：
1. 在 docs/audits/ 起一份升级提案（含 §G.1 三项满足证据）
2. 异源 sanity check 至少 1 家确认（防自我升格）
3. 用户裁决（不可由智能体单方升格）
4. 升级生效后落 user-decision-log

### §G.4 反向：从核心降级为可选

任一项已在 core 但 ≥90 天未触发任何真实问题 → 触发"core 降级嫌疑"评估，按 §E.2 指标复审流程处理。

## §H 主笔轮换机制

承接 [#012](user-decision-log.md#012-m-005-起草启动--主笔轮换-deepseek--010-字数升级同-pr-落地) + M-000 v1.0/v1.1/v1.2/v2.0 主笔均 Codex 的同源累积实证。

### §H.1 同源累积识别信号

任一信号出现 → 触发主笔轮换审议：

1. **连续 ≥3 版同 vendor 主笔**（M-000 v1.0/v1.1/v1.2 = 3 版 Codex 时已应触发；实际 v2.0 触发延后到 [#012](user-decision-log.md#012-m-005-起草启动--主笔轮换-deepseek--010-字数升级同-pr-落地)）
2. **同 vendor 主笔产物中累计 ≥5 项硬伤被异源 sanity check 抓出**（即使每次单独看可接受）
3. **主笔风格反向塑形折叠 prompt**：折叠任务书出现"沿用 X 主笔风格 / 保留 X 主笔结构"等锚点
4. **主笔在 §C 任一信号上出现 ≥2 次实证记录**

### §H.2 轮换流程

§H.1 触发后：
1. 主笔候选提名（异源 sanity check 中表现稳定 / 该领域题材匹配的家）
2. 用户裁决候选（不可由智能体单方决定）
3. 旧主笔转辅助 reviewer（不强制退出，避免知识断层）
4. 落 user-decision-log（[#012](user-decision-log.md#012-m-005-起草启动--主笔轮换-deepseek--010-字数升级同-pr-落地) 体例）

### §H.3 主笔不是独享特权

3 家 sign-off 中任一家 BLOCK → 主笔产出回炉。BLOCK 必须满足 §B.3 强反对的客观判据，否则降格为 CONDITIONAL（不阻塞但记录）。

### §H.4 主笔轮换与同 PR 修订的衔接

主笔轮换发生时，若同 PR 涉及元规则修订（如本轮 M-005 ratify 同 PR 修订 M-000 §6 + frontmatter），新主笔有权重写修订条款，但必须显式 Overrule 旧主笔的对应条款（M-002 流程）。

## §I 自作主张越权防线（承接 [#005](user-decision-log.md#005-docsmeta-归档治理--归档路径用户显式批准) + [#010](user-decision-log.md#010-m-000-v20-final-候选追认--字数上限第一性原理升级待-m-005-处理-status_enum-加-draft)）

### §I.1 结构性决定清单（必须显式用户批准）

智能体在以下场景**禁止**自作主张，必须显式提交用户批准：

| 决定类型 | 实证 |
|---|---|
| 归档路径选择 / 目录创建 | [#005](user-decision-log.md#005-docsmeta-归档治理--归档路径用户显式批准) Claude 自作主张归档路径 |
| 跨目录文件移动 | [#005](user-decision-log.md#005-docsmeta-归档治理--归档路径用户显式批准) docs/ 重组 |
| 批量 frontmatter 修改 | [#011](user-decision-log.md#011-m-000-v20-ratified--v12-归档) 级联引用更新延后裁决 |
| 元规则文本修订 | M-000 v2.0 ratify 流程 |
| 主笔轮换 | [#012](user-decision-log.md#012-m-005-起草启动--主笔轮换-deepseek--010-字数升级同-pr-落地) Q2 |
| Sprint Contract 范围扩展 | [#012](user-decision-log.md#012-m-005-起草启动--主笔轮换-deepseek--010-字数升级同-pr-落地) Q1 |

不需要显式批准的（智能体提案权范围内）：
- 单文件内的内容修改（不动 frontmatter 关键字段、不跨目录）
- 添加新的 user-decision-log 条目（这本身就是裁决记录的提案，但裁决内容由用户）
- 在已批准的 Sprint Contract 范围内的执行步骤

### §I.2 主分支可见性要求（承接 [#010](user-decision-log.md#010-m-000-v20-final-候选追认--字数上限第一性原理升级待-m-005-处理-status_enum-加-draft) 实证）

智能体（特别是主笔）收到用户**私下授权 / Overrule** 时，必须在主分支 user-decision-log 同步落档，否则其他参与方（特别是中立主笔 / sanity check 方）触发"自作主张嫌疑"。

**实证**：[#010](user-decision-log.md#010-m-000-v20-final-候选追认--字数上限第一性原理升级待-m-005-处理-status_enum-加-draft) Codex 收到帅哥私下 Overrule 字数目标（不压缩到 3000-3500 nwc），Codex 在 worktree 内合规执行，但 Claude 主分支未见私下对话内容，sanity check 触发。事后帅哥显式确认是合规授权，但**主分支可见性缺失**本身是流程瑕疵。

### §I.3 误触发 vs 真违纪的辨别

§I 触发"嫌疑"后，辨别路径：
- 用户事后追认 + 行为本身合规 → 误触发，不进入违纪记录，但要求未来主分支同步落档
- 用户事后追认 + 行为本身不合规（如归档路径选择实际未经批准）→ 进入"治理失误"记录，要求方法论复盘（[#005](user-decision-log.md#005-docsmeta-归档治理--归档路径用户显式批准) 体例）
- 用户事后撤回 + Overrule → 进入 [#005](user-decision-log.md#005-docsmeta-归档治理--归档路径用户显式批准) 体例处置

避免对合规授权产生过度噪声：嫌疑触发 → 用户裁决 → 不留违纪记录除非确认违规。

### §I.4 与 M-002 的衔接

§I 给"什么算结构性决定 + 主分支可见性要求"的判据；M-002 给"未授权自作主张的事后追认 / 废弃流程"。两者不重复。

## §J 正向质量判据 + 字数原则升级

承接 [#010](user-decision-log.md#010-m-000-v20-final-候选追认--字数上限第一性原理升级待-m-005-处理-status_enum-加-draft) 预声明 + [#012](user-decision-log.md#012-m-005-起草启动--主笔轮换-deepseek--010-字数升级同-pr-落地) Q3 同 PR 落地裁决。

### §J.1 核心原则：信息密度决定字数，不预设上限

文档字数由信息密度决定，不预设上限。"密度"判据：
- 每段都不能下沉到下游（standards / skills / ADR）
- 每段都不能压缩到更少字数而保留同等论证强度
- 每段都不能省略而不影响消费方理解

**实证**：[#001](user-decision-log.md#001-字数硬上限-1500-字--2000-字) 1500 → 2000 字调整理由就是"客观规律不以人的意志为转移。如果完整理念无法压缩到 1500 字以内，那么 1500 字上限本身就是错误的决定"——这是 §J.1 的最初实证表述。

### §J.2 override_rationale 的正向作用

`override_rationale` frontmatter 字段不是"破例的歉意书"，而是"密度的证明"：
- 必须列出本文每段不能下沉的理由
- 必须列出本文每段不能压缩的理由
- 必须给出"何时复审"的触发条件（如下游派生稳定后是否可下沉）

**反例**：仅写"内容较多需要详细说明"——这是无密度证明的 override，应回炉补论证。

### §J.3 冗余检测信号（与 §J.1 互补）

文档出现以下任一信号 → 触发"密度不足"嫌疑：
- 相同概念在不同段落定义 2 次以上
- 段落只重述上文 / 提供"装饰性论证"而无新判据
- 章节存在但内部全是 TODO / 占位 / "待补充"
- 形式合规（结构完整 / 字数达标）但消费方读完无可操作判据

触发动作：作者补论证 / 压缩 / 删除该段；不修订也不删除 → 进入 [#005](user-decision-log.md#005-docsmeta-归档治理--归档路径用户显式批准) 治理失误记录。

### §J.4 同 PR 修订 M-000 v2.0 §6 + frontmatter 的方案

M-005 ratify 同 PR 完成以下 M-000 v2.0 修订：

**修订前**（v2.0 当前 §6）：
> M-000 默认正文预算为 2500 non-whitespace chars；这是可读性和冷启动成本的设计目标，不是自动否决线。超过默认预算时，frontmatter 必须写 `override_rationale`...

**修订后**（M-005 ratify 后）：
> M-000 正文字数无预设上限，由作者通过 frontmatter `override_rationale` 给出密度证明：每段不能下沉、不能压缩、不能省略。`override_rationale` 是密度证明，不是破例申请。代码块预算与英文译本预算同此原则，独立 override_rationale 承载。

**frontmatter 修订**：
- 删除 `default_word_budget: 2500` 字段
- 保留 `override_rationale` 字段（语义改为"密度证明"）
- 在 `freshness.decay_trigger` 中增加 `density_proof_invalidated`

**Overrule 关系**：M-005 ratify 条目（预编号 #013）必须显式声明：
- Overrule [#009](user-decision-log.md#009-m-000-第一性原理审计--7-红旗接受改造--3-primary--3-分歧全保留--启动-v20-起草) R2「default_word_budget 字段保留」处理方式
- 接续 [#010](user-decision-log.md#010-m-000-v20-final-候选追认--字数上限第一性原理升级待-m-005-处理-status_enum-加-draft) 预声明
- 保留 [#001](user-decision-log.md#001-字数硬上限-1500-字--2000-字)/[#003](user-decision-log.md#003-字数计量单位精化b-方案non-whitespace--代码块独立--译本乘数) 历史裁决（不 Overrule，仅渐进废弃）

### §J.5 下游脚本兼容性处理

`default_word_budget` 字段删除后，下游消费该字段的脚本可能受影响。M-005 ratify 同 PR 必须：
1. 全仓 grep `default_word_budget` 找消费点
2. 受影响脚本同步修订（不消费该字段 / 改消费 `override_rationale` 存在性）
3. 若发现消费点但本轮无法修订，落 user-decision-log "字数升级后续 PR backlog" 条目，不阻塞本轮 ratify

按 §F.3 工程兼容性优先：若下游脚本删除阻碍其他工作流，可暂保留 `default_word_budget` 字段值为 `null`（语义为"不预设"），单独 PR 完成最终删除。

### §K.2 M-005 复审的禁止事项

复审不得用于：
- 把"麻烦的判据"软化为"建议"（§A.2 可验伪信号 / §B.3 强反对客观判据等）
- 把"具体编号"模糊化为"历史经验"
- 删除实证案例以简化文本（按 §A.1 必须可追溯）

复审仅可用于：
- 新增 / 扩展实证案例
- 调整章节顺序 / 表达密度
- 修订与下游派生的分工边界（§3）

### §K.3 与 M-000 §11 的衔接

M-005 视为 M-000 v2.0 §11 派生表中"M-005 质量判据与退化检测"行的具体落地。M-005 修订不触发 M-000 修订（除非影响 §11 派生表本身）。M-000 §6 字数预算章的修订在 M-005 ratify 同 PR 完成（[#012](user-decision-log.md#012-m-005-起草启动--主笔轮换-deepseek--010-字数升级同-pr-落地) Q3）。
