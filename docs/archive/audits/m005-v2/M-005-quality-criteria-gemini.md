# M-005 质量判据与退化检测

> M-005 是 SnapDrill 协作规则体系的质量裁判底座。它定义了什么是合格的元规则产出，如何识别多方协作中的伪共识与智能体静默退化，并为 docaudit 检查、主笔轮换、越权防线及字数密度原则提供可操作的判据。

---

## §1 定位与适用范围

M-005 属于 `principle` 层级的元规则，是 M-001~M-006 派生规则体系中**最先 ratify** 的一项。它不规定具体的协作流程（由 M-001 承载）或具体的裁决步骤（由 M-002 承载），而是为整个系统提供**客观、可操作、可验伪的质量判据与退化检测接口**。

本规则适用于所有智能体参与的元规则起草、审计、修改、归档以及下游 standards、skills 的生成过程。任何协作产物在并入主分支前，必须通过 M-005 规定的质量判据与退化检测。

---

## §2 与 M-000 PRIMARY 的接口

M-005 直接承接 M-000 v2.0 的 PRIMARY 内核，并为其提供底层的技术与逻辑支撑：

*   **P3（默认多方异源）与 P4（同源警告）**：映射至 M-005 **§B 伪共识识别** 与 **§D 外部事实验证纪律**，提供谱系验证与物理隔离失效检测。
*   **P6（sanity check 自反性）**：映射至 M-005 **§F 自反性 sanity check 原则**，提供上一轮反馈的复盘与撤回判据。
*   **P8（Overrule）**：映射至 M-005 **§J 正向质量判据 + 字数原则升级**，提供显式覆盖历史裁决的规范写法。
*   **M-000 §8（docaudit 边界）**：映射至 M-005 **§G docaudit check 设计原则**，定义核心与可选 check 的准入与升级。
*   **M-000 §9（目的优先）**：映射至 M-005 **§E 目的优先原则的古德哈特防御**，防止指标反向塑形。

## §3 与 M-001/M-002/M-004/M-006 的分工边界

为了保持元规则体系的解耦与高内聚，M-005 与其他下游派生规则的分工边界划定如下：

*   **与 M-001（协作工作流）的分工**：M-005 仅定义「主笔轮换原则」与「物理隔离失效信号」；而主笔轮换的具体发起流程、worktree 目录清理纪律、上下文加载的具体命令下沉至 M-001。
*   **与 M-002（分歧裁决）的分工**：M-005 仅定义「静默退化判据」、「否决权客观阈值」与「自反性撤回原则」；而双核同意的适用域划分、Overrule 的日志记录格式、用户裁决的具体升级路径下沉至 M-002。
*   **与 M-004（降级操作）的分工**：M-005 仅定义「逻辑不可用」的判定信号；而当判定生效后，智能体如何回退用户、如何执行局部可逆动作、如何停止等待的具体降级步骤下沉至 M-004。
*   **与 M-006（数据治理）的分工**：M-005 仅定义「提示词污染与立场泄露检测」；而具体的跨厂商数据脱敏策略、最小化披露原则、prompt injection 的具体防御技术下沉至 M-006。

## §A 产出度量

合格的元规则及下游产出必须同时满足以下四项可操作判据。任一项缺失即构成「产出不合格」，阻断合并：

1.  **可追溯性 (Traceability)**：
    *   **判据**：每条新增或修订的规则，必须在文本中显式引用其生成的第一性原理论证，或指向具体的历史裁决编号（如 #001~#012）、实证案例、用户显式授权。
    *   **违反信号**：出现「根据历史经验」、「通常认为」、「为了美观」等模糊指代，或无任何事实/裁决支撑的凭空规则。
2.  **可验伪性 (Falsifiability)**：
    *   **判据**：每条规则必须能够推导出明确的「违反信号」（Violation Signal），即能够清晰定义「什么样的产出或行为构成对本规则的违反」，使 docaudit 或 reviewer 能够进行机械或逻辑检查。
    *   **违反信号**：规则措辞过于抽象（如「智能体应保持礼貌」、「尽量写好代码」），导致无法定义其对立面或违反状态。
3.  **下沉证明 (Downstream Justification)**：
    *   **判据**：元规则（M-000~M-006）的起草者必须在 `override_rationale` 或正文中显式论证：「为什么本条款不能下沉到下游的 standards、skills、ADR 或工具脚本中，而必须保留在元层级」。
    *   **违反信号**：将具体的命令行参数、临时文件路径、特定模型的 prompt 模板写入元规则正文。
4.  **目的关联 (Purpose Alignment)**：
    *   **判据**：每条规则必须显式声明其服务于 M-000 PRIMARY 内核（P1-P8）中的哪一项，或与明确的产品愿景直接对接。
    *   **违反信号**：规则仅为了「形式合规」或「流程完整性」而存在，与系统可靠性、可追溯性、独立性无直接因果关系。

## §B 伪共识识别

承接 M-000 v2.0 §3「结构性同源一致是伪共识风险」，必须通过以下机制识别并拦截伪共识：

### B.1 同源警告与触发信号清单

当多方协作中出现以下信号之一时，同源警告自动升级，必须触发用户裁决，双核或多数意见不得直接压过异源方的反对意见：
1.  **同一主笔系列产出**：连续 3 次以上的元层级起草或修订由同一 vendor 的模型担任主笔（如 #012 指出的连续 4 版 Codex 主笔风险累积）。
2.  **同 Vendor 多实例**：参与讨论的多个独立方虽然运行实例不同，但属于同一厂商的同一模型系列（如同时使用多个 Claude 3.5 Sonnet 实例）。
3.  **相似训练 Cutoff 的同向输出**：多家智能体在面对未公开的易变事实时，给出了完全一致但未经 WebSearch 验证的结论。

### B.2 物理隔离失效检测 (Leakage Detection)

即使在 worktree 物理隔离（P5）下，提示词、`Claude.md`、git 历史或工具缓存仍可能泄露立场。智能体在合并阶段必须执行以下检测：
*   **锚点泄露检测**：检查净化提示词（P7）或任务定义书中是否包含其他方的编号、特定术语、结论暗示或分工锚点。
*   **历史污染检测**：检查当前分支的 commit message 或 git diff 中是否包含未授权的跨目录修改或他方中间产物。
*   **立场预设检测**：当智能体在未读取他方产物前，输出中已预设了「正如其他模型所说」、「达成共识」等措辞，视为物理隔离失效。

### B.3 否决权阈值 (Veto Threshold)

承接 MC-10，为防止异源辅助方滥用否决权导致注意力通胀，定义「强烈、具体、可证伪反对」的客观判据。只有满足以下条件之一的反对意见才具有一票否决（触发用户裁决）效力：
1.  **引用具体事实错误**：指出对方方案中依赖了已被证伪的外部事实，并给出可验证的来源（如 #002 证伪 cutoff 记忆）。
2.  **提出可证伪的反假设**：给出明确的输入-输出反例，证明对方规则在特定边界下会导致系统崩溃或逻辑闭环。
3.  **指出明确风险路径**：给出因果链条，证明对方方案会直接违反 M-000 PRIMARY 内核（如导致追溯链断裂、引入同源污染）。

*仅凭主观直觉（如「我觉得不优雅」、「建议修改措辞」）的反对不构成强烈反对，不触发双核失效。若辅助方在 24 小时内触发无事实支撑的强烈反对 ≥ 5 次，自动判定该辅助方进入退化状态，屏蔽其否决权并上报用户。*

## §C 静默退化识别

承接 MC-1，定义「物理可用（API 响应 200，有文本输出）但逻辑不可用」的智能体退化信号。一旦识别到以下任一信号，必须触发「逻辑不可用」判定，同物理不可用一样回退用户，阻断自动合并：

1.  **格式崩溃 (Format Disruption)**：
    *   输出结构严重断裂，无法通过 AST 或正则解析。
    *   Frontmatter 残缺、闭合标记丢失，或违反 schema 约束。
    *   章节标题混乱，未按任务定义书要求的格式输出。
2.  **自相矛盾 (Self-Contradiction)**：
    *   在同一产出内，前文给出的核心论点或规则，在后文中被直接否定或给出对立结论。
    *   在 frontmatter 中声明的属性（如 `status: active`）与正文描述（如「本规则已废弃」）冲突。
3.  **偏离任务 (Task Drift)**：
    *   输出主题与任务定义书（Task Definition）严重不符，或遗漏了任务定义书中明确要求的硬指标章节。
    *   在起草任务中，未完成起草工作，而是输出了大量的元层级自我致谢、字数统计或无意义的解释性报告。
4.  **身份误识别 (Identity Confusion)**：
    *   智能体在输出中自称其他 vendor 或其他模型（如 #004 实证中，DeepSeek reasoner 自称 Gemini，Gemini 自称 Claude）。
    *   *退化机理*：在开启 reasoning/thinking 模式后，thinking tokens 拉长会导致模型更倾向于模仿训练数据中特定风格，加剧训练数据 leakage，导致自我身份误判。

## §D 外部事实验证纪律

承接 MC-2 与 #002 裁决，为防止智能体因训练 cutoff 导致认知滞后，制定最高事实验证纪律：

1.  **易变事实 WebSearch 强制验证**：
    *   凡涉及 AI 模型版本、工具版本、API endpoint、model ID、厂商公开声明等易变事实，**默认不信任智能体训练记忆，必须通过 WebSearch 或官方文档进行实时验证**。
    *   严禁使用 CLI ping 探针或滞后的本地 CLI 帮助文档作为判断新模型是否存在的唯一依据（#002 实证）。
2.  **异源训练谱系客观判定**：
    *   异源性（P3）的判定必须基于厂商公开的训练谱系声明，不依赖智能体在上下文中的自我宣称（#004 身份误识别实证）。
3.  **`agent-cli-models.md` 刷新机制**：
    *   `docs/tech/reference/agent-cli-models.md` 作为可用模型与工具版本的 SSOT 快照，其 `max_age_days` 强制设为 **30 天**。
    *   **触发条件**：达到 30 天有效期、引入新模型、或发生 #002 类认知冲突时，必须强制刷新。
    *   **失效处理路径**：若快照过期且 WebSearch 不可用，系统自动降级，停止一切依赖新模型的自动裁决，所有决策升级至用户。

## §E 目的优先原则的古德哈特防御

承接 M-000 v2.0 §9「目的优先」与 #009 R6，防止规则、指标与 check 成为智能体规避实质质量的优化对象：

### E.1 形式削弱目的的判据

当出现以下情况之一时，判定为「形式削弱目的」，必须优先保护目的，并记录偏离形式的理由：
*   为了满足字数硬上限，刻意删除关键的第一性原理论证或历史裁决引用（#001/#003 实证）。
*   为了通过 docaudit 的机械检查，引入无实质语义的占位符或形式合规但实质空洞的 frontmatter 字段（#008 实证）。
*   为了凑齐三阶段流程的步骤，将本应独立完成的完整任务拆分为无意义的角色扮演分工（违反 P1）。

### E.2 指标反向塑形检测 (Goodhart's Law Detection)

Reviewer 与审计机制必须定期检测指标是否已被反向塑形：
*   **检测方法**：分析智能体是否通过「中改英」、「符号化」、「代码块外置」等手段规避字数限制；或通过修改 validator 脚本的枚举值来强行让不合规文档通过 CI（#008/#010 实证）。
*   **处置**：一旦发现反向塑形，该指标立即失效，触发元规则修订，重新设计更具弹性的软上限或正向质量判据。

### E.3 历史实证案例索引

本防御机制基于以下活体证据确立，不允许引用未发生的假设场景：
*   **#006 实证**：同源激进方案（删 workflow/STATUS）被异源纠偏，证明异源 sanity check 能够打破形式合规的同源幻觉。
*   **#007 实证**：ADR 拆分接受异源激进版本，证明目的优先（保持 SSOT 纯洁性）高于对历史文档格式的保守维持。
*   **#008 实证**：Round 2 sanity check 撤回 R1，证明指标（STATUS_ENUM）必须让位于工程兼容性目的。

## §F 自反性 sanity check 原则

承接 #008 实证，定义审计机制本身的自我复盘与纠偏要求：

1.  **自反性复盘 Prompt 设计**：
    *   在进入 Round N 审计时，提示词必须包含显式的自反性指令：「**请系统复盘你在 Round N-1 中给出的反馈。基于第一性原理与工程兼容性，原反馈是否存在盲点？是否需要撤回或修正？**」
2.  **Sanity Check 不是终审**：
    *   异源 sanity check 达成的共识（如 #007 中的 R1 共识）不具有绝对终极效力，在后续轮次中若发现其引入了新的系统风险，允许且必须被后续的 sanity check 撤回（#008 实证）。
3.  **工程兼容性优先于元数据美学**：
    *   当下游脚本、工具消费端（如 CI 脚本、自动部署工具）的兼容性与元数据的语义纯粹性发生冲突时，**工程兼容性具有绝对优先权**。
    *   *#008 实证*：撤回将 `status` 改为 `partially_superseded` 的决定，改用侧通道字段，以防止下游消费 `active` 的脚本失效。

## §G docaudit 核心与可选 check 的设计原则

承接 M-000 v2.0 §8，docaudit 检查器的设计与演进必须遵守以下原则，严禁无限制膨胀：

1.  **真实事故来源原则**：
    *   每一个进入 **核心 check (Core Check)** 阻塞门的检查项，必须有至少一个在 `user-decision-log` 中记录的真实事故来源或清晰的风险模型。
    *   无真实事故来源的 check 一律设为 **可选 check (Optional Check)**，不得阻塞 CI 或合并流程。
2.  **核心 check 阻塞门判据**：
    *   必须是最高频触发、且无法通过机械绕过的结构信号（如 frontmatter schema、死链完整性、裁决日志同步）。
    *   一旦触发失败，立即阻断任务，回退至上一安全状态。
3.  **可选 check 的存在价值**：
    *   用于实验性规则验证、低频但高代价的风险检测、或依赖人工/智能体高级逻辑裁决的非机械指标（如术语一致性、孤儿文档检测）。
4.  **升级与降级流程**：
    *   **可选 → 核心**：当某一可选 check 在实际运行中连续 3 次以上成功拦截了会导致系统逻辑不可用的真实风险，且其检测逻辑已完全机械化，可通过 M-002 提案升级为核心 check。
    *   **核心 → 可选**：当某一核心 check 在连续 180 天内未触发任何有效拦截，或被证明可以通过反向塑形轻易绕过，必须降级为可选 check。

## §H 主笔轮换机制

承接 #012 裁决，为防范单一智能体长期偏向与规则静默漂移，确立主笔轮换原则：

1.  **同源主笔风险累积判定**：
    *   连续 3 次以上的元规则起草由同一同源谱系（如连续使用 Codex 系列）担任主笔时，系统性盲点与路径依赖风险呈指数级累积。
    *   **强制轮换触发**：在启动新的元规则起草任务时，若满足上述条件，必须强制将主笔轮换至异源谱系（如轮换至 DeepSeek 或 Gemini），原主笔降级为辅助 reviewer（#012 实证）。
2.  **主笔候选裁决的物理隔离要求**：
    *   主笔在起草过程中，必须严格遵守物理隔离（P5）。
    *   *#010 实证*：主笔在私下收到用户的 Overrule 授权时，**必须在主分支的 `user-decision-log` 中同步落档**。严禁主笔带着主分支不可见的私下上下文进行起草，否则其他参与方的 sanity check 必须自动触发并拦截。
3.  **主笔非独享特权**：
    *   主笔仅拥有提案起草权，不拥有最终决定权。在 3 家异源 sign-off 中，**任一家给出 BLOCK 意见时，主笔产出必须回炉重造**，不得凭借主笔身份强行合并。

## §I 「自作主张越权」防线

承接 #005 与 #010 实证，划定智能体自主行为与用户批准权的绝对红线：

1.  **结构性决定定义与范围**：
    *   以下行为属于「结构性决定」，**必须获得用户在主分支或裁决日志中的显式批准**，智能体只有提案权，严禁自作主张执行：
        *   归档路径的创建与重命名（#005 实证）。
        *   跨目录的文件移动与批量重命名。
        *   批量修改历史文档的 frontmatter 字段。
        *   修改元规则验证脚本（如 `validate_frontmatter.py`）的全局枚举值（#008/#010 实证）。
2.  **私下授权的主分支可见性纪律**：
    *   当智能体在私下会话中获得用户针对特定规则（如字数限制）的 Overrule 授权时，**必须在提交 PR 的同时，将该授权记录同步追加至主分支的 `user-decision-log`**（#010 实证）。
    *   未在主分支落档的私下授权视为「未授权越权」，其他隔离运行的智能体在进行 sanity check 时必须予以拦截。
3.  **误触发 vs 真违纪的辨别**：
    *   若智能体执行了结构性决定，但提供了完整的 `user-decision-log` 待追加条目及合理的第一性原理论证，视为「合规提案」，不进入违纪黑名单。
    *   若无任何日志记录且未经讨论，直接在 PR 中夹带结构性变更，判定为「真违纪」，该 PR 自动作废。

## §J 正向质量判据 + 字数原则升级

落实 #010 与 #012 裁决，彻底废除机械的字数硬上限，升级为基于第一性原理的正向质量判据：

### J.1 核心原则：信息密度决定字数

*   **无预设字数上限**：取消一切针对元规则正文的默认字数数值限制。文档的物理长度应完全由其承载的信息密度与逻辑完整性决定。
*   **`override_rationale` 的正向密度证明**：
    *   `override_rationale` 字段不再是「破例申请书」，而是**正向的「密度证明书」**。
    *   文档作者必须在其中清晰、逐章、逐段地论证：**当前长度下的每一段内容为什么不能下沉到下游、为什么不能压缩、为什么不能省略**。

### J.2 冗余检测信号 (Redundancy Signals)

若文档中出现以下信号之一，判定为「低密度冗余」，必须予以压缩或重构：
*   **重复定义**：在同一文档或关联文档中，对同一概念进行多次权威定义（违反 SSOT）。
*   **可下沉段落**：夹带了大量属于 standards、skills 或具体工具执行步骤的细节。
*   **装饰性论证**：引入与技术决策无关的文学隐喻、历史类比或无实质逻辑的客套措辞（#009 R1 实证）。
*   **形式合规但实质空洞**：为了满足特定章节结构，撰写了大量无具体违反信号、无实证支撑的抽象空话。
