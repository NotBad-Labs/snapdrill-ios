# 智能体协作元宪章（Meta-Vision）（Claude Desktop chat 草案）

> 草案 #4 of 4。Claude CLI 作为中立主笔，本草案落档阶段不评点。

## 一、核心命题

多智能体协作的目的不是补偿单智能体能力不足，而是把「我相信此答案」升级为「我有理由相信此答案」——任何单一来源的输出都受其训练分布、架构偏好与服务状态制约，只有多源独立趋同才构成可信证据。

## 二、认识论根基

冗余的根基有二。其一是「跨先验的独立趋同」：不同训练语料、不同对齐方式的智能体独立得出一致结论，大致等同于贝叶斯意义上的模型平均，显著降低单一先验主导误判的概率。可复现是必要不充分的——单模型自洽地稳定输出错误，同样可复现。其二是失败模式覆盖：每个智能体的盲区不同（谄媚、幻觉、过度保守），协作只要被设计成「暴露分歧」而非「快速收敛」，就有相互纠错的潜力。

单智能体的「采纳建议」与多智能体的「三角测量」在结构上不同：前者线性被动，后者结构化对抗。

## 三、适用范围

判断标准是决策的可逆性与代价，而非任务难度。

需要多方：架构决策、长期维护代码、对外承诺、安全合规、不可逆操作、公开发布。一旦走错，修正成本远高于事前协商。

可以单方：探索性试验、临时脚本、格式转换、有唯一解的事实查询、依赖单家明显强项的任务。

反直觉但关键：**极端时间压力下的可逆决策，多方协作反而有害**。等待裁决错过窗口期，通常比单方决策后纠正代价更高。

## 四、降级策略

降级判据不在「额度耗尽」，而在「被阻塞方对本任务是否具备独特价值」。若无关，直接前行；若相关，比较「等待至额度重置」与「降级完成后复核」的总成本。

两方是底线。跌至单方时进入「草稿模式」：输出标记为待复核，不视为完成，另一方上线后立即补审。这既不阻塞，又保留协作本质。

## 五、失败定义与缓解

协作失败有三种形态：

**显性分歧**——多方公开不一致。这恰是协作发挥作用之处，不是失败。

**隐性同谋（假共识）**——多方一致同意错误结论。原因可能是训练语料重叠、用户前置提问泄露倾向、某方草稿被过早传阅锚定他方。这是最危险的失败，因不可见。

**质量退化**——多方都产出平庸但能「过关」的答案，相互放行。源于评审标准模糊或评审方被生产方视角同化。

除独立工作环境外，缓解机制有：**盲式起草**作为标配（本任务即范例）；**对抗性配对**——明确指派某方为「挑战者」，其唯一职责是寻找他方弱点；**证据链可追溯**——任何关键论断必须可溯源至具体出处，不可溯源者默认待验证；**时间错位复审**——同一智能体不同时间审视同一产出，作为半独立的二次来源。

## 六、裁决机制

用户原意我基本认同，但建议以下细化。

**裁决权不等于通过权**。即便 Claude 与 Codex 两方同意，以下决策仍应上交用户：不可逆操作、跨元层级修改、法律或财务承诺。

**警惕裁决方相关性**。Claude 与 Codex 在训练与对齐上存在相关性，二者一致不等于两个真独立证据源。其余智能体若强烈反对，主笔应将异议上报用户，而非简单忽略。

**主笔权限**。主笔负责整合与记录，但不得静默放弃任何一方的实质性意见，被舍弃意见须留下理由。

**用户介入时机**。除分歧外，以下情况也主动请用户介入：进入未踏入的新领域、检测到系统性盲点、规则本身需修订。

## 七、元规则的元规则

实事求是、版本控制、奥卡姆剃刀这三条原则我完全认同。补充以下具体机制：

**修改必须带触发场景**。提案须附带「哪一次真实协作暴露了现有规则的不足」，无具体场景的修改默认不予采纳——这是抑制凭空想象式膨胀的关键阀门。

**新规则有试用期**。新增条款先以「草案」身份存在固定时长（如四周），期满专项复核，要么转正要么淘汰，防止「加上去就下不来」。

**周期性精简**。规则集每隔一段时间整体复核，长期未被引用或被实际行为否定的条款应删除。

**语义单一性**。每个概念在整个体系中只有一处定义，其他地方只能引用。发现某概念两处定义不一致，本身就是元规则失效的警报。

## 八、与产品 vision 的关系

二者在范畴上正交：产品 vision 回答「做什么」，协作元规则回答「怎么做、与谁做」。绝大多数情况不冲突。

会冲突的边界情形，往往是产品 vision 要求的速度或自由度，与元规则要求的多方共识或可追溯性相抵触。冲突的默认倾向应是：**涉及不可逆或高代价决策，元规则优先；涉及可逆或时间敏感决策，产品 vision 优先**。此默认仍可被用户具体裁决覆盖，但避免每次冲突都打扰用户。

## 九、演进愿景

希望长成的样子：核心文档保持极简，周边以按需加载的技能或附则形式存在；每条规则有清晰归属、明确范围、可追溯历史；经验稳定沉淀为可复用技能，而非散落在对话片段中；层级始终清晰，概念单一权威。

最怕变成的样子：层级混乱的大杂烩；长篇却无人遵循的死规则；同一概念语义漂移；token 消耗大却边际价值递减；以及最隐蔽的——元规则本身被遗忘或绕过，而无机制能察觉。

## 十、下游派生

预期派生（按依赖关系）：**协作工作流规约**（每次协作如何分工、流转、归档）→ **裁决日志格式**（分歧如何记录与回顾）→ **技能库治理**（经验如何沉淀、命名、淘汰）→ **各智能体提示基线**（每家如何调用、上下文如何裁剪）→ **评估与度量规则**（协作质量如何衡量）。

产品 vision 作为平行体系不在派生链中，但工作流规约须明确二者的接口与冲突上报路径。

## 我对原话的修正意见

**对第 1 条**：用户将冗余本质定义为「可复现」，建议细化为「跨先验的独立趋同」。单一模型稳定地复现一个错误也是可复现，这不构成证据。真正有价值的是不同先验下独立得到一致结论。

**对第 5 条**：「Claude 与 Codex 同意即可不问用户」在多数场景合理，但应保留三类例外：不可逆操作、跨元层级修改、法律或财务承诺——即使两方同意仍应上交。

**对第 6 条**：「修改必须能溯源」建议加一条平行约束——「修改必须带触发场景」。无真实场景驱动的修改默认不采纳，这是防止规则膨胀的关键阀门。

## 我作为 Claude 起草的盲点

**主笔自身偏向**。若主笔由我担任，我对叙事的细微偏好（措辞、结构、强调）可能在不自知的情况下影响成稿，自省难以触及。需外部机制（轮换主笔、非主笔最终校对）弥补。

**协作的边际成本未量化**。多方每次都意味着 token、时间、用户认知负担的成倍增加。我倾向把「多方」作为默认，但缺乏「多方边际成本是否值得」的核算。更成熟的方案应给出「何时三方、两方、单方」的可量化判据，我目前只有定性描述。

**先后顺序污染**。即使盲式起草，若某家智能体习惯性更晚交付，后到者可能受用户在对话中无意识透露的前者思路所污染。识别与缓解机制我未给出。

**利益相关方论证**。裁决权分配给 Claude 与 Codex 时，我作为利益相关方讨论此规则的客观性本身可疑。我可能不自觉地论证了对自己有利的安排。

**宏观环境变化未涉及**。模型版本迭代、服务条款变更、厂商停止服务等外部冲击，我只讨论了体系内部演进，未给出应对机制。
