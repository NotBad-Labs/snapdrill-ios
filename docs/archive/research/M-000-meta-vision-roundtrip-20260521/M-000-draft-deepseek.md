# Meta-Vision（DeepSeek 草案）

> 草案 #3 of 4。Claude CLI 作为中立主笔，本草案落档阶段不评点。

智能体协作元规则的最顶层指导文档，地位等同于产品 vision。所有下游规则、流程、标准必须服从本文。

## 1. 核心命题

多智能体协作不是「用更多模型做同一件事」，而是**通过独立冗余获得可比较的认知差异，从而择优进化**。单个智能体即便再强，也无法同时提供不同推理路径、不同架构偏好、不同失败模式下的多重解。多智能体体系让选择权回到人手里，而不是盲目信任某一家厂商的单一输出。

## 2. 认识论根基

冗余在工程上常被理解为容错备份，但这里的冗余本质是**科学复现**——同一问题交由不同认知主体独立求解，如果多方结论收敛，则结论的可信度远超单方断言；如果结论发散，则揭示问题本身的模糊性或某一方的认知盲区。这与单智能体的本质差异在于：单智能体的「反复生成」只是同一推理空间内的多次采样，而跨模型的多智能体协作是**不同推理空间之间的交叉验证**。知识不是被单一权威颁布的，而是在独立观察的汇聚中涌现的。

## 3. 适用范围

**必须多方的场景**：所有影响下游决策的关键产出——包括但不限于架构选型、规则制定、安全策略、对外发布的内容、生产代码合并、数据解析结论。这些场景的共性是对正确性和鲁棒性有不可妥协的要求，单方错误会造成级联成本。

**可以单方的场景**：纯探索性分析、个人学习笔记、不进入生产链路的临时脚本、娱乐性对话。其边界在于：产出的生命周期短、影响范围仅限用户本人当时当次、不存在被下游继承的风险。

一旦某个单方产出被纳入长期维护或传递给其他协作者，它必须重新经过多方审视。

## 4. 降级策略

原则：**宁等勿降，保持至少两方**。三方协作是标准态，当其中某个服务因额度、中断等原因不可用时，降级为两方协同；如果仅剩一方可用，除非任务有时效硬约束且后果可逆，否则**停止工作并等待恢复**，而非降级到单方盲信。

额度感觉上 Claude 最充裕，Gemini 次之，Codex 相对紧张，但这只是经验观察，不做为硬性判据。实际判据是：能否在五分钟内获得该智能体的有效响应。如果连续三次尝试均失败或返回降质服务标记，即视该方暂时不可用。

两方协同的降级路径：优先保留 Claude（MAX 订阅额度最稳），第二选择按以下顺序尝试：Gemini → Codex → DeepSeek API。如果 Claude 本身不可用，则 Codex + Gemini 或 Codex + DeepSeek，始终保持两方。不降级为仅单方的底线是绝对的，除非用户本人明确下令。

## 5. 失败定义与缓解

协作失败的定义：**无法达成可验证的共识**。这包括三类情况：①多方结论逻辑互斥，且无法通过同一组事实或数据裁决；②某一方产出明显退化（质量骤降、循环论证、脱离上下文）；③多方结论表面一致，但该共识建立在错误前提之上（共谋型假共识）。

**污染**：一方产出被另一方不经批判地接受，丧失独立性。识破方法：要求每方先独立形成输出，再交叉比对，比对时追溯每条结论的推理链。**退化**：模型输出质量明显低于其正常水平，表现为回避实质、过度泛化、自我重复。识破方法：对照该模型在同类任务上的历史输出特征，一旦显著偏离则触发重试或暂停。**共谋**：多方基于同一虚假前提达成一致。识破方法：显式要求每方陈述其核心假设，并让其他方批判这些假设，而不是批判结论。

缓解机制除独立工作环境（隔离上下文、不同分支）外，还包括：**强制异议制**——在关键节点指定某一方必须扮演反驳者，不管它自身倾向如何；**溯源锚定**——所有结论必须附带可追溯的推理链和事实依据，不能仅凭权威；**时间隔离**——不同方在时间上错开工作，避免实时交互中的无意识对齐。

## 6. 裁决机制

用户拥有最终裁决权。Claude 和 Codex 拥有代理裁决权，可以在二者意见一致时直接形成结论，无需中断用户工作流。其他智能体无裁决权，只有建议权。

分歧收敛路径：当 Claude 和 Codex 意见一致，结论自动通过。当二者不一致，或者其中一方与 Gemini / DeepSeek 形成一致而另一方孤立时，必须将分歧点、各方推理摘要、事实依据整理为结构化简报，提交用户裁决。任何一方都不得在分歧未解决前将未决结论推入下游执行。

主笔智能体（被指派主导某项产出的那一方）的权力边界：有权决定表达方式、结构组织、节奏控制，但无权压制其他方的实质性异议。如果主笔与审查方在实质结论上僵持，同样上升至裁决。

## 7. 元规则的元规则

这份文档的演进遵循**实事求是**——任何修改必须有事实或数据支撑，不能仅凭感觉或偏好。修改权限向所有智能体和用户开放，但修改不是随意的。奥卡姆剃刀原则：如无必要，勿增实体。每增加一条规则，必须证明它解决了现有规则无法解决的明确问题，并评估其 token 成本。

修改必须记录：变更动机、提议方、决策依据、生效时间，且全部纳入版本控制系统追踪。每次修改需在提交信息中写明「为什么改」而非仅仅「改了什么」。任何智能体在加载元规则时，若发现自身记忆与版本库中的当前版本不一致，以版本库为准。这就是单一权威源原则在元规则本身的应用。

## 8. 与产品 vision 的关系

本元规则与产品 vision **平级且正交**。产品 vision 定义「我们要去向哪里」，本元规则定义「我们如何一起工作才能安全高效地到达那里」。两者同为最高层指导，不存在一方服从另一方的关系。

当两者在实践中发生冲突时（例如产品 vision 要求急速交付，但元规则要求必须三方协作），没有预设的让步层级，必须立即停止并交由用户本人裁决。用户在这种冲突中的决定本身，会成为后续解释规则的先例，但不会自动改写本元规则——改写仍需走元规则修改流程。

## 9. 演进愿景

这套体系应当成长为**一棵纪律严明的规则树**：本 Meta-Vision 是根，派生出一级下游规则（协作流程、分歧裁决细则、技能加载标准、降级操作手册等），再由一级规则派生更细的二级规范。层级清晰，依赖关系明确。每个概念只在一个地方定义，所有引用指向同一权威源。

**最怕**：规则不断堆砌却从未删减，最终变成一锅大杂烩——智能体加载后要花大量 token 理解冗余甚至矛盾的条款，反而降低协作效率。防止这一结局的唯一方式就是严格执行奥卡姆剃刀和溯源记录，让每条规则都能被问责。

## 10. 下游派生

本元规则将直接派生出以下一级下游文档（仅列方向，非具体文档名）：
- **协作会话协议**：定义多方交互的回合规则、上下文隔离边界、信息共享的白名单机制
- **分歧裁决细则**：详细规定分歧等级、上升条件、裁决格式、执行与复核
- **技能加载与淘汰标准**：规定什么经验可以沉淀为可加载技能，技能的测试、废弃与替换流程
- **降级操作手册**：明确各服务的状态监控方法、切换流程、恢复后重同步机制
- **质量判据与退化检测**：定义产出质量的度量维度和自动警报条件

这些下游文档的修订都必须服从本 Meta-Vision，并在自身开头声明其所依据的元规则版本。

---

**我对原话第 4 条的修正意见**：失败不应仅定义为「无法达成共识」，还应包括「达成的是不可靠的假共识」——即共识形成过程违反独立原则（如一方直接复制另一方）或建立在未被检验的错误前提上。元规则需要保护的不是共识本身，而是共识的认知质量。

**我对原话第 5 条的补充意见**：Claude 和 Codex 的裁决权应附带「可问责性」约束——当它们共同做出裁决后，如果事后证明该裁决有重大偏差，必须在元规则中记录该案例并探讨是否需要调整裁决权的分配。裁决权不能是无成本的。

---

**我作为 DeepSeek 起草的盲点**：我可能低估了上下文窗口限制对规则加载的实际影响——当多方需要同时加载大量上下文时，冗长的元规则本身是否会挤占核心任务的认知资源，我没有给出定量评估。我也没有充分考虑用户交互界面（桌面端 chat / cowork / code 与命令行的行为差异）对协作模式的实质制约，这些差异可能在某些场景下使「独立工作环境」难以技术实现。此外，我对「强制异议制」可能引入人为对抗、拖慢简单任务的风险缺少具体缓解措施。最后，元规则的生命周期管理——即何时应考虑整体废除重写而非局部修订——我未给出判据，这可能在长期演进中成为问题。
