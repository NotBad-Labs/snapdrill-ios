## ADR-003: OCR 处理流水线与重处理策略

* **状态**: 已采纳
* **日期**: 2025-09-10
* **决策者**: 架构负责人 / iOS 工程组
* **取代**: -

## 上下文

错题图片需识别题干与关键信息（公式、文本、手写标注）。早期版本使用设备端 Vision / Core ML OCR 能力；需兼顾性能、能耗、隐私与失败/低质量重处理能力。

## 决策驱动因素

1. 识别准确度与公式/混合文本支持。
2. 端侧处理性能与用户等待时间。
3. 离线可用性与隐私（不将图片上传第三方）。
4. 重处理触发与版本追踪机制。
5. 可插拔性：未来引入更高精度模型或云端增强。

## 方案对比 (摘录)

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| 纯端侧 Vision + 内置模型 | 使用 Apple Vision API | 隐私好；无网络延迟 | 对复杂公式/排版准确度有限 |
| 端侧 + 自训轻量模型 | 自带额外 CoreML 模型 | 更好公式支持 | 训练/维护成本；包体增加 |
| 云端 OCR 服务扩展 | 第三方/自建云服务 | 更高准确率 | 隐私/合规 & 网络依赖 |

## 决策结果

阶段1 使用纯端侧 Vision；保留重处理日志与多版本文本；抽象 OCRService 协议，为未来替换或级联后端增强铺路。

## 核心设计要点

* OCRService 接口：process(image) -> OCRResult (textBlocks[], latency, modelVersion)
* 结果持久化：存储结构含 version, createdAt, source(hot/rehydrated/reprocess)
* 重处理触发：用户手动发起 / 模型版本升级 / 低置信度阈值命中
* 版本保留：仅标记最新=active，其余归档可回溯

## 后果

### 正面

* 上线快，隐私风险低。
* 行为可观测：统计识别失败率 & 平均延迟。
* 未来可渐进加入云增强层。

### 负面 / 风险

* 复杂题型识别率不足影响可用性。
* 多版本归档占用一定存储空间。
* 用户批量重处理可能带来瞬时性能压力。

## 风险缓解

* 启用并发队列限流（同时重处理任务数上限）。
* 记录低置信度样本供人工评估模型替换收益。
* 定期清理超过阈值（例如30天）未访问的旧归档版本（软清理）。

## 后续行动

* 定义 OCRResult 数据模型 & 持久化结构。
* 指标：failure_rate, avg_latency_ms, reprocess_rate。
* 评估接入公式专用模型的临界条件 (target accuracy delta)。
