> Last verified: 2026-03-21
>
> 本文件展示项目从「为什么做」到「交付上线」的完整链条。
> 每一层不仅说明**有什么**，还说明与上下游的**关节**——输入是什么、输出是什么、谁约束谁。
>
> 维护规则：新增文档或机制时，同步更新本文件。

## 层间关节详解

> 「关节」是层与层之间的转换机制——输入经过什么过程变成输出。
> 关节断裂 = 上游决策没有传导到下游执行 = 系统性盲区。

### 关节 1→2：愿景 → 需求

| 维度 | 说明 |
|---|---|
| **转换机制** | 产品原则（PV-1~5）作为过滤器，每个功能必须追溯到某条原则 |
| **验证手段** | 用户旅程（5 条具体场景）验证需求的真实性 |
| **断裂风险** | 功能蔓延——需求无法追溯到愿景 → 用旅程验证拦截 |
| **实证** | #305 终审中产品经理帽发现 Onboarding 字段选择违反 PV 原则 5（家长友好） |

### 关节 2→3：需求 → 设计

| 维度 | 说明 |
|---|---|
| **转换机制** | 决策前研究铁律（principles.md）+ ADR 记录 |
| **验证手段** | 蓝图验证 #287（57 条能力逐条核对） |
| **断裂风险** | 架构决策脱离产品约束 → ADR 必须注明产品需求来源 |
| **实证** | ADR-001（@Model = 领域对象）直接来源于「每改一字段最多 3 文件」的产品效率要求 |

### 关节 3→4：设计 → 实现

| 维度 | 说明 |
|---|---|
| **转换机制** | architecture.md 定包边界 → conventions.md 定编码标准 → infrastructure.md 定 API 签名 |
| **验证手段** | swiftlint --strict + xcodebuild build（编译器强制依赖方向） |
| **断裂风险** | API 文档与代码不同步 → 新增 API 必须同步更新 infrastructure.md |
| **实证** | #376 审计发现 conventions.md 中图片加载规则缺失 → 补充后全量 Grep 扫描 |

### 关节 4→5：实现 → 协作

| 维度 | 说明 |
|---|---|
| **转换机制** | 每个代码改动通过 Git 工作流流转：Issue → 分支 → PR → Review → 合并 |
| **验证手段** | 三方 Code Review（Gemini 自动 + Antigravity/Xcode 手动 + Claude 核实） |
| **断裂风险** | 跳过 Review 直推 → Git 铁律禁止；Review 结论不追踪 → 发现即追踪铁律 |
| **实证** | PR #303 经三轮 Review 迭代才发现 Feature Flag 死开关问题（用户切换无效） |

### 关节 5→6：协作 → 质量

| 维度 | 说明 |
|---|---|
| **转换机制** | PR 合并前对照 DoD 自检 → 发版前走 release-checklist |
| **验证手段** | 四级质量门（见下方） |
| **断裂风险** | diff 级 Review 无法发现全局问题 → 需要周期性全量审计补充 |
| **实证** | PR #336-#379 合并后新模式未被审计，直到 #376 全量审计发现 141 个问题 |

### 关节 6→7：质量 → 交付

| 维度 | 说明 |
|---|---|
| **转换机制** | release-checklist.md 全部通过 → Archive → TestFlight → App Store |
| **验证手段** | 真机验收（iPhone 17）+ TestFlight 内部测试 |
| **断裂风险** | 文档通过但真机体验不一致 → 真机验收是发版阻断项 |
| **实证** | PR #374/#375 在真机验收中发现 Onboarding 字段选择页仍存在（文档已改但代码未删） |

### 反馈关节 7→1/2：交付 → 愿景/需求

| 维度 | 说明 |
|---|---|
| **转换机制** | 用户反馈 + 数据分析 → 产品决策 → 需求更新或愿景调整 |
| **验证手段** | App Store 评价、Analytics 数据、用户研究 |
| **断裂风险** | 反馈未被系统性收集 → v1.0 阶段依赖 App Store 评价 + 主动用户访谈 |

## 四级质量门

质量保障不是单一环节，而是四级递进：

```
Level 1: PR Review（每次 PR，diff 级别）
  ├─ Gemini 自动（GitHub Action）
  ├─ Antigravity / Xcode Intelligence（手动，按复杂度）
  └─ Claude 独立核实（每条 finding）
      │
      │ 发现的问题 → 当前 PR 修复 or 新建 Issue
      ▼
Level 2: 蓝图验证（里程碑级别，纵向）
  └─ 代码是否实现了需求？逐条核对（#287：57 条能力）
      │
      │ 未实现 → 补实现；过度实现 → 删代码
      ▼
Level 3: 全链路终审（里程碑级别，横向）
  └─ 需求是否合理？产品是否准备好了？
  └─ 7 帽子审视 + 三方独立审计（#305）
      │
      │ 发现 → 按 S0-S3 分级 → 依优先级修复
      ▼
Level 4: 全量代码审计（发版前，全代码库）
  └─ 8 维度扫描（#376：141 个发现 → 11 个 Issue）
  └─ 复盘沉淀（#404：7 类盲区 → 编入文档体系）
      │
      │ 经验 → 更新 principles.md / conventions.md / workflow.md
      │      → 下次审计时作为检查项
      ▼
回到 Level 1（持续循环）
```

## 设计原则

1. **每层约束下一层**：上游的决策是下游的输入和边界，不能跳层
2. **关节必须有机制**：层间转换不能靠"记得"，必须有文档或工具强制执行
3. **反馈必须能回传**：下游发现的问题必须有路径反馈到上游（Issue → 需求更新 / 规则修订）
4. **闭环 > 完美**：每个环节有 80% 的覆盖 + 闭环反馈，好过某个环节 100% 但其他环节断裂
