# SnapDrill 文档体系全量审计与改进建议 (SEPG 视角)

作为一名拥有 15 年经验的软件工程过程改进顾问，我不仅从传统的 **CMMI/ISO** 标准审视此体系，更结合 **AI-Native Engineering** 的特殊性。以下是针对 SnapDrill 现有文档体系的独立审计报告。

---

## 1. 完整性审计 (Completeness Audit)

按 SDLC 生命周期维度评估，当前 10+4 体系的覆盖情况如下：

| 维度 | 评估结论 | 评价与缺口 |
|---|---|---|
| **战略与愿景** | 🟢 **卓越** | `product-vision` 与 `product-business` 提供了远超一般独立项目的商业透明度。 |
| **需求与发现** | 🟢 **卓越** | `product-journeys` 极具价值，它为 AI 提供了「同理心上下文」，防止功能堆砌。 |
| **架构与设计** | 🟡 **稳健但有欠缺** | 包边界与依赖原则非常清晰。**缺口**：缺乏 **ADR (Architecture Decision Record)**。目前的 `architecture.md` 仅记录当前状态，不记录演进过程中的「为什么不」。 |
| **实现与规范** | 🟢 **卓越** | `principles.md` 的「研究铁律」是该体系的灵魂，它强制将 AI 从「盲目生成」拉回到「先行调研」。 |
| **质量与测试** | 🔴 **系统性薄弱** | 虽有 `audit-checklist`，但缺乏统一的 **Test Strategy**。目前对「什么该单元测试、什么该集成测试、UI 测试边界」的界定模糊。 |
| **交付与运维** | 🟢 **匹配** | Git 工作流与三方 Review 流程对单人项目来说是非常高的标杆。 |
| **知识管理** | 🟢 **创新** | **16 角色系统** 是该项目的核心竞争力，它通过指令隔离解决了 AI 认知摩擦问题。 |

## 2. 内部分析核实 (Internal Conclusion Verification)

| 内部结论 | 独立判断 | 理由与依据 |
|---|---|---|
| **1. 体系完善，相当 80 人公司** | **部分同意** | **逻辑层** 达到了 80 人公司的水平，甚至在 S0-S3 优先级分级上更严谨。但 **过程层** 欠缺（如 RTM 的替代品、配置管理记录）。 |
| **2. RTM 对消费级 App 不必要** | **同意** | 在敏捷环境中，Issue → PR → Code 的链路已足够满足 29148 标准中的「双向追溯性」。 |
| **3. 最大缺口是 ADR 和 Changelog** | **同意** | 尤其是 ADR。在 AI 参与的架构演进中，AI 极易因为旧文档的惯性而在新架构上做出「复古」决策，ADR 是唯一的刹车。 |
| **4. DoD 和 Test Strategy 应独立** | **同意** | 现有文档中测试守则被分散在 `principles` 和 `workflow` 中，这会导致 AI 在执行任务时因需要综合多文件而漏掉质量门禁。 |

## 4. 第一份第三方 Review (Claude Sonnet 4) 交叉核实

| Claude 结论 | 独立判断 | SEPG 视角下的深度解读 |
|---|---|---|
| **ADR > DoD > Changelog** | **同意** | **理由**：ADR 解决的是「方向一致性」，DoD 解决的是「单点合规性」。对 AI 而言，导向错误比单点不规范更难修复。 |
| **反模式：文档规则主义** | **高度同意** | 这是一个隐含的风险。AI 对「永不变更」这种绝对化词汇有执行偏好。建议改为「基准周期变更权」。 |
| **AI 特殊考量：Context Snapshot** | **部分同意** | 我认为不仅仅是 Snapshot，更需要一个 **Technical Debt Ledger**（技术债分类账）。目前 `principles` 底部有标记，但不够系统。 |

### 🔍 识别 Claude 家族的系统性偏见
我观察到 Claude 的分析存在明显的 **「完美协作假设」** 偏见：
- Claude 倾向于通过增加文档类型（如 Context Snapshot）来解决感知局限。
- 它过度强调了「被否决方案记录」，这是因为它自身内存窗口限制导致的对「反复被纠错」的恐惧。
- 它忽略了文档维护的 **「熵增成本」**。对于独立开发者，过多的辅助文档（4个）会显著增加在代码编写之外的非生产性开销。

## 4. 优先级建议 (Top 3 Recommendations)

如果只能增加 3 个文档，我推荐：

1. **`ADR (Architecture Decision Record)` (优先级：极高)**
   - **理由**：记录关键决策的「背景-方案-后果」。防止多个 AI 协作者在不同会话中对同一模块进行反复的、冲突的「优化」。
2. **`DoD (Definition of Done)` (优先级：高)**
   - **理由**：作为 AI 任务结束前的强制 Checklist。应包含：Lint 通过、循环引用检查、S0 风险自查、L10n 完整性。
3. **`Technical-Debt-Ledger.md` (优先级：中)**
   - **理由**：与其写 Changelog 记录过去，不如记录「未来要还的债」。AI 经常在修复 A 时引入了 B（为了速度），需要一个集中地记录这些「有意为之的不完美」。

## 5. 反模式预警

**警告：当前体系正滑向「文档虚假权威 (Pseudo-Authority Index)」反模式。**

- **迹象**：`infrastructure.md` 声称是 API 的权威参考，但它是**手工维护**的。
- **风险**：一旦代码重构而文档未更新，AI 会基于「过期权威」生成大量由于签名不符导致的编译错误代码。
- **对策**：必须建立「文档即代码」的校验机制，或者承认它是「最佳努力参考」而非「权威参考」。

---

## 6. AI 协作者的特殊考量

传统文档是为了「防止人类忘记」，而 AI 文档是为了「防止 AI 漂移」。

1. **Explicit Constraint Density (显式约束密度)**：AI 擅长执行逻辑门禁。在 `conventions.md` 中，应尽量减少描述性文字，增加 **「禁止表 (Prohibition Table)」**。
2. **One-Way Directional Logic (单向导航逻辑)**：目前 `CLAUDE.md` 做得很好。AI 不需要冗余信息，它需要清晰的 **Pointer (指针)**。
3. **Implicit Knowledge Externalization (隐性知识显性化)**：传统项目中「大家心照不宣」的规则（如：不使用三方库），对 AI 必须写在 `principles.md` 里。

---

## 7. 被两份分析遗漏的关键点

**「文档的元衰减期 (Document Half-life)」管理。**

两份报告都谈到了「加什么」，没谈到「怎么减」。独立开发者项目最怕文档体系比代码库还重。
- **建议**：为每个文档标注「维护成本级别」。
- **核心建议：统一 L10n 治理策略。** 当前项目中多次出现由于 Localizable 键值缺失导致的 S1 风险。目前的 14 个文档里，没有任何一个深度定义了 **「国际化与多语言管理流程」**（即从代码中使用硬编码字符串到提取到 `.strings` 的自动化预期）。这在后期是巨大的技术债。
