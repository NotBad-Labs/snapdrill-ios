## 项目背景

iOS 间隔重复学习 App（SnapDrill），Swift 6.2 + SwiftUI + SwiftData，iOS 18.0+，单用户本地优先，无后端。所有 Repository 均为 `@MainActor final class`，共享同一个 `mainContext`。

### 已完成的相关修复（本次不重复审查）

- `ReviewRepository.updateSubjectUsage/Source/Grade`：已在 PR #84 中移除内部 `save()`，改为纯内存操作，由 ViewModel 统一 `saveContext()` 收口。

### 关键设计背景

- `SubjectRepository.insertAndSave` 在插入前会先检查同名记录（`fetchCount > 0` 则抛 `DataError.duplicateName`），防止重名
- `TagRepository.fetchOrCreateModel` 是 upsert 语义：存在则返回，不存在则 insert + save
- 三个 Manager Repository（Subject/Source/Grade）结构完全对称
- 所有 Repository 的 `seedDefaultsIfNeeded()` 在 App 启动时由 `DependencyContainer` 调用

## 审查问题

1. **`insertAndSave` 的重名检查与 save 是否原子**：`SubjectRepository.insertAndSave` 先 `fetchCount`，若为 0 再 `insert` + `save`。由于全部在 `@MainActor` 单线程执行，两步之间没有 `await` 挂起点，这个检查是否足够安全？`DataError.duplicateName` 是否是正确的错误类型？

2. **`TagRepository.fetchOrCreateModel` 的 upsert 安全性**：`fetchOrCreate` 先 fetch，若不存在则 `insert` + `save`，成功后返回新 Tag。若 `save` 失败，新 Tag 是否会留在 mainContext 成为脏数据（缺少 rollback）？调用方（`CaptureResultViewModel`、`LibraryEditViewModel`）在失败时能否正确处理？

3. **`seedDefaultsIfNeeded` 的错误静默**：三个 Repository 的 `seedDefaultsIfNeeded` 在 catch 块只打 log，启动时若播种失败用户看到空列表但无任何提示。这在生产环境中的影响有多大？是否需要更明确的降级处理？

4. **`deleteAll` 跨 Repository 的链式调用**：`RepositoryContainer.deleteAllData()` 依次调用 `review.deleteAll()`、`subject.deleteAll()`、`source.deleteAll()`、`tag.deleteAll()`、`grade.deleteAll()`，每个方法内部各自 `save()`。若中间某步失败，前面已删除的数据无法恢复。这种链式多步删除在本 App 场景下（Settings 一键清空）风险如何评估？有无比现在更安全的实现方式？

5. **`GradeRepository` 是否有 `insertAndSave` 的重名保护**：SubjectRepository 和 SourceRepository 的 `insertAndSave` 都有 `fetchCount > 0` 的重名检查，`GradeRepository.insertAndSave` 是否也有同样的保护？若无，用户是否可能创建同名年级？

### 问题 1：insertAndSave 重名检查原子性

🟢 **无问题 / 建议**

- **文件与行号**：`SubjectRepository.swift` L:94-103
- **分析**：由于全部方法处于 `@MainActor`。在当前“单用户、本地优先、单 mainContext”的架构设定下，主线程内的连续同步语句执行中**不存在** `await` 挂起点。因此，这段单线程执行的指令序列在应用内部是绝对串行的，不会有另一个界面的保存逻辑穿插进入导致“Time-of-check to time-of-use” 的竞态条件。`DataError.duplicateName` 的定义符合上下文报错需求。
- **说明**：此原子性仅立足于当前的同步主线程设计。如果是通过跨隔离域或异步 Context 的高并发写入（比如后台同步），则这种应用级别的检查依然无法阻止 SQLite 层面的并发复写，此时需要底层 Unique Constraint。目前阶段是够用的。

### 问题 2：TagRepository.fetchOrCreateModel upsert 安全性

🔴 **严重**

- **文件与行号**：`TagRepository.swift` L:43-55
- **分析**：代码 `modelContext.insert(newTag)` 后立刻紧跟 `try modelContext.save()`。当 `save()` 因为各种原因抛出异常退出函数时，新插入的且未经物理保存的 `newTag` 对象并没有被清除（**缺少 `rollback()` 或 `modelContext.delete()`**），而是以“脏状态”继续潜伏在跨局域享用的 `mainContext` 中。
如同之前的审查，这会导致该脏数据在 ViewModel 层任意无关的操作触发的全局存盘被隐式和静默带入。这种带有持久化意图的数据写入设计在底层 Repository 进行并不好处理；抛出错误给外层意味着调用方即便知道错了也要负责擦屁股给别人发起的事务执行 rollback。

### 问题 3：seedDefaultsIfNeeded 错误静默

🟡 **警告**

- **文件与行号**：`SubjectRepository.swift` L:39-74 等三处文件
- **分析**：如果在数据库初建时发生写入落盘失败（极小概率事件但绝非为 0，例如沙盒 I/O 问题或表结构迁移错误），它仅仅只是打下 Exception 日志。用户会直接面对一个完全空的列表页，很多以之为强依赖的前端业务（例如 Capture 预选框）会存在未知的数据越界越野问题或无法提交表单。
- **建议**：启动初始化这种级别的数据，如果出错最好抛给 `DependencyContainer` 处理（例如进行强硬的重启重试或者弹窗告知数据损坏），以避免出现空数据库的业务穿透。

### 问题 4：deleteAll 链式调用的失败风险

🔴 **严重**

- **文件与行号**：`SubjectRepository.swift` L:120-123（其他 Repository 同理）
- **分析**：这是一个**完全破坏了事务一致性**的设计。各 Repository 的 `deleteAll()` 逻辑全都是先 delete 再自行调用 `try modelContext.save()` 落实到磁盘上。
在 `RepositoryContainer.deleteAllData()` 被链式调用时：比如 `review.deleteAll()`（已持久化删除完毕），随后到 `subject.deleteAll()` 异常抛出了报错。这时候代码停止，结果是“题库完全被删光了，但是学科分类和来源全都残留在这个用户设备上，一键清空只清空了一部分”，并且因为之前的记录已经 `save` 物理落盘，没有进行任何跨实体级别的 `rollback` 可能。
- **建议**：Repository 中的增删指令应该改为**纯内存方法**。`RepositoryContainer.deleteAllData()` 应当作为唯一的事务管理者，在连续下达一系列所有模型的 `modelContext.delete(...)` 指令结束后，在末尾由外部发起一个唯一且统合的 `try context.save()`。如果失败就全体不删并回滚。

### 问题 5：GradeRepository 重名保护

🟢 **无问题**

- **文件与行号**：`GradeRepository.swift` L:89-98
- **分析**：经过验证，`GradeRepository` 内部完整包含了相同的预检查重名保护：

  ```swift
  let descriptor = FetchDescriptor<GradeModel>(predicate: namePredicate)
  if try modelContext.fetchCount(descriptor) > 0 { throw DataError.duplicateName(...) }
  ```

不存在用户意外创建同名年级的漏洞。

### 综合评估

🔴 **严重：未通过审查**。

核心风险仍在于存储的分布式 `save` 设计导致的事务碎裂。最优先修复：

1. **统一剥夺层内 Save 权**：将所有 Repository（包括本次发现的 `deleteAll()`，`TagRepository` 的 upsert 等）内部强行执行的 `try modelContext.save()` 全部踢出。Repository 只负责生成修改或建立描述删除的操作图谱。
2. **重构一键清理机制**：`clearAllData` 必须被保障在唯一一个同步事物的原子保护伞下（例如统一的一个全局环境 `save` 加上配套处理磁盘垃圾业务）。
