# SnapDrill · 大概需要多少个 PR？

> **结论**：整段 greenfield **不必、也不应该**「几百个 PR」。合理目标是 **约 30–70 个** 合并到 MVP 上架；若快到 **100+**，说明 PR 切得过碎或返工多，应合并任务或收紧范围。

## 怎么估的

| 阶段 | PRD | 粗算 PR 数 | 说明 |
|---|---|---|---|
| 文档 / 架构 | PRD v0.8、ARCHITECTURE、原则 | **~5–10** | 已做一多半 |
| 阶段 0 | 去手写验证、接入 Pipeline | **~3–8** | 含模型迭代，可 spike 分支 |
| Slice 1 壳 | AC-01 部分 | **~2–3** | 已 2+ |
| Slice 2 采集 | AC-02、03 | **~8–15** | 相机、相册、多页、框选、保存分 PR |
| Slice 3–5 | 去手写 UI、列表、复习 | **~10–18** | Library protocol 后拆开 |
| Slice 6–7 | PDF、订阅、CloudKit | **~8–12** | 风险集中，宜小 PR |
| Slice 8 | 五语、a11y、边界 | **~6–10** | 可按语言拆 |
| 上架 / 合规 | 备案文案、商店素材 | **~3–6** | 非代码为主 |
| **合计 MVP** | §13 十条 AC | **~45–80** | 中间值 **~60** |

## 和「几百个 PR」对比

| 情况 | PR 数量级 | 含义 |
|---|---|---|
| **健康** | 30–70 | 一 PR 一边界，8–10 周 MVP |
| **偏多但可接受** | 80–120 | Agent 粒度很细 + 文档/修 bug 多 |
| **警惕** | **200+** | 重复返工、Scope 不清、或从未合并的大分支 |

旧仓库曾 **60+ 远端分支** 是多年 Agent 实验叠加，**不是** MVP 应有的 PR 次数。greenfield 用 **合并后删分支** + 模板约束，避免重演。

## 不单独开 PR 的事（减少噪音）

- 纯 typo、仅 `xcuserdata`（应 ignore）
- 与当前 Slice 无关的「顺手重构」
- 未过 PO 的 PRD 行为变更
